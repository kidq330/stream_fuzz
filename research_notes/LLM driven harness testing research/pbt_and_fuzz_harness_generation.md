## KQ1. What do the PBT-specific papers find, and how is property quality measured?

### Takeaway
LLMs can reliably produce syntactically valid Hypothesis/QuickCheck-style PBTs, but the hard part is *sound, non-trivial* properties: PBT-GPT (Vikram, Lemieux, Sunshine, Padhye) found GPT-4 could synthesize correct PBTs for only ~21% of documentation-extractable properties, needing ~2.4 samples to get one valid-and-sound test; the field measures quality via validity (runs without error on the generator's inputs), soundness (does not fail on correct code), and "property coverage" (kills property-mutants), with later 2025–2026 work adding mutation score, adversarial refinement against "superficial" tests, and agentic end-to-end bug hunting (Hatfield-Dodds/Carlini) across the top-10k PyPI packages.

### Cited Findings

**PBT-GPT / "Can Large Language Models Write Good Property-Based Tests?" (Vikram, Lemieux, Sunshine, Padhye; arXiv 2307.04346, first posted July 2023, revised 2024)**
- The LLM writes both the Hypothesis *generator* (strategies) and the *property assertions* from API documentation; Hypothesis executes them. The paper proposes a methodology considering validity, soundness, and "property coverage, a novel metric that measures the ability of the PBT to detect property violations through generation of property mutants" — [arXiv 2307.04346 (via search)](https://arxiv.org/abs/2307.04346) [abstract/search]
- Evaluation: 40 Python library API methods across GPT-4, Gemini-1.5-Pro and Claude-3-Opus; "with the best model and prompting approach, a valid and sound PBT can be synthesized in 2.4 samples on average"; GPT-4 "was able to automatically synthesize correct PBTs for 21% of properties extractable from API documentation" — [arXiv 2307.04346](https://arxiv.org/pdf/2307.04346) [abstract/search]
- Their automatic soundness metric "is aligned with human judgment of property assertions, achieving a precision of 100% and recall of 97%" — [arXiv 2307.04346](https://arxiv.org/abs/2307.04346) [abstract/search]
- Independent characterization (from a later survey-style summary surfaced by search): current LLMs "can generate syntactically valid property-based tests in frameworks such as Hypothesis (Python) and QuickCheck (Haskell) with moderate success, but the generated properties are frequently trivial or incorrect" — [Guardrailing CPS paper, arXiv 2505.23549 (via search)](https://arxiv.org/html/2505.23549v2) [abstract/search]
- Listed in the community PBT bibliography as the canonical LLM-PBT paper — [ngernest/pbt-bibliography](https://github.com/ngernest/pbt-bibliography) [primary]

**"Understanding the Characteristics of LLM-Generated Property-Based Tests in Exploring Edge Cases" (arXiv 2510.25297, Oct 2025; also IEEE Xplore 11334197)**
- Setup: 16 HumanEval problems whose canonical solutions fail on extended tests; PBT and example-based tests (EBT) both generated by Claude-4-sonnet using Hypothesis; selection criteria: boundary-value bugs (0, negatives, min/max), performance/timeout bugs, structure/combination bugs — [arXiv 2510.25297 (via search)](https://www.arxiv.org/pdf/2510.25297) [abstract/search]
- Result: PBT and EBT each detected 68.75% of the bugs individually; combined 81.25%. PBT was better at performance issues and broad input-space edge cases; EBT better at specific boundary values — [IEEE Xplore 11334197 (via search)](https://ieeexplore.ieee.org/document/11334197/) [abstract/search]
- Weakness: n = 16 problems, single model; no mutation score reported in the surfaced abstract.

**"From Prompts to Properties: Rethinking LLM Code Generation with Property-Based Testing" (FSE 2025 companion, ACM 10.1145/3696630.3728702)**
- Uses PBT as an *evaluation oracle* for StarCoder and CodeLlama on MBPP/HumanEval; finds 30–32% of generated solutions only partially satisfy correctness properties and 18–23% fail outright even when pass@k looks moderate — [ACM DL (via search)](https://dl.acm.org/doi/10.1145/3696630.3728702) [abstract/search]

**"Use Property-Based Testing to Bridge LLM Code Generation and Validation" / PGS (He et al., arXiv 2506.18315, June 2025; later ICML 2026 as "PGS: Effective LLM Code Refinement via Property-Oriented and Structurally Minimal Feedback")**
- Two agents: a Generator writes code; a Tester "manages the PBT life-cycle and formulates semantically rich feedback from property violations"; reports up to 17.4% absolute pass@1 improvement and "relative pass@1 gains of 23–37% over standard TDD" — [search summary of arXiv 2506.18315](https://www.researchgate.net/publication/392941211_Use_Property-Based_Testing_to_Bridge_LLM_Code_Generation_and_Validation) [abstract/search]; ICML 2026 version listed at [OpenReview 6xeSRifGeL via pbt-bibliography](https://github.com/ngernest/pbt-bibliography) [primary listing]
- Note: here PBT is the *feedback signal for code repair*, not a bug-finding deliverable; properties are LLM-written and executed by Hypothesis.

**"Agentic Property-Based Testing: Finding Bugs Across the Python Ecosystem" (Maaz, DeVoe, Hatfield-Dodds, Carlini; NeurIPS 2025 Deep Learning for Code workshop; arXiv 2510.09907)**
- Pipeline (repo): Claude Code (Opus) agent, sandboxed to a per-package venv with write access only to .py/.md in a test dir, performs property mining -> writes Hypothesis tests -> runs pytest -> writes markdown bug reports; a separate Claude Opus 4.1 call scores reports against a rubric (initial and "final" rubric versions published) and exports CSV — [mmaaz-git/agentic-pbt README](https://raw.githubusercontent.com/mmaaz-git/agentic-pbt/main/README.md) [primary]
- Evaluation sample: "15 hardcoded pypi packages, 15 hardcoded stdlib packages, and 70 randomly sampled pypi packages" (100 repos), plus an example config for the top 10,000 PyPI packages; 5 bugs were manually reported to maintainers (Appendix B); `paper/results/` holds ~120 per-package result directories (numpy, pandas, django, flask, requests, sqlalchemy, pydantic, cryptography, stdlib modules, etc.) — [agentic-pbt/paper](https://github.com/mmaaz-git/agentic-pbt/tree/main/paper) [primary]; [results dir](https://github.com/mmaaz-git/agentic-pbt/tree/main/paper/results) [primary]
- Bug site and Hypothesis blog post exist (https://mmaaz-git.github.io/agentic-pbt-site, https://hypothesis.works/articles/claude-code-plugin/) but were blocked; aggregate true/false-positive counts could not be verified — [README](https://raw.githubusercontent.com/mmaaz-git/agentic-pbt/main/README.md) [primary for URLs only]
- Significance: this is the most direct "LLM writes PBT, Hypothesis finds the bug, LLM-judge triages" system from the Hypothesis maintainers; it is the de-facto "Hypothesis Ghostwriter + LLM" successor (no paper was found that literally combines `hypothesis.extra.ghostwriter` with an LLM).

### Inferences
- Quality measurement has converged on a three-part rubric for LLM-written properties: (1) validity (test runs, generator produces in-domain inputs), (2) soundness (no false alarms on correct code), (3) strength (property coverage / mutation score / adversarial robustness). Vacuity is attacked indirectly via mutation-style metrics (PBT-GPT's property mutants; "Beyond Superficial Tests"), and via Tyche-style generator visualizations.
- The 21%-of-properties figure (PBT-GPT, GPT-4) and the "frequently trivial or incorrect" characterization suggest the binding constraint in 2023–24 was oracle quality, not generator syntax; by 2025 the Hatfield-Dodds/Carlini agentic system shifts the design to *many cheap properties + LLM-judge triage* rather than trying to make each property sound.
- PBT-as-feedback-for-code-generation (PGS, "From Prompts to Properties") is a different use than PBT-as-bug-finder; the report should keep these separate because the success metric (pass@1) says nothing about false-positive rates of the properties.

### Gaps
- Could not fetch the PBT-GPT PDF: per-model breakdown (GPT-4 vs Gemini-1.5-Pro vs Claude-3-Opus), the exact definition of "property coverage", and token/cost figures are missing.
- Agentic-PBT aggregate numbers (bug reports generated, judged-genuine rate, maintainer-confirmed count, $ per bug) exist on the blocked bug site / arXiv paper and are unverified here.
- PBT-Bench, "Beyond Superficial Tests", Guardrailing-CPS, and NL-to-properties (mobile) numbers were not retrievable.
- No paper was found on LLM synthesis of QuickCheck/PropEr generators specifically, nor on Rust proptest generation; the closest is Gentoo (Java/JQF, see KQ2).

## KQ2. Fuzz-driver / harness generation: systems, loops, harness-validity problems, and results

### Takeaway
From Google's OSS-Fuzz-Gen (2023–24) through PromptFuzz (CCS'24), Zhang et al.'s ISSTA'24 study, CKGFuzzer (ICSE'25 industry), and 2025–26 agentic systems (HarnessAgent, QuartetFuzz, MASFuzzer, Gentoo), the consistent pattern is: the LLM drafts the harness/generator, a compile-run-fuzz loop feeds back build errors, runtime crashes, and coverage, and the dominant failure mode is *semantically wrong harnesses* (API misuse) producing fake crashes — e.g., 168 of 199 crashes in one study were API-misuse false positives — which newer systems attack with knowledge graphs, protocol checks, adversarial probes, and crash triage agents, reaching ~human-parity coverage (QuartetFuzz: +0.03pp line vs human "Gold" harnesses) at ~$5/harness.

### Cited Findings

**OSS-Fuzz-Gen (Google, Aug 2023 –)**
- Aug 2023 pilot: 14 of 31 OSS-Fuzz projects got compiling new targets with coverage increases of 0–31%; TinyXML2 line coverage went from 38% to 69% "without any interventions"; per-project gains tinyxml2 29.84%, inih 29.67%, lodepng 26.21%, libarchive 23.39%, cmark 21.61% — [google.github.io/oss-fuzz research page (via search)](https://google.github.io/oss-fuzz/research/llms/target_generation/) [abstract/search]
- README (experiment of Jan 31, 2024): 1,300+ benchmarks from 297 open-source projects; 160 C/C++ projects with valid generated targets; max line-coverage increase 29% over existing human-written targets; 30 new bugs/vulnerabilities incl. CVE-2024-9143 (OpenSSL OOB read/write), OOB/UAF/stack-underflow/uninitialised-memory bugs in cJSON, libplist, hunspell, zstd, gdbm, SQLite3, plus a Java RCE and a regex DoS; models: Vertex code-bison, Gemini Pro/Ultra/1.5, GPT-3.5/4/4o/4-turbo; four metrics: compilability, runtime crashes, runtime coverage, line-coverage diff — [google/oss-fuzz-gen README](https://github.com/google/oss-fuzz-gen) [primary]
- Agent pipeline: FunctionAnalyzer -> Prototyper -> ExecutionStage -> CrashAnalyzer / ContextAnalyzer / CoverageAnalyzer; "agents are stacked in a pipeline and executed using the results obtained from previously executed agents"; crash stacktraces and coverage reports are consumed by later agents — [oss-fuzz-gen agent_tests readme](https://github.com/google/oss-fuzz-gen/blob/main/agent_tests/readme.md) [primary]
- Nov 2024 blog ("Leveling Up Fuzzing"): 26 new vulnerabilities reported incl. OpenSSL CVE-2024-9143 (present "nearly two decades"); project count grew from 160 to 272, "an additional 370,000 lines of code" covered; largest single-project gain 77 -> 5,434 lines (~7,000%); the LLM "generate[s] and improve[s] fuzz targets, fix[es] build and runtime issues in those targets, and help[s] triage crashes" — [The Hacker News summary of Google blog](https://thehackernews.com/2024/11/googles-ai-powered-oss-fuzz-tool-finds.html); [Bugflation summary](https://bugflation.com/systems/google-oss-fuzz-ai/) [secondary; Google blog blocked]
- Later comparisons: OSS-Fuzz-Gen "produces working harnesses for only 64/100 cases; its average coverage trails by 6.9–8.3pp" vs QuartetFuzz — [arXiv 2605.21824 (via search)](https://arxiv.org/pdf/2605.21824) [abstract/search]

**"How Effective Are They? Exploring LLM-Based Fuzz Driver Generation" (Zhang et al., ISSTA 2024; arXiv 2307.12469)**
- Dataset: 86 fuzz-driver-generation questions from 30 widely-used C projects; 6 prompting strategies x 5 LLMs x 5 temperatures; 736,430 drivers generated; 0.85 billion tokens ($8,000+); 3.75 CPU-years of fuzzing comparing against industry (OSS-Fuzz) drivers — [ACM DL / arXiv (via search)](https://dl.acm.org/doi/abs/10.1145/3650212.3680355) [abstract/search]
- Best configuration solved 91% of questions (78/86); all top-20 configurations solved >= 50%; beneficial design choices: repeated queries, querying with examples, iterative querying; "LLMs face difficulties in generating effective fuzz drivers for APIs with intricate specifics"; LLM drivers showed "comparable fuzzing outcomes compared to OSS-Fuzz drivers"; insights were fed into OSS-Fuzz-Gen — [arXiv 2307.12469 (via search)](https://arxiv.org/pdf/2307.12469) [abstract/search]
- Validity problem statement: "Current validation methods only detect syntactic problems or shallow logic errors and fail to detect complex semantic errors like incorrect library usage, which when used as fuzz drivers incurs many false positives" — [search summary citing Zhang et al./CKGFuzzer](https://scispace.com/pdf/understanding-large-language-model-based-fuzz-driver-229730hxrn.pdf) [abstract/search]

**PromptFuzz (Lyu et al., CCS 2024; arXiv 2312.17677)**
- LLM writes drivers from function signatures + docs; libFuzzer is the engine and supplies coverage; "coverage-guided prompt mutation" prioritizes API combinations; "driver sanitization" checks "syntax, semantics, behavior, and coverage" and filters erroneous drivers before fuzzing — [PromptFuzz README](https://github.com/PromptFuzz/PromptFuzz) [primary]
- Results: 40.12% branch coverage across libraries (libaom, libvpx, libmagic, libTIFF, sqlite3, …), 1.61x OSS-Fuzz and 1.67x Hopper; 33 confirmed security bugs from 49 unique crashes; CVE-2023-6277, CVE-2023-52355, CVE-2023-52356 — [PromptFuzz README](https://github.com/PromptFuzz/PromptFuzz) [primary] (search summary gives 1.63x for Hopper — minor discrepancy between README and search summary)

**CKGFuzzer (ICSE 2025 Industry Challenge; arXiv 2411.11532)**
- CodeQL-extracted code knowledge graph (APIs + call graph) feeds an LLM agent system that writes drivers and seeds, repairs compile errors, and analyzes crash reports — [security-pride/CKGFuzzer README](https://github.com/security-pride/CKGFuzzer) [primary]; claims superior coverage vs PromptFuzz and OSS-Fuzz — [arXiv 2411.11532 (via search)](https://arxiv.org/abs/2411.11532) [abstract/search]
- A search-surfaced figure (source attribution ambiguous between CKGFuzzer and Zhang et al.): "LLM-based fuzzer tools identified 199 unique crashes, of which 168 were determined to be caused by the misuse of library APIs" — [search summary](https://arxiv.org/pdf/2411.11532) [abstract/search; attribution unverified]

**HarnessAgent (arXiv 2512.03420, Dec 2025)**
- Tool-augmented LLM pipeline; "improved the three-shot success rate by approximately 20% over existing techniques, achieving 87% for C targets and 81% for C++ targets"; "over 75% of harnesses ... increased the target function coverage compared to baselines, with an improvement exceeding 10%" — [search summary](https://arxiv.org/html/2512.03420v1) [abstract/search]

**QuartetFuzz / "Quality-Assured Fuzz Harness Generation via the Four Principles Framework" (arXiv 2605.21824, 2026)**
- Four principles: P1 Logic Correctness (no leaks/UAF/stale state, 8 sub-checks), P2 API Protocol Compliance (init order, lifecycle, cleanup, 8 sub-checks), P3 Security Boundary Respect (public API only), P4 Entry Point Adequacy; stages: Logic Group Discovery (danger-score ranking) -> API Protocol Research -> Static-Driven Build against the OSS-Fuzz Dockerfile with self-review -> Adversarial Validation (agent crafts an attack blob run under ASan/LSan to catch harness bugs; GDB breakpoint confirms the harness reaches the target API) — [OwenSanzas/QuartetFuzz README](https://github.com/OwenSanzas/QuartetFuzz) [primary]
- Models/cost: Claude Opus 4.6 for discovery/protocol agents (50/30 turns), Claude Sonnet 4.6 for harness generation + probes (50 turns); ~$120 for a 25-case run with Opus (~$4.80/harness), ~$10 with Gemini Flash; ~45 min on 4 workers (Flash) vs ~5 h (Opus); coverage protocol "10 x 600 s libFuzzer, empty corpus, ASan; per-case median"; 100 cases total — [QuartetFuzz README](https://github.com/OwenSanzas/QuartetFuzz) [primary]
- Results: vs human "Gold" harnesses +0.03pp line / -0.07pp branch (parity); beats OSS-Fuzz-Gen by 6.9–8.3pp and PromeFuzz by 4.1–5.2pp; 42 bug reports across 23 projects with a 4.8% false-positive rate; checks "intercepted 58 harness-induced crashes that would have been false-positive reports"; Scheduzz is "the only prior pre-generation checker that validates types, not API protocol" and is closed-source — [search summary of arXiv 2605.21824](https://arxiv.org/html/2605.21824v1) [abstract/search]

**MASFuzzer (arXiv 2604.17977, 2026)** — multidimensional API sequences + adaptive scheduling; coverage up in 11 libraries, +8.54% / +15.07% / +37.95% vs PromeFuzz / CKGFuzzer / Liberator — [search summary](https://arxiv.org/pdf/2604.17977) [abstract/search] (the search summary also repeats HarnessAgent's 87%/81% figures under MASFuzzer; likely a conflation — treat as unverified)

**Gentoo / "Fuzzing with Agents? Generators Are All You Need" (Vikram, Padhye; arXiv 2604.01442, 2026; listed as ASE 2026 "Predicate-Guided Synthesis of Input Generators")**
- An LLM coding agent with terminal access and library source "iteratively synthesize[s] and refine[s] an input generator" for JQF/Zest targets, optionally with predicate-level coverage feedback; three configurations vs human-written generators on 7 real-world Java libraries — [search summary](https://arxiv.org/html/2604.01442) [abstract/search]
- Agent generators achieved statistically significantly higher branch coverage on 4/7 benchmarks, +11–21% on average; "coverage guidance and mutation strategies are not statistically significantly beneficial for agent-synthesized generators, but is significant for all human-written generators" — [search summary](https://arxiv.org/html/2604.01442) [abstract/search]; bibliography entry — [pbt-bibliography](https://github.com/ngernest/pbt-bibliography) [primary listing]

**Other harness/driver systems surfaced (numbers not retrievable)**: LibLMFuzz (black-box libraries, arXiv 2507.15058), Scheduzz (constraint-based drivers, arXiv 2507.18289), "Coverage-Guided Multi-Agent Harness Generation for Java Library Fuzzing" (arXiv 2603.08616, 2026), "Thinking More, Harnessing Better: State Machine Guided Harness Generation" (arXiv 2607.07007, 2026), PromeFuzz, Liberator, Hopper (non-LLM interpretative library fuzzing baseline) — [search listings](https://arxiv.org/pdf/2507.15058); position papers "Towards Reliable LLM-Driven Fuzz Testing: Vision and Road Ahead" (arXiv 2503.00795) and "Agentic Fuzzing: Opportunities and Challenges" (arXiv 2605.10074) — [search listing](https://arxiv.org/pdf/2605.10074).

**Adjacent "LLM writes the spec/grammar, engine fuzzes" systems (not harnesses per se)**
- KernelGPT (ASPLOS 2025): LLM writes Syzkaller specs (syzlang); specs validated by `syz-check`, errors fed back for automatic repair; 1,000 specs generated; 24 new Linux kernel bugs, 11 CVEs (12 fixed); specs merged upstream into Syzkaller — [ise-uiuc/KernelGPT](https://github.com/ise-uiuc/KernelGPT) [primary]
- ChatAFL (NDSS 2024): LLM extracts a protocol grammar for structure-aware mutation, enriches seeds, and generates messages to escape coverage plateaus; built on AFLNet; subjects kamailio, pure-ftpd, live555, proftpd, exim — [ChatAFLndss/ChatAFL](https://github.com/ChatAFLndss/ChatAFL) [primary]; 29.55%/25.75% more states and 5.81%/6.74% more code than baselines, 9 previously unknown vulnerabilities — [search summary](https://mboehme.github.io/paper/NDSS24-chatafl.pdf) [abstract/search]
- LLM-as-input-generator line (LLM replaces the engine rather than driving it): TitanFuzz (ISSTA 2023; Codex seeds + InCoder mutation; +30.38%/+50.84% coverage on TF/PyTorch; 65 bugs, 55 confirmed, 44 previously unknown, 21 fixed) — [ise-uiuc/TitanFuzz](https://github.com/ise-uiuc/TitanFuzz) [primary]; FuzzGPT (ICSE 2024; 76 bugs, 49 confirmed new, 11 high-priority; +36.03%/+60.70% coverage over TitanFuzz) — [search summary](https://arxiv.org/pdf/2304.02014) [abstract/search]; WhiteFox (OOPSLA 2024; analysis-LLM summarizes optimization source, generation-LLM writes tests; 96 bugs, 80 confirmed new, 61 fixed on PyTorch Inductor/XLA/TFLite/LLVM) — [ise-uiuc/WhiteFox](https://github.com/ise-uiuc/WhiteFox) [primary] (search summary says 101/92/70 — version discrepancy); Fuzz4All (ICSE 2024; autoprompting + LLM generation loop; +36.8% coverage, 98 bugs, 64 confirmed) — [fuzz4all repo](https://github.com/fuzz4all/fuzz4all) [primary for approach]; [search summary for numbers](https://arxiv.org/pdf/2308.04748) [abstract/search]; LLAMAFUZZ (LLM mutates structured inputs inside AFL++; Magma: 41 bugs avg / 47 unique, +27.19% coverage over AFL++ on 10/15 targets) — [search summary](https://arxiv.org/abs/2406.07714) [abstract/search]

### Inferences
- The feedback-loop ladder across these systems is: (1) compile/link errors -> LLM repair (all systems since OSS-Fuzz-Gen 2023); (2) runtime crash on first run -> LLM repair (OSS-Fuzz-Gen, Zhang et al.); (3) coverage delta vs existing harnesses -> prompt mutation / API re-selection (PromptFuzz, OSS-Fuzz-Gen CoverageAnalyzer, Gentoo predicate coverage); (4) crash triage for harness-induced false positives (OSS-Fuzz-Gen CrashAnalyzer, CKGFuzzer, QuartetFuzz adversarial probes, Scheduzz type checks). Only step (4) addresses the dominant failure mode, and it is where 2025–26 work concentrates.
- Gentoo's finding that coverage guidance no longer helps once the generator encodes semantics suggests the "LLM writes the generator, engine does blind random sampling" split may suffice for well-structured inputs; this is the strongest evidence that an LLM-written *generator* (PBT style) can substitute for grey-box mutation, but it is 7 Java libraries only.
- Cost is converging: Zhang et al.'s $8k study was ~$0.01/driver at 2023 prices but needed massive sampling; QuartetFuzz's ~$5/harness (Opus 4.6) or ~$0.40 (Gemini Flash) is the first per-harness cost tied to a human-parity coverage result.

- Attribution of the "199 crashes / 168 API misuse" figure is unverified.

## KQ3. LLM-generated metamorphic relations and test oracles vs generated example tests

### Takeaway
LLM-based oracle work shows large gains over neural predecessors (TOGLL: 3.8x more correct assertion oracles and 4.9x more exception oracles than TOGA, whose assertions were 47% false positives), and LLMs are now used to lift hard-coded example pairs into executable metamorphic relations (MR-Adopt: input transformations applicable to all source inputs for 72% of encoded MRs, +33.33pp over vanilla GPT-3.5), but natural-language MRs still carry false-positive rates comparable to true-positive rates in some domains, and "anchoring" of LLM oracles to the implementation under test is an emerging concern.

### Cited Findings
- TOGA baseline (background, 2022): generates assertion oracles only 38% of the time; of those 47% are false positives; exception-oracle false-positive rate 81% — [TOGLL arXiv 2405.03786 (via search)](https://arxiv.org/pdf/2405.03786) [abstract/search]
- TOGLL (Hossain et al., ICSE 2025): "3.8 times more correct assertion oracles and 4.9 times more exception oracles than TOGA"; first study of LLM oracles' ability to find many unique bugs — [ACM DL (via search)](https://dl.acm.org/doi/10.1109/ICSE55347.2025.00098) [abstract/search]
- 2025 follow-up on oracle validity: LLMs generate "at least 1 valid assertion in between 89.34% and 93.76% of the cases" — [search summary](https://arxiv.org/abs/2405.03786) [abstract/search; paper identity unclear]
- "Do LLMs generate test oracles that capture the actual or the expected program behaviour?" (arXiv 2410.21136) — raises the anchoring question — [search listing](https://arxiv.org/pdf/2410.21136); "Oracles That Cannot Fail: Anchoring and the Expectation That Moves With the Fault" (arXiv 2608.17214, 2026) names the phenomenon — [search listing](https://arxiv.org/pdf/2608.17214) [titles only]
- MR-Adopt (Xu et al., ASE 2024): deduces input-transformation functions from hard-coded source/follow-up inputs in existing tests; LLM infers intent and generates extra source/follow-up pairs; transformations applicable to all source inputs for 72.00% of encoded MRs, "33.33% more than using vanilla GPT-3.5" — [ACM DL (via search)](https://dl.acm.org/doi/10.1145/3691620.3696020) [abstract/search]
- GenMorph (Terragni et al., arXiv 2312.15302; non-LLM genetic programming baseline): fitness rewards MRs with fewer false positives and false negatives; effective MRs for 18/23 Java methods; raises fault detection of automated suites — [arXiv 2312.15302 (via search)](https://arxiv.org/html/2312.15302) [abstract/search]
- LLM MR-inference workflows: "Towards metamorphic testing with LLM-based workflows: MR inference and follow-up test case generation" (Information & Software Technology, 2026) — [ScienceDirect (via search)](https://www.sciencedirect.com/science/article/pii/S0950584926001394) [title]; "Bidirectional Empowerment of Metamorphic Testing and LLMs: A Systematic Survey" (arXiv 2605.13898) notes LLM-assisted MR generation includes few-shot prompting, domain-customised GPTs and multi-agent RAG pipelines — [search summary](https://arxiv.org/pdf/2605.13898) [abstract/search]
- False positives of NL-based MRs: in MT-for-NLP, average true-positive (21%) and false-positive (23%) rates were similar; LGMT grounds MRs in first-order logic (20 MR types) to avoid this — [search summary of arXiv 2605.23965 / Terragni ICSME 2025](https://valerio-terragni.github.io/assets/pdf/cho-icsme-2025.pdf) [abstract/search]
- Metamorphic oracles for fuzzing specifically: "Investigating Metamorphic Fuzz Oracle Enhancement via Large Language Models" (arXiv 2606.14164, 2026) — [search listing](https://arxiv.org/pdf/2606.14164) [title only; content blocked]
- Example-vs-property comparison: PBT and EBT each found 68.75% of edge-case bugs; union 81.25% (16 HumanEval problems, Claude-4-sonnet) — [arXiv 2510.25297 (via search)](https://www.arxiv.org/pdf/2510.25297) [abstract/search]

### Inferences
- LLM-generated MRs/oracles are evaluated the same way as LLM PBT properties: false-positive rate on correct code plus mutation/fault detection; the MT community's finding that FP ~= TP for NL MRs is the metamorphic analogue of PBT-GPT's soundness problem.
- The most robust designs do not ask the LLM for a novel oracle at all: MR-Adopt lifts an existing human example into a relation (oracle authored implicitly by a human), and PGS/Gentoo-style systems keep the oracle to crashes/sanitizers or implementation-independent properties.

### Gaps
- No quantitative comparison was found that pits LLM-generated MRs directly against LLM-generated example tests on the same bug set, except the small 2510.25297 PBT-vs-EBT study.
- MR-Adopt's fault-detection/mutation-score numbers and the 2606.14164 fuzz-oracle results were not retrievable.

## KQ5. "Why not just ask the LLM to find the bug?" — token cost, recall, precision, hallucinated bugs

### Takeaway
Papers and benchmarks on direct LLM vulnerability detection report false-positive rates above 50% and F1 near 20% on realistic data (a 7B model drops from 68.26% F1 on BigVul to 3.09% on PrimeVul), while the harness-driven systems report concrete, reproducible crashes with FP rates like 4.8% (QuartetFuzz) and dozens of confirmed CVEs; the harness route is defensible because the engine supplies a ground-truth oracle (sanitizer crash, property failure) and a reproducer, whereas LLM-only reports require human verification of possibly hallucinated bugs.

### Cited Findings
- "The false positive rate of current mainstream LLMs in vulnerability detection is generally higher than 50%"; "no prior benchmark reports false positive rates" — [search summary of arXiv 2605.23243 / 2504.13474](https://arxiv.org/html/2605.23243v3) [abstract/search]
- PrimeVul (Ding et al., arXiv 2403.18624): "a state-of-the-art 7B model scored 68.26% F1 on BigVul but only 3.09% F1 on PRIMEVUL"; existing benchmarks "significantly overestimate" performance — [search summary](https://arxiv.org/pdf/2403.18624) [abstract/search]
- Repository-level benchmarking: "even the best-performing models achieve F1 scores of only around 20%"; some models "classify approximately 69% of all samples as vulnerable ... regardless of ground truth" — [search summary](https://www.researchgate.net/publication/394271008_Benchmarking_LLMs_and_LLM-based_Agents_in_Practical_Vulnerability_Detection_for_Code_Repositories) [abstract/search]
- Cost of exhaustive LLM sampling for harnesses: Zhang et al. spent 0.85B tokens (~$8,000) generating 736,430 drivers for 86 questions and 3.75 CPU-years fuzzing them — [search summary](https://dl.acm.org/doi/abs/10.1145/3650212.3680355) [abstract/search]
- Harness-route precision: QuartetFuzz 42 bug reports / 23 projects / 4.8% FP; 58 harness-induced crashes intercepted before reporting — [search summary](https://arxiv.org/html/2605.21824v1) [abstract/search]; PromptFuzz 33 confirmed bugs from 49 unique crashes (~67% crash->bug) — [PromptFuzz README](https://github.com/PromptFuzz/PromptFuzz) [primary]; OSS-Fuzz-Gen 26 vulns incl. OpenSSL CVE-2024-9143 — [THN summary](https://thehackernews.com/2024/11/googles-ai-powered-oss-fuzz-tool-finds.html)
- Harness-route failure mode is *also* hallucination, but of API usage: "crashes may stem from the incorrect fuzz driver, improper API usage, or deeper issues within the system" and "LLMs face difficulties ... for APIs with intricate specifics" — [search summaries](https://arxiv.org/pdf/2307.12469) [abstract/search]
- Agentic-PBT addresses report quality by having a second model (Claude Opus 4.1) score each agent-written bug report against a rubric before humans look — [agentic-pbt README](https://raw.githubusercontent.com/mmaaz-git/agentic-pbt/main/README.md) [primary]
- Gentoo: with a strong agent-written generator, the engine's coverage guidance/mutation becomes statistically unnecessary — i.e. the LLM's value is in encoding structure, not in searching — [search summary](https://arxiv.org/html/2604.01442) [abstract/search]
- Position papers framing this trade-off: "Agentic Fuzzing: Opportunities and Challenges" (arXiv 2605.10074) and "Towards Reliable LLM-Driven Fuzz Testing: Vision and Road Ahead" (arXiv 2503.00795) — [search listings](https://arxiv.org/pdf/2503.00795) [titles only]

### Inferences
- No paper found runs a controlled head-to-head of "LLM reads code and reports bugs" vs "LLM writes harness, fuzzer finds bugs" on the same targets with matched token budgets; the comparison in the literature is indirect (vulnerability-detection benchmarks vs harness-generation evaluations). This is a notable methodological hole.
- The harness route converts an unverifiable LLM claim into a verifiable artifact (reproducer + sanitizer report), which is why the reported FP rates (4.8%) are an order of magnitude below LLM-only detection (>50%); but harness FP is dominated by API misuse, so the engine's oracle only helps if the harness semantics are validated.

### Gaps
- No token-matched cost comparison between LLM-only detection and harness generation was found.
- Google Big Sleep (LLM-only agent) vs OSS-Fuzz-Gen results could not be retrieved for a same-organization comparison.

## KQ6. Benchmarks used and their weaknesses

### Takeaway
Harness-generation papers mostly build ad-hoc benchmarks from OSS-Fuzz projects (Zhang et al.: 86 questions/30 projects; OSS-Fuzz-Gen: 1,300+ benchmarks/297 projects; QuartetFuzz: 100 cases with human "Gold" harnesses), compare coverage against the human OSS-Fuzz harness, and count confirmed bugs/CVEs; ground-truth suites (Magma, ARVO) are used mainly by input-generation fuzzers (LLAMAFUZZ on Magma), and all inherit known weaknesses: FuzzBench is coverage-only, Magma's sparse forward-ported bugs and inflated crash counts, and LLM-specific risks of training-data contamination and non-reproducibility that the position papers flag.

### Cited Findings
- OSS-Fuzz-Gen: 1,300+ benchmarks from 297 projects; metrics compilability, runtime crashes, runtime coverage, line-coverage diff vs existing human targets — [oss-fuzz-gen README](https://github.com/google/oss-fuzz-gen) [primary]
- Zhang et al.: 86 questions / 30 C projects, compared to industry OSS-Fuzz drivers over 3.75 CPU-years — [search summary](https://dl.acm.org/doi/abs/10.1145/3650212.3680355) [abstract/search]
- QuartetFuzz: 100 cases, human "Gold" harness baseline, "10 x 600 s libFuzzer, empty corpus, ASan; per-case median", cross-fork fairness comparisons vs OSS-Fuzz-Gen and PromeFuzz — [QuartetFuzz README](https://github.com/OwenSanzas/QuartetFuzz) [primary]
- PBT side: PBT-GPT uses 40 hand-picked Python API methods; 2510.25297 uses 16 HumanEval problems; PGS/"From Prompts to Properties" use HumanEval/MBPP; Agentic-PBT uses 100 sampled PyPI/stdlib packages and a top-10k PyPI config; PBT-Bench (2026) is the first dedicated PBT agent benchmark; Etna is the PBT-framework evaluation platform — [pbt-bibliography](https://github.com/ngernest/pbt-bibliography) [primary]; [agentic-pbt/paper](https://github.com/mmaaz-git/agentic-pbt/tree/main/paper) [primary]
- Magma: ground-truth forward-ported bugs; criticisms: evaluation "solely based on bug coverage and can be misleading due to the sparse distribution of real-world bugs"; "crash count is often inflated, even after attempts at de-duplication" — [search summary of arXiv 2608.28016 / 2405.10220](https://arxiv.org/pdf/2608.28016) [abstract/search]
- FuzzBench: "relies solely on coverage profiles ... dismisses the need for ground truth ... more coverage does not necessarily imply higher effectiveness" — [search summary of SoK: Prudent Evaluation Practices for Fuzzing, arXiv 2405.10220](https://arxiv.org/pdf/2405.10220) [abstract/search]
- ARVO: 6,000+ reproducible real-world memory vulnerabilities across 250+ OSS-Fuzz projects — [search summary](https://arxiv.org/pdf/2607.08949) [abstract/search]
- LLAMAFUZZ evaluated on Magma (41 bugs avg / 47 unique) — [search summary](https://arxiv.org/abs/2406.07714) [abstract/search]
- Reproducibility concern: "Large Language Models for Software Engineering: A Reproducibility Crisis" (arXiv 2512.00651) surfaced alongside PBT-GPT in search — [search listing](https://arxiv.org/pdf/2512.00651) [title only]
- Mutation-score vs coverage disconnect for LLM tests ("100% coverage but only 4% mutation score") — [search summary](https://arxiv.org/html/2511.21382v1) [abstract/search]

### Inferences
- Because the main baseline is "the existing human OSS-Fuzz harness", results like "+29% line coverage" are relative to whatever harness a maintainer happened to write; several papers (Zhang et al., QuartetFuzz) explicitly report *parity* rather than superiority, which is the more honest framing.
- Defects4J / SWE-bench-style sets did not appear in any PBT/harness paper surfaced here; the PBT line uses HumanEval/MBPP (contamination-prone), the harness line uses OSS-Fuzz corpora (also likely in training data — OSS-Fuzz harnesses are public on GitHub), and no paper surfaced controls for the LLM having seen the human harness.

### Gaps
- No LLM-harness paper surfaced that uses Magma/ARVO ground truth to measure recall of known bugs; whether such evaluations exist in the blocked full texts is unknown.
- Contamination analysis (did the model see the OSS-Fuzz harness?) was not found in any abstract.
