## KQ1. Does an LLM write the Coyote test / P model / Shuttle-Loom harness / stateful PBT model, and a systematic explorer then find bugs? What were the results?

### Takeaway
There is no peer-reviewed paper (found) in which an LLM writes Coyote tests or Shuttle/Loom harnesses and a controlled scheduler then finds bugs; the published evidence for the "LLM writes the model, explorer explores" pattern is (a) the P-language repo's own agentic invariant-mining/spec-inference toolkit (PChecker as sound oracle; 82 candidates -> 50 verified invariants, 0 confirmed bugs on 4 tutorial benchmarks), (b) Eywa (LLM builds protocol model for model-based testing; 33 bugs, 16 new, in DNS/BGP/SMTP), (c) SyncPetri (Petri-net-guided LLM generation of Loom-compatible harnesses for Rust), and (d) a rapidly growing body of open-source commits where Claude/Codex co-author Coyote, Shuttle, Loom, Concuerror and Hypothesis-stateful tests. In that grassroots corpus, Coyote reproducing real races in Claude-written tests is documented at least once; most LLM-written Loom/Coyote models report "no bug found" and are validated by mutation instead.

### Inferences
- The strongest "LLM writes model, checker explores" evidence is coming from tool maintainers themselves (P's maintainer, Hypothesis maintainers, XState) rather than from independent SE papers; the P PRs are the only case with an explicit vacuity/spuriousness ledger (0 real bugs vs 15 avoided false reports), which suggests the main engineering problem is adjudication, not generation.
- In the grassroots corpus, LLM-written Loom/Coyote models mostly report "no bug found", and authors increasingly validate them by mutation ("still catch their intended bugs when code is intentionally broken") — mirroring Antithesis's mutation-testing skill (KQ2). Vacuity, over-wide models (Loom nightly timeouts) and harness misuse (unrewritten Coyote assemblies, parallel TestingEngines) are the recurring failure modes.
- Where real bugs are documented (Hawsey, Hedgehog NAT race), the LLM wrote both the fix and the test, so the explorer acted as a reproduction/regression oracle rather than a discovery engine.

### Gaps
- No peer-reviewed study quantifies bugs found by LLM-generated Coyote tests or Shuttle/Loom harnesses on real codebases; SyncPetri's and CONCUR's numeric results were not retrievable (arXiv blocked).
- No public evaluation of PeasyAI or of P PR #977 on the FD/2PC benchmarks yet ("awaiting live acceptance testing").
- No Jepsen/Elle report involving LLM-generated workloads or histories was found; search returned nothing relevant.
- FoundationDB simulation, Turmoil and madsim: no LLM-driven work found in search; Turso's simulator PRs could not be checked for agent co-authorship within budget.

## KQ2. Antithesis 2025–2026: agent skills, "autonomous testing", MCP, published results, and the "agents need a deterministic environment" argument

### Takeaway
Antithesis moved in April 2026 to position itself as the verification loop for coding agents (press release "Antithesis Teaches AIs To Correct Their Own Output"), and in 2026 published an Apache-2.0 skills pack for Claude Code/Codex in which the agent writes the property catalog, Docker harness, workload and assertions while the Antithesis engine does the search and fault injection; the pack's distinctive quality controls are mutation testing of properties, "reach claims" checked via fired `Sometimes` assertions, and an input-randomness review. Public numbers on bugs found by agent-written workloads were not found; all claims are vendor self-reports.

### Cited Findings
- Press release 2026-04-23: Antithesis "demonstrated a way for AI coding agents to correct their own code"; "the suite of tools enables AI agents to use Antithesis without human intervention, and when the agent cannot fix an error, Antithesis alerts human developers"; CEO Will Wilson: "Today we're taking a giant step towards solving the verification gap... Our universal property-based testing and deterministic simulation technology can solve this problem"; framing: AI "shifted the bottleneck in software development from writing code to verifying it" (snippet; vendor self-report) — [GlobeNewswire 2026-04-23](https://www.globenewswire.com/news-release/2026/04/23/3280089/0/en/Antithesis-Teaches-AIs-To-Correct-Their-Own-Output.html)
- Antithesis product page claims its "causality analysis provides high enough precision to serve as an automated quality gate in agentic coding loops" and that "AI coding agents are good at creating broad harnesses, but they can also create plausible tests that miss the real invariant" (snippet; vendor self-report) — [antithesis.com/product](https://antithesis.com/product/)
- Blog "Antithesis skills for agents" (2026): a trio of skills "can generally one-shot a system to the end of setup, provide you with a set of basic but valuable test properties, and a similarly basic but valuable workload"; `antithesis-research` analyzes the codebase, `antithesis-debug` drives the multiverse debugger, `antithesis-query-logs` searches "across all timelines in an Antithesis test run" (snippet; vendor self-report) — [antithesis.com/blog/2026/agent_skills](https://antithesis.com/blog/2026/agent_skills/)
- antithesishq/antithesis-skills (Apache-2.0; `npx skills add antithesishq/antithesis-skills`): 14 skills — documentation, research, setup, setup-k8s (in development), workload, feature-workload, triage, debug, query-logs, launch, mutation-testing, review-inputs, agent-browser, skills-feedback; "Tested with Claude Code and OpenAI Codex. - Division of labour (workload skill): "Agents own the workload and assertions; the engine owns search and fault injection." Assertion vocabulary: `Always`/`AlwaysOrUnreachable` for safety, `Sometimes(cond)` "for liveness or non-trivial semantic states that should occur at least once", `Reachable`/`Unreachable`; rule: "Assert the precondition, not the violation... unfired ones are evidence the workload isn't reaching its targets"; anti-vacuity rule: "No reach claim is the negation of an Always or AlwaysOrUnreachable at the same site" — [antithesis-workload SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-workload/SKILL.md)
- Mutation-testing skill: one realistic mutant per property, applied only in an ephemeral fork; survivors are classified as Bad Mutant / Bad Oracle ("A mutant that exposes a bad oracle is a success, not a detour") / Workload Gap (`example_count` 0 on baseline triggers longer re-runs) / Unfalsifiable Property (routed back to research for withdrawal); `Sometimes` assertions are deliberately excluded from mutation because "a Sometimes fails only when its condition is false in every timeline, so a subtle, prerequisite-gated mutant leaves it green"; coverage-instrumentation signals ("Software was instrumented", "Symbols were uploaded") gate verdicts, and for Python "the fuzzer has no coverage feedback to steer toward a divergence, so prefer a longer re-run to a bad oracle diagnosis" — [antithesis-mutation-testing SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Review-inputs skill: reviews workload input generation for state-space reach; principle "randomize the policy per run, not just the choices under a fixed policy"; high-signal finding = "clear structural limitation that prevents it from reaching entire regions of state space" — [antithesis-review-inputs SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-review-inputs/SKILL.md)
- Triage skill: agent reads passed/failed property counts, the two instrumentation properties, "the first failing example" with its "moment" in the timeline, and downloaded logs ("the property status and assertion text alone are not sufficient"); next-step routing: all pass -> mutation testing or workload enhancement; unclear cause -> multiverse debugger; "Treat these as suggestions for the user, not actions to take automatically" — [antithesis-triage SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-triage/SKILL.md)
- Feature-workload skill defines a "self-driving workload" as "a single program that drives the SUT, checks invariants, and runs without external orchestration" with dual-mode assertions (SDK when `ANTITHESIS_OUTPUT_DIR` set, local checks otherwise) and "TDD-style stubs for unbuilt parts. Assertions go green as code lands"; success requires that "the workload has run in Antithesis and findings have been verified" — [antithesis-feature-workload SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-feature-workload/SKILL.md)
- Research skill derives properties from docs, incidents/bug reports and code inspection; "Prefer specific, checkable guarantees over vague goals like 'test failover'"; each property gets an explicit assertion type with justification and an evidence trail — [antithesis-research SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-research/SKILL.md)

- GitHub code search for "mcp" across the antithesishq org returns only hits inside a Materialize proof-of-concept fork (Materialize's own MCP server docs), i.e. no public Antithesis MCP server repository was found — [antithesishq org](https://github.com/antithesishq)

### Inferences
- Antithesis's design encodes a specific theory of agent failure: agents write plausible-but-vacuous properties, so the loop needs (1) runtime evidence that `Sometimes`/reach claims fired, (2) mutation kills, and (3) randomness review — i.e., the engine supplies ground truth the agent cannot get by reading code. The skills documents imply rather than state this argument; the explicit "why agents can't test by reading code" essay was presumably on antithesis.com pages that could not be fetched.
- The "autonomous" offering appears to be delivered mainly through agent skills and the existing web/API surface, not an MCP server (none found publicly).

### Gaps
- No published numbers from Antithesis on bugs found by agent-written workloads, nor customer case studies naming agent-driven runs; everything is vendor framing.
- The antithesis.com blog post text, docs, and any "agents can't test by reading code" essay were not readable (egress blocked); details rest on snippets.
- Whether Antithesis exposes MCP tooling (vs. skills + browser helper) is unconfirmed.

## KQ3. TigerBeetle protocol-aware DST (2026), "sometimes assertions" as coverage, and Oxide RFD 576 on LLM-generated tests

### Takeaway
TigerBeetle's August 2026 post describes a protocol-aware simulator that asserts consensus/storage invariants per replica inside the VOPR (going beyond Jepsen-style black-box checks), with no LLM angle found; "sometimes assertions" as a coverage metric appears in this corpus only as Antithesis's assertion type and its treatment in the mutation-testing skill. Oxide's RFD 576 (Bryan Cantrill) warns that even test-writing, a seemingly natural LLM task, needs care because "it's easy for LLMs to spiral into nonsense on even simple tasks"; nothing was found in RFD 576 specifically contrasting LLM-written tests with TLA+ or proptest.

### Cited Findings
- TigerBeetle blog "Protocol-Aware Deterministic Simulation Testing" (2026-08-20): the simulator "is protocol-aware, which enables testing safety and liveness invariants not just at the database level, but also at the level of each individual replica"; because of "logical determinism and physical determinism" it runs "the real consensus and storage engine code in a single process with simulated time, then assert[s] invariants at the level of each replica's write-ahead log and LSM tree"; for consensus safety it "asserts that a committed request's checksum matches across every replica each time it commits, going deeper than the production check that only fires on periodic commit messages"; explicitly positioned "beyond traditional black-box testing approaches like Jepsen" (snippet) — [tigerbeetle.com 2026-08-20](https://tigerbeetle.com/blog/2026-08-20-protocol-aware-dst/)
- Same material presented by Chaitanya Bhandari (TigerBeetle) at BugBash 2026 (snippet) — [Antithesis BugBash talk page](https://antithesis.com/bugbash/talks/protocol-aware-deterministic-simulation-testing/); [YouTube](https://www.youtube.com/watch?v=F78FeuSIX-A)
- TigerBeetle architecture docs: "Both client and server code are full of assertions which double-check that intended invariants have been preserved"; the control plane may spend "O(N) time to verify O(1) operation" (snippet) — [tigerbeetle docs/ARCHITECTURE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/ARCHITECTURE.md)
- TigerBeetle's docs/internals/testing.md documents only the VOPR's 16-column output format (replica roles, checkpoint/commit ops, WAL/journal, grid, pipeline) and contains no AI/LLM mention — [tigerbeetle docs/internals/testing.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/testing.md)
- GitHub PR search in tigerbeetle/tigerbeetle for VOPR PRs mentioning LLM/Claude/Copilot/AI-generated returned only ordinary VOPR work (e.g. "vopr: fix isolating one replica in uniform_partition", 2026-09-23), i.e. no evidence of LLM-written VOPR tests — [tigerbeetle PR 3938](https://github.com/tigerbeetle/tigerbeetle/pull/3938)
- Jepsen's independent TigerBeetle analysis (0.16.11) noted "several crashes were due to overly cautious assertions" (snippet) — [jepsen.io/analyses/tigerbeetle-0.16.11](https://jepsen.io/analyses/tigerbeetle-0.16.11)
- Third-party agent skill "tigerbeetle-deterministic-simulation" exists on a skills marketplace, teaching agents TigerBeetle-style DST (page not readable; existence only) — [lobehub skill listing](https://lobehub.com/skills/copyleftdev-sk1llz-deterministic-simulation)
- Oxide RFD 576 "Using LLMs at Oxide" (Bryan Cantrill): grounds LLM use in Oxide's values and evaluates LLMs as readers, researchers, editors, writers, code reviewers, debuggers, programmers; "Human judgement remains firmly in the loop: even if an LLM is generating an artifact that will be used, their output is the responsibility of the human using them"; "Even with something that seems natural for LLM contribution (e.g., writing tests), one should still be careful: it's easy for LLMs to spiral into nonsense on even simple tasks"; requires engineers to self-review LLM-generated code before peer review; later extended to require public Oxide writing be "reported by Pangram as human-authored" (snippets) — [rfd.shared.oxide.computer/rfd/0576](https://rfd.shared.oxide.computer/rfd/0576); [HN discussion](https://news.ycombinator.com/item?id=46178347); [Cantrill, "The revolt of the reader", 2026-09-05](https://bcantrill.dtrace.org/2026/09/05/the-revolt-of-the-reader/)

### Inferences
- "Sometimes assertion" coverage is an Antithesis-vocabulary concept; TigerBeetle's coverage story (as far as retrievable) is dense runtime assertions plus per-replica invariants, not fired-`Sometimes` accounting. The two converge on the same idea: the signal that a scenario was *reached* is as important as the absence of violations.

## KQ4. LLM-generated TLA+/Alloy/P specs; spec-to-test pipelines; NL-to-TLA+ correctness; trace validation and whether LLMs can write the harness

### Takeaway
Measured NL-to-TLA+ generation remains poor (up to 26.6% syntactic, 8.6% semantic correctness across 30 LLMs), and practitioners report LLMs are good at syntax fixing and trace summarizing but "very poor at generating meaningful properties from scratch". Nevertheless, by Sep 2026 agent-co-authored TLA+ trace-validation harnesses are appearing in open-source repos (Claude Opus 5.5 co-authored a 5-spec TLA+ suite with 56 recorded Go traces, 10 mutations and 7 validated findings in invowk; Copilot co-reviewed a TLC-trace-replay harness for a Rust BPM engine), showing the trace-validation harness is within reach of agents when a human defines the refinement mapping and reviews it.

### Cited Findings
- "Can LLMs Write Correct TLA+ Specifications? Evaluating Natural-Language-to-TLA+ Generation" (arXiv 2606.05792, 2026): 30 LLMs across 8 families on 205 TLA+ specs; 25 open-weight models x 4 prompting strategies (2,600 runs) + 5 proprietary models few-shot (130 runs); "up to 26.6% syntactic correctness but only 8.6% semantic correctness, with successes exclusive to progressive prompting"; five recurring hallucination categories "all traceable to specific training data biases"; conclusion: "Current LLMs do not generate reliable TLA+ specifications without expert oversight" (snippet) — [arXiv 2606.05792](https://arxiv.org/abs/2606.05792)
- TLA-Prover (arXiv 2606.06133, 2026): 20B-parameter model fine-tuned via preference-optimized LoRA for TLA+ specification synthesis (snippet; numbers not retrievable) — [arXiv 2606.06133](https://arxiv.org/abs/2606.06133v1)
- SysMoBench "Evaluating AI on Formally Modeling Complex Real-World Systems" (arXiv 2509.23130, 2025) — benchmark of LLM formal modeling of real systems (snippet; task/evaluation details and scores not retrievable) — [arXiv 2509.23130](https://arxiv.org/pdf/2509.23130)
- "Can Large Language Models Model Programs Formally?" (arXiv 2604.01851, 2026) (title only) — [arXiv 2604.01851](https://arxiv.org/pdf/2604.01851)
- "Synthesizing Inductive Invariants for Distributed Protocols via IC3 and Large Language Models" (arXiv 2605.24619, 2026) (title only) — [arXiv 2605.24619](https://arxiv.org/pdf/2605.24619)
- Practitioner assessment attributed to Hillel Wayne (July 2026): LLMs are "excellent at fixing syntax errors in specs and summarizing error traces, good at boilerplate changes, but very poor at generating meaningful properties from scratch for a spec" (snippet) — [hillelwayne.com formal-methods tag](https://www.hillelwayne.com/tags/formal-methods/)
- Murat Demirbas (MongoDB): "In the age of LLMs, the syntax of TLA+ is no longer the bottleneck... the real challenge is the intrinsic complexity of modeling judgment: knowing where to start, what to ignore, and how to choose the right abstractions" (snippet, "TLA+ Mental Models", Mar 2026) — [muratbuffalo TLA+ Mental Models](https://muratbuffalo.blogspot.com/2026/03/tla-mental-models.html); related [AWS outage DNS race TLA+ model, Nov 2025](https://muratbuffalo.blogspot.com/2025/11/tla-modeling-of-aws-outage-dns-race.html)
- Trace validation background: MongoDB "use[s] the model-checker to check that state sequences are permitted by TLA+ specs to ensure their C++ code behaves in a way that conforms to the spec" and can "generate test cases from TLA+ traces that exercise the real WiredTiger code" (snippet; no LLM mention) — [MongoDB conformance checking blog](https://www.mongodb.com/company/blog/engineering/conformance-checking-at-mongodb-testing-our-code-matches-our-tla-specs); [Modular verification of MongoDB transactions](http://muratbuffalo.blogspot.com/2025/05/modular-verification-of-mongodb.html)
- CCF (Microsoft): "collects implementation traces before validating them against its high-level consensus TLA+ specification"; consensus unit tests ~1.6 kLoC, e2e tests >2 kLoC Python (snippet) — [Smart Casual Verification of CCF, arXiv 2406.17455](https://arxiv.org/pdf/2406.17455); general method: [Validating Traces of Distributed Programs Against TLA+ Specifications, arXiv 2404.16075](https://arxiv.org/pdf/2404.16075)
- Agent-co-authored trace validation, case 1: invowk PR #144 (merged; commits credit "Claude Opus 5.5 (1M context)" as co-author): five TLA+ specs (server lifecycle, lock integrity, atomic write under power loss, host callback token, watch/debounce with liveness); records 56 execution traces from real Go code via `INVOWK_FORMAL_TRACE_DIR`, validates them against the specs "to ensure no observable states are skipped", applies 10 targeted mutations "to expose specification weaknesses"; CI workflow runs model checking and trace validation in parallel (~7 s each); seven findings F1–F7 each with counterexample trace and validated fix (e.g. "Stop during Start leaves server context uncancelled", "Power loss leaves empty lock file without fsync", "Session outlives token execution") — [invowk/invowk PR 144](https://github.com/invowk/invowk/pull/144)
- Case 2: nano-bpm PR #1254 (merged 2026-09-26, Josh Wulf; five commits "Co-authored-by: Copilot"): `gen-traces.sh` runs TLC with a `~completed` witness invariant to emit shortest completing behaviours as JSON; `engine-core/tests/trace_validation.rs` replays them through the real Rust engine and asserts the "observable milestone multiset" matches exactly. Copilot review flagged a soundness hole ("flows lack per-flow identity in observable milestones, allowing an engine to take one duplicate flow twice without detection") and a silent partial-replay bug — [nanobpm/nano-bpm PR 1254](https://github.com/nanobpm/nano-bpm/pull/1254)
- Case 3: LedgerLens PR #1257 (2026-09-26): bounded TLC behaviours translated into Soroban contract invocations with a refinement mapping comparing abstract state after each step; "a deliberate mutation regression proving that the harness detects implementation/model divergence" at step 1; no explicit LLM co-authorship stated — [Ledger-Lenz/Ledgerlens-contract PR 1257](https://github.com/Ledger-Lenz/Ledgerlens-contract/pull/1257)
- "Ranking Formal Specifications using LLMs" (Mike He, Princeton, LMPL 2025) (title only) — [PDF](https://www.cs.princeton.edu/~dh7120/assets/papers/LMPL2025.pdf)
- "Evaluating LLM-Generated Finite State Machines: The Impact of Prompting Techniques" (Springer 2026) reports iterative-refinement prompts "achieve near-perfect accuracy" on FSMs from textual specs (snippet) — [Springer chapter](https://link.springer.com/chapter/10.1007/978-3-032-28274-3_22)

### Inferences
- The benchmark literature (8.6% semantic correctness) and the field reports (agents shipping multi-spec trace-validation suites) are reconcilable: the latter are human-steered, iterative, and checked by TLC and mutation, exactly the "expert oversight" the paper calls for.
- Mutation of the implementation to confirm the harness detects divergence has become the de facto quality check for agent-written trace validation (all three cases above), paralleling Antithesis's mutation skill.

### Gaps
- No controlled study of LLMs writing trace-validation harnesses (refinement mappings, trace loggers) was found; evidence is anecdotal PRs.
- No evidence found for LLM-generated Alloy specs feeding tests, nor for spec-to-test derivation at MongoDB/Confluent/CCF involving LLMs.
- SysMoBench and TLA-Prover numbers unavailable (arXiv blocked).

## KQ5. Concurrency-bug detection: LLM-only vs tools (ThreadSanitizer, Coyote, Shuttle); quantified LLM recall; hybrids

### Takeaway
On DataRaceBench-derived evaluations, traditional dynamic/static race detectors beat LLMs on F1, while a 2025 hybrid ("vibe translation": LLM translates C/C++ OpenMP programs to Go, then the Go race detector runs) is reported to outperform Clang/ThreadSanitizer+Archer on DataRaceBench. Benchmarks now use model checkers (Java PathFinder) as oracles for LLM-generated concurrent code (CONCUR), and comprehension studies find LLMs struggle to identify data races and deadlocks reliably. No study was found quantifying LLM recall against Coyote or Shuttle specifically.

### Cited Findings
- DataRaceBench: 208 C and 168 Fortran OpenMP programs; DRB-ML dataset derived from it "to support evaluation of large language models for data race analysis"; "traditional tools achieve superior performance in terms of the F1 score when compared to LLMs" (snippet) — [DataRaceBench, SC'17](https://dl.acm.org/doi/pdf/10.1145/3126908.3126958); [Data Race Detection Using LLMs (2023)](https://www.researchgate.net/publication/373141982_Data_Race_Detection_Using_Large_Language_Models)
- Tool recall baseline on DataRaceBench: ThreadSanitizer recall 0.613 vs OpenRace 1.000; OpenMP-aware tools (Archer, Intel Inspector) have higher precision than Helgrind/TSan (snippet) — [LLNL regression study](https://www.osti.gov/servlets/purl/1574623)
- "Data Race Detection through Vibe Translation" (ACM, 2025): "Translate-then-check for DataRaceBench C/C++ programs translated to Go outperforms the current version of Clang/ThreadSanitizer with Archer" (snippet; precise P/R not retrievable) — [ACM DL 10.1145/3731599.3767363](https://dl.acm.org/doi/full/10.1145/3731599.3767363)
- "Assessing Large Language Models in Comprehending and Verifying Concurrent Programs" (arXiv 2501.14326, 2025): examines "whether LLMs can correctly identify concurrency-related issues such as data races, deadlocks, and race conditions" (snippet; accuracy figures not retrievable) — [arXiv 2501.14326](https://arxiv.org/pdf/2501.14326)
- CONCUR (arXiv 2603.03683, 2026): LLM-generated Java concurrent code judged by JPF exhaustive interleaving exploration with PreciseRaceDetector and DeadlockAnalyzer listeners (snippet) — [arXiv 2603.03683](https://arxiv.org/abs/2603.03683)
- "An End-to-End Approach for Fixing Concurrency Bugs via SHB-Based Context Extractor" (arXiv 2604.05753, 2026): LLM repair guided by schedulable-happens-before context; dataset of 33 non-deadlock concurrency bugs (atomicity violations, data races) and 10 deadlocks (snippet) — [arXiv 2604.05753](https://arxiv.org/html/2604.05753)
- "Black-Box Bug-Amplification for Multithreaded Software" (arXiv 2507.21318, 2025) (title only; dynamic amplification, not LLM) — [arXiv 2507.21318](https://arxiv.org/pdf/2507.21318)
- Field anecdote: Hedgehog's commits show PCT + random Shuttle schedulers run in CI with LLM assistance (KQ1), and Hawsey shows Coyote reproducing races in LLM-written tests (KQ1) — [githedgehog/dataplane commit aa3c455](https://github.com/githedgehog/dataplane/commit/aa3c455ccad2d3df069910c73eccd4bd495b0c8d)

### Inferences
- The emerging winning pattern is hybrid: the LLM lifts code into a form a sound/complete-ish dynamic checker can exercise (Go race detector, JPF, Coyote, PChecker), rather than the LLM judging interleavings itself.

### Gaps
- No paper found evaluating LLM recall on GoBench or JaConTeBe, nor comparing LLM-only detection to Coyote/Shuttle on the same bug set.
- Exact precision/recall figures for the vibe-translation and comprehension studies were not retrievable (ACM/arXiv blocked).

## KQ7. LLM agents inside deterministic simulators ("agentic DST"), agent-in-the-loop fault injection, LLM-generated chaos experiments

### Takeaway
"Agentic DST" in the strict sense — an LLM agent operating inside a deterministic simulator and steering fault injection — is realized commercially only by Antithesis's skills loop (agent writes workload/properties, reads fired assertions and timelines, injects mutants; KQ2). The academic literature in 2025–2026 instead covers (a) LLMs generating chaos-engineering experiments for Kubernetes-style systems and (b) chaos engineering *of* LLM agents (fault injection into LLM API calls), which is the inverse problem.

### Cited Findings
- "LLM-Powered Fully Automated Chaos Engineering" (arXiv 2511.07865, Nov 2025) — LLM generates chaos experiments end to end (snippet; title and existence only; execution engine and results not retrievable) — [arXiv 2511.07865](https://www.arxiv.org/pdf/2511.07865)
- AgentChaos (arXiv 2608.06790, 2026): "chaos engineering framework for controlled, runtime, non-intrusive LLM API fault injection" at the shared HTTP layer; fault taxonomy "covering crash, omission, and value faults on both content and tool call fields, yielding 65 fault configurations" (snippet) — [arXiv 2608.06790](https://arxiv.org/html/2608.06790)
- ReliabilityBench (arXiv 2601.06112, 2026): "first systematic application of chaos engineering principles to LLM agent evaluation", configurable fault profiles (transient timeouts, rate limits), "Reliability Surface" of consistency/robustness/fault tolerance (snippet) — [arXiv 2601.06112](https://arxiv.org/html/2601.06112v1)
- "Observability and Fault Injection for LLM-Based Multi-Agent Systems in Software Engineering" (arXiv 2608.24271, 2026) and "When Agentic Executions Fail: Detecting and Localizing Runtime Faults from Telemetry" (arXiv 2608.14680) (titles only) — [arXiv 2608.24271](https://arxiv.org/pdf/2608.24271); [arXiv 2608.14680](https://arxiv.org/pdf/2608.14680)
