## KQ1. LLM-only vulnerability/bug detection: precision, recall, reasoning failures (2024 baselines) and 2025–2026 frontier/agent updates

### Takeaway
Through 2024, controlled benchmarks consistently showed that LLMs reading code alone are barely better than chance at distinguishing vulnerable from patched functions (balanced accuracy ≈0.50–0.55, PrimeVul pairwise accuracy ≈8–11%), with unstable, unfaithful reasoning. In 2025–2026, frontier models and agent scaffolds (Big Sleep, Aardvark, Claude Opus 4.6/Mythos, "Carlini loop") produced large numbers of real, confirmed zero-days, but almost every credible production result includes an execution-based verification step (sandbox, crash PoC, debugger, task verifier), and uncontrolled "raw" output is now flooding maintainers (curl's HackerOne validity rate fell below 5%; Linux kernel security list went from 2–3 reports/week to 5–10/day). Public, independent precision numbers for frontier LLM-only scanning remain scarce; the one vendor-run measurement found ~28% recall at >40% false-positive rate for Claude Opus 4.6 on 435 CVEs.

### Cited Findings

**2024 academic baselines (peer-reviewed)**
- PrimeVul (Ding et al., ICSE 2025): ~7k vulnerable + ~229k benign C/C++ functions, 140+ CWEs; labels claimed "up to 3× more accurate than existing automatic labeling approaches"; introduces the VD-Score ("risks of missing security flaws when not overwhelming developers with false alarms") and *paired* vulnerable/patched evaluation to expose whether a model can distinguish a vulnerability from its fix — [PrimeVul GitHub README](https://github.com/DLVulDet/PrimeVul); [arXiv 2403.18624](https://arxiv.org/abs/2403.18624). Gemini 1.5 was evaluated on PrimeVul by Google (README, 06/14/24).
- On PrimeVul, "LLM-based methods generally demonstrate better results than learning-based methods ... with pairwise accuracy (PairAcc) ranging from 8.28%–10.57%"; a 2026 fine-tuned reasoning model (ReasonVul) is reported at 40.00% PairAcc [via search summary] — [Three Heads Are Better Than One, arXiv 2605.18153](https://arxiv.org/pdf/2605.18153). (Pairwise accuracy = a pair counts as correct only if both the vulnerable function and its patch are classified correctly.)
- SecLLMHolmes (Ullah, Han, Pujar, Pearce, Coskun, Stringhini; IEEE S&P 2024): 8 LLMs × 8 investigative dimensions × 228 code scenarios; LLMs "provide non-deterministic responses, incorrect and unfaithful reasoning, and perform poorly in real-world scenarios." Merely renaming functions/variables or adding library functions flipped answers in 26% (PaLM2) and 17% (GPT-4) of cases; conclusion: "LLMs are not yet ready to be used for automated vulnerability detection." — [arXiv 2312.12575](https://arxiv.org/html/2312.12575v3); [IEEE Xplore](https://ieeexplore.ieee.org/document/10646663/)
- Steenhoek et al., "A Comprehensive Study of the Capabilities of LLMs for Vulnerability Detection" (arXiv 2403.17218): 11 LLMs, zero-shot/n-shot/contrastive-pair/CoT prompting incl. CoT from static analysis and CVE descriptions; "balanced accuracy of all models, ranging from 7B LLMs to GPT-4-turbo, lies between 0.5 and 0.55 ... no clear scaling law"; models "frequently misidentify bug types and fail to distinguish between buggy and fixed versions." [via search summary] — [Lacuna summary](https://lacuna.tiptreesystems.com/work/a-comprehensive-study-of-the-capabilities-of-large-language-models-for/wrk_59c89fc1065b88e18df3c21879e45027); [Steenhoek publications](https://benjijang.com/publications/)
- "Reasoning with LLMs for Zero-Shot Vulnerability Detection" (arXiv 2503.17885): Llama 3.1 highest recall but precision 0.24; Mistral v0.3 precision 0.46 with much lower recall [via search summary] — [arXiv 2503.17885](https://arxiv.org/pdf/2503.17885)
- Further 2025 surveys/evaluations of the same "LLMs reading functions" paradigm (not opened; listed for the writer): "From Large to Mammoth: A Comparative Evaluation of LLMs ..." (NDSS 2025) — [PDF](https://www.ndss-symposium.org/wp-content/uploads/2025-1491-paper.pdf); "Everything You Wanted to Know About LLM-based Vulnerability Detection But Were Afraid to Ask" — [arXiv 2504.13474](https://arxiv.org/pdf/2504.13474); "Guessing As A Service: LLMs Are Not [reliable vulnerability detectors]" (ITASEC survey) — [PDF](https://re.public.polimi.it/retrieve/1a011e87-e965-4637-bcfe-4568b14e5441/_ITASEC__Survey_LLMs_for_Vulnerability_Detection.pdf); "Benchmarking LLMs and LLM-based Agents in Practical Vulnerability Detection for Code Repositories" (ACL 2025) — [PDF](https://aclanthology.org/2025.acl-long.1490.pdf).

**2025–2026 benchmarks with agents / frontier models**
- CyberGym (arXiv 2506.02548): 1,507 real vulnerability instances from 188 projects (OSS-Fuzz/ARVO-derived); task = produce a PoC input that reproduces the vulnerability from a text description + codebase, verified by execution. Best configuration OpenHands + Claude Sonnet 4 reached 17.9% success; "even the top-performing combinations only achieve ∼20%". The runs incidentally discovered 35 zero-days in latest versions and 17 incomplete patches. Leaderboard submissions must report cost. [via search summary + README] — [alphaXiv overview](https://www.alphaxiv.org/overview/2506.02548); [GitHub](https://github.com/sunblaze-ucb/cybergym)
- SastBench (Feiglin & Dar, arXiv 2601.02941): agentic *triage* of SAST findings; 2,737 samples (299 TP real CVEs, 2,438 FP), FP:TP = 8.15:1, 38 languages, 139 CWEs. Best: Gemini 2.5 Pro improved-prompt ReAct MCC 0.148, precision 0.169, recall 0.582, F1 0.262; Claude Sonnet 4.5 recall 0.722 at precision 0.140 (MCC 0.110); weaker LLMs (Llama 4 Maverick) negative MCC (worse than random). Gemini 2.5 Pro *without tools* already matched/exceeded some ReAct agents on recall. [via search summary] — [arXiv 2601.02941](https://arxiv.org/pdf/2601.02941); [Rival Research overview](https://rival.security/posts/sastbench-overview)
- RealVuln (arXiv 2604.13764) **[likely VENDOR-affiliated: benchmark hosted at realvuln.kolega.dev and the top scorer is Kolega.Dev]**: three tiers under F3 (recall weighted 9× precision): Kolega.Dev F3 73.0 (recall 0.809, precision 0.388); best general-purpose LLM Claude Sonnet 4.6 F3 51.7 (recall 0.498, precision 0.785); best rule-based SAST Semgrep F3 17.7. Note the general-purpose LLM had the *highest precision* but half the recall. [via search summary] — [arXiv 2604.13764](https://arxiv.org/html/2604.13764v1); [realvuln.com](https://realvuln.com/)

[via search summary] — [ZeroPath: AI coding assistants are not SAST](https://zeropath.com/blog/ai-coding-assistants-are-not-sast); [ZeroPath benchmark](https://zeropath.com/blog/benchmarking-zeropath)

### Inferences
- Across 2024 function-level benchmarks the signal is remarkably uniform: without execution, LLM classification of vulnerable-vs-fixed is near chance, and performance is brittle to semantics-preserving renames. The 2025–26 jump in real-world findings coincides with (i) much stronger models and (ii) scaffolds that *run code* (sandboxes, debuggers, PoC verifiers, task verifiers), so the field has not produced a clean demonstration that *reading alone* became reliable.
- Where precision is measured independently (SastBench P≈0.14–0.17; ZeroPath's Opus 4.6 run FP>40%; XBOW ~25% non-actionable), LLM-only or weakly-tooled pipelines are low-precision/high-recall; where vendors report "zero false positives" the mechanism is always a deterministic validator.
- The curl/kernel/HackerOne data show the externality of raw reports: validity rates collapsed where reporters lacked execution evidence; HackerOne's "nearly half valid" hackbot figure is far better than curl's <5%, consistent with hackbots that validate before filing.

### Gaps
- Could not open the PrimeVul paper to confirm the headline F1 collapse (commonly quoted as ~68% on BigVul vs ~3% on PrimeVul for a 7B model) or GPT-4/CoT numbers — writer should verify at [arXiv 2403.18624](https://arxiv.org/abs/2403.18624).
- No independent, peer-reviewed precision/recall measurement of Opus 4.6, Mythos, Aardvark or Big Sleep exists in what I found; all are self-reports. Mythos' per-finding cost and false-positive/triage burden were not published in any source found.
- Steenhoek et al. 2025 follow-up (the "reasoning failures" taxonomy) and the NDSS 2025 "From Large to Mammoth" numbers were not retrievable.

## KQ2. Hybrid pipelines with explicit ablations: what does the ablation attribute to the tool vs the LLM?

### Takeaway
Every ablation found attributes the *precision* (and often the recall) to the classical engine, and the *specification/driver authoring* to the LLM: IRIS's gains vanish when LLM-inferred taint specs are replaced with CodeQL's; LLift turns ~1,000 static-analysis candidates into 50%-precision results with no misses; RepoAudit's path-condition validator is what lifts precision to 78–88%; SWT-Bench shows direct prompting reproduces only 3.6% of bugs while execution-filtered patch selection (Agentless) is the cheapest path to top SWE-bench scores; Meta's ACH uses mutation testing as the oracle and gets 73% engineer acceptance; and in AIxCC and OSS-Fuzz-Gen the fuzzer, not the model, produces the verdict.

### Cited Findings
- IRIS (Li, Dutta, Naik et al., ICLR 2025): LLM infers CWE-specific taint sources/sinks for third-party APIs, CodeQL does whole-repo dataflow, LLM then filters alerts. On CWE-Bench-Java (120 manually validated vulns), CodeQL alone detects 27; IRIS with GPT-4 detects 55 (+28) and "improves CodeQL's average false discovery rate by 5% points"; 4 previously unknown vulns. Ablation: replacing either the LLM-inferred source or sink specs with CodeQL's built-in specs yields "significantly fewer vulnerabilities" — the LLM's contribution is spec mining, the engine's is sound propagation. [via search summary] — [arXiv 2405.17238](https://arxiv.org/html/2405.17238v3); [ICLR PDF](https://proceedings.iclr.cc/paper_files/paper/2025/file/582d4e27fa24168f3af1f4582655034b-Paper-Conference.pdf). The public CWE-Bench-Java has since grown to 213 CVEs / 49 CWEs (CWE-22: 60, CWE-79: 38, CWE-94: 23) with 50 CVEs carrying hand-written CodeQL source/sink annotations (fetched) — [iris-sast/iris README](https://github.com/iris-sast/iris)
- LLift (Li, Hao, Zhai, Qian; OOPSLA 2024): post-processes UBITect (Linux-kernel use-before-initialization static analyzer) reports whose symbolic-execution phase times out — "approximately 40% of the potential bugs reported in the static analysis phase failed to be completed due to timeouts or memory limits." On nearly 1,000 candidates LLift reaches "a reasonable precision (50%) and appears to have no missing bug," finding 13 new UBI bugs in the kernel. Key LLM role: post-constraint-guided path-feasibility reasoning. [via search summary] — [OOPSLA PDF](https://www.cs.ucr.edu/~zhiyunq/pub/oopsla24_llift.pdf); [ACM DL](https://dl.acm.org/doi/10.1145/3649828); [arXiv 2308.00245](https://arxiv.org/pdf/2308.00245)
- RepoAudit (Guo et al., ICML 2025): LLM agent does demand-driven, interprocedural data-flow exploration; a *validator* "verif[ies] data-flow facts and check[s] the satisfiability of path conditions" to cut hallucinations. 40 true bugs on 15 benchmark projects at 78.43% precision; 185 new bugs in high-profile projects, 174 confirmed/fixed; average 0.44 h and $2.54 per project with Claude 3.5 Sonnet; precision 88.46% with DeepSeek-R1 / Claude 3.7 Sonnet / o3-mini. [via search summary] — [arXiv 2501.18160](https://arxiv.org/html/2501.18160v1); [ICML poster](https://icml.cc/virtual/2025/poster/45170); [GitHub](https://github.com/PurCL/RepoAudit) (README adds ">100 bugs in open-source projects this quarter" but no metrics).
- Industrial static-analysis FP triage: "Reducing False Positives in Static Bug Detection with LLMs: An Empirical Study in Industry" (arXiv 2601.18844) — exists but could not be opened; listed for follow-up — [arXiv 2601.18844](https://arxiv.org/pdf/2601.18844). Related: "LLM-Driven SAST-Genius: A Hybrid Static Analysis Framework" — [arXiv 2509.15433](https://arxiv.org/pdf/2509.15433).
- SWT-Bench (Mündler, Müller, He, Vechev; NeurIPS 2024): test = fail-to-pass (F→P) on the pre-/post-golden-patch codebase. "Directly prompting an LLM creates bug reproduction tests successfully in only 3.6% of cases on SWT-Bench-Lite" (ZeroShot); agents do far better. Dataset: Lite 276, Verified 433, Full 2,294 instances; gold-patch validation P→P rates 10.86% / 15.01% / 17.65% (fetched) — [GitHub](https://github.com/logic-star-ai/swt-bench); [arXiv 2406.12952](https://arxiv.org/html/2406.12952v3). AssertFlip (2025) tops the leaderboard by first having the LLM write *passing* tests on buggy behavior and then inverting the assertions — "LLMs are better at writing passing tests than ones that crash or fail on purpose" [via search summary] — [arXiv 2507.17542](https://arxiv.org/html/2507.17542)
- Agentless (Xia, Deng, Dunn, Zhang; FSE 2025): three-phase localize → repair → *validate*, where it "generates additional reproduction test[s]" and uses regression + reproduction test outcomes to "re-rank all remaining patches to select one to submit." GPT-4o: 82 fixes (27.3%) on SWE-bench Lite at $0.34 per issue; Claude 3.5 Sonnet: 40.7% Lite / 50.8% Verified (fetched) — [GitHub](https://github.com/OpenAutoCoder/Agentless); [FSE 2025 PDF](https://lingming.cs.illinois.edu/publications/fse2025.pdf). For comparison AutoCodeRover ≈ $1.33/instance and 4.5 min/instance [via search summary] — [SWE-Bench+, arXiv 2410.06992](https://arxiv.org/pdf/2410.06992)
- Meta ACH, "Mutation-Guided LLM-based Test Generation at Meta" (FSE 2025 Industry): LLM generates targeted *mutants* (privacy faults), then tests that kill them — the mutant kill is the oracle, not coverage. Applied to 10,795 Kotlin classes across 7 platforms → 9,095 mutants, 571 privacy-hardening tests; LLM equivalent-mutant detector precision 0.79 / recall 0.47 (0.95 / 0.96 with simple preprocessing); engineers in Messenger/WhatsApp test-a-thons accepted 73% of tests and judged 36% privacy-relevant [via search summary] — [FSE 2025 page](https://conf.researchr.org/details/fse-2025/fse-2025-industry-papers/16/Mutation-Guided-LLM-based-Test-Generation-at-Meta); [Meta Engineering](https://engineering.fb.com/2025/02/05/security/revolutionizing-software-testing-llm-powered-bug-catchers-meta-ach/); open challenges paper "Harden and Catch" — [arXiv 2504.16472](https://arxiv.org/pdf/2504.16472)
- OSS-Fuzz-Gen (Google; fetched README): LLM writes fuzz targets, OSS-Fuzz runs them; "30 new bugs/vulnerabilities found by automatically generated targets" incl. OpenSSL CVE-2024-9143 (OOB read/write), OOB reads in cJSON, libplist, hunspell, sqlite3, gpac (×4), UAF in openbabel, a pending Java RCE and a ReDoS; "These bugs could only have been discovered with newly generated targets. They were not reachable with existing OSS-Fuzz targets." Valid targets with non-zero coverage gain for 160 C/C++ projects; max line-coverage increase 29% over human targets; 1,300+ benchmarks from 297 projects. Top relative gains: phmap +205.75%, onednn +7057% (from 77 lines), casync +903%. — [google/oss-fuzz-gen](https://github.com/google/oss-fuzz-gen); earlier Google post [AI-Powered Fuzzing](https://security.googleblog.com/2023/08/ai-powered-fuzzing-breaking-bug-hunting.html); Nov-2024 update [Leveling up fuzzing](https://security.googleblog.com/2024/11/leveling-up-fuzzing-finding-more.html)
- Harness quality caveat: "Quality-Assured Fuzz Harness Generation via the Four Principles Framework" (QuartetFuzz, arXiv 2605.21824) reports that in studied OSS-Fuzz-Gen benchmarks "between 57% and 65% of crashes initially flagged as bugs were later shown to be spurious — unreachable from documented calling contexts," i.e., LLM-written harnesses violate API preconditions; QuartetFuzz harnesses statistically match human OSS-Fuzz harnesses in coverage (+0.03 pp line, −0.07 pp branch; TOST equivalence within ±2 pp) [via search summary] — [arXiv 2605.21824](https://arxiv.org/html/2605.21824v1)
- Other harness-generation ablations: libErator (FSE 2025) reaches coverage comparable to manual drivers and above prior automated techniques, with component ablation — [PDF](https://nebelwelt.net/files/25FSE2.pdf); deepSURF (Rust) ablates static harness generation vs LLM augmentation vs harness selection — [arXiv 2506.15648](https://arxiv.org/pdf/2506.15648); "Understanding LLM-Based Fuzz Driver Generation" (ISSTA 2024) found LLM drivers "competent ... compared to manually written ones" but with "practical challenges in filtering out ineffective fuzz drivers" — [arXiv 2307.12469](https://arxiv.org/pdf/2307.12469); "Fuzzing with Agents? Generators Are All You Need" (2026) — [arXiv 2604.01442](https://arxiv.org/pdf/2604.01442); Branch Flipper (coverage-grounded LLM to unblock fuzz blockers) — [PDF](https://revsic.github.io/pdf/Branch_flipper.pdf); ELFuzz — [arXiv 2506.10323](https://arxiv.org/html/2506.10323)
- DARPA AIxCC finals (Aug 2025): CRSs found 54 of 63 synthetic vulnerabilities (86%, up from 37% at semifinals), patched 43; also found 18 real, unplanted vulns and patched 11; average cost per task $152 with ~45 min to remediation. Trail of Bits' Buttercup (2nd place) is explicitly fuzzing-first: "an AI/ML-assisted fuzzing campaign (built on oss-fuzz) ... When vulnerabilities are found, Buttercup analyzes them and uses a multi-agent AI-driven patcher" with an LLM seed generator (fetched README) — [Buttercup](https://github.com/trailofbits/buttercup); [DARPA results](https://www.darpa.mil/news/2025/aixcc-results); [Trail of Bits blog](https://blog.trailofbits.com/2025/08/09/trail-of-bits-buttercup-wins-2nd-place-in-aixcc-challenge/); SoK of AIxCC designs — [arXiv 2602.07666](https://arxiv.org/html/2602.07666v2)

### Inferences
- The consistent division of labor in the ablations: LLM = specification/harness/seed/path-reasoning author; engine = exhaustive search and ground-truth verdict. IRIS is the cleanest attribution (swap specs → detections drop; keep CodeQL → precision holds). RepoAudit's and XBOW's "validator" components are the same idea applied to LLM-only exploration.
- Execution feedback is cheap relative to model calls: Agentless's $0.34/issue includes test generation + re-ranking and beat agent frameworks costing 4× more.
- The harness route has its own false-positive channel (API-misuse crashes, 57–65% spurious in QuartetFuzz's analysis of OSS-Fuzz-Gen), so "fuzzer verdict" ≠ "true bug" unless harness preconditions are checked — a cost that should be budgeted when comparing to LLM-only false positives.

### Gaps
- No paper found that runs the *same* frontier model (e.g., Opus 4.6/GPT-5) head-to-head as (a) raw reviewer vs (b) harness author on the same targets with matched budget; the ablations are within hybrid systems, not across paradigms.
- IRIS per-LLM detection counts beyond GPT-4, and the contextual-filter ablation numbers, were not retrievable.

## KQ4. Meta-research on measuring test/harness quality: coverage vs mutation score, test smells, tests that pass on buggy code, oracle validity, contamination

### Takeaway
The literature converges on execution-based, bug-sensitive metrics: TestGenEval shows LLM tests reach 35% coverage but only ~19% mutation score; SWT-Bench and the "misguidance effect" study show tests are often written *to the buggy behavior*; roughly half of Copilot-generated tests carry test smells; benchmark saturation is documented (XBOW's suite at ~100%); and 57–65% of LLM-harness crashes in OSS-Fuzz-Gen were spurious, so even fuzzer verdicts need precondition checking.

### Cited Findings
- TestGenEval (Jain et al., ICLR 2025): 1,210 code/test-file pairs from 11 repos (code files avg 782 LOC, tests avg 677 LOC, median human coverage 60.4%); metrics: pass@1, coverage, mutation score and "mutation score improvement compared to the gold (human written) tests" (fetched README). Best model GPT-4o: 35.2% coverage, 18.8% mutation score; Llama 3.1 405B: 35.0% / 16.4% [via search summary] — [GitHub](https://github.com/facebookresearch/testgeneval); [arXiv 2410.00752](https://arxiv.org/html/2410.00752v1); [site](https://testgeneval.github.io/)
- SWT-Bench (NeurIPS 2024): defines F→P reproduction and coverage-of-golden-patch (Δall) as metrics; zero-shot LLM F→P 3.6% on Lite — [GitHub](https://github.com/logic-star-ai/swt-bench); [arXiv 2406.12952](https://arxiv.org/html/2406.12952v3)
- "Evaluating and Mitigating the Misguidance Effect of Buggy Code in LLM-Generated Unit Tests" (arXiv 2607.22883): on Defects4J v3.0 (854 defects, 17 projects) quantifies tests that "pass on the buggy version but fail on its bug-free counterpart"; surprising finding that among tests passing on buggy code, ">90% on average are, in fact, True Negatives" (i.e., they simply don't exercise the bug) [via search summary] — [arXiv 2607.22883](https://arxiv.org/html/2607.22883v1)
- "Do Coverage and Mutation Scores of LLM-Generated Test Suites Correlate with Their Effectiveness? (Replicability Study)" (arXiv 2607.22880) — directly on-topic, not openable in sandbox — [arXiv 2607.22880](https://arxiv.org/html/2607.22880v1)
- Test oracle studies on real bugs: TOGLL — [arXiv 2405.03786](https://arxiv.org/pdf/2405.03786); Doc2OracLL — [arXiv 2412.09360](https://arxiv.org/pdf/2412.09360); "From Business Requirements to Test Assertions: Evaluating LLM-Generated Oracles on Real Bugs" (Defects4J) — [arXiv 2607.10277](https://arxiv.org/abs/2607.10277)
- Test smells: 47.4% of GitHub Copilot-generated Python tests had at least one smell (Assertion Roulette, Magic Number Test, conditional logic) [via search summary] — [SBES paper](https://sol.sbc.org.br/index.php/sbes/article/view/30398); "On the Diffusion of Test Smells in LLM-Generated Unit Tests": 20,505 class-level suites from GPT-3.5, GPT-4, Mistral 7B, Mixtral 8x7B, consistently showing Assertion Roulette and Magic Number smells — [arXiv 2410.10628](https://arxiv.org/abs/2410.10628); "Quality Assessment of Python Tests Generated by LLMs" — [arXiv 2506.14297](https://arxiv.org/pdf/2506.14297)
- Mutation-guided generation as the fix: Meta ACH (above) and "On Mutation-Guided Unit Test Generation" — [arXiv 2506.02954](https://arxiv.org/html/2506.02954v2); open-source reproduction (testforge) reports an offline example where added ungated tests raised coverage 87.2%→91.5% with mutation score unchanged at 85.5% — explicit coverage/detection decoupling (fetched README) — [GitHub](https://github.com/Luz7818/testforge)
- Harness-level validity: 57–65% of OSS-Fuzz-Gen crashes spurious (precondition-violating harnesses) [via search summary] — [QuartetFuzz, arXiv 2605.21824](https://arxiv.org/html/2605.21824v1); "An Empirical Study of Fuzz Harness Degradation" (how human harnesses rot over time; not openable) — [arXiv 2505.06177](https://pith.science/paper/2505.06177)
- Benchmark contamination/saturation: XBOW's 104-benchmark suite "saturated ... trained into the models ... approximately 100%" by mid-2026 (fetched) — [GitHub](https://github.com/xbow-engineering/validation-benchmarks); SWE-Bench+ documents solution leakage and weak tests in SWE-bench — [arXiv 2410.06992](https://arxiv.org/pdf/2410.06992); PrimeVul's motivation was label noise in BigVul/Devign (labels "up to 3× more accurate") — [GitHub](https://github.com/DLVulDet/PrimeVul); "How well do LLM-based test generation techniques perform with newer LLM versions?" (replication drift) — [arXiv 2601.09695](https://arxiv.org/pdf/2601.09695)
- Model-version drift and prompt sensitivity as threats: SecLLMHolmes 17–26% flips under renaming (KQ1); SastBench shows prompt engineering alone moved Gemini precision and Claude recall materially [via search summary] — [arXiv 2601.02941](https://arxiv.org/pdf/2601.02941)

### Inferences
- Coverage is a weak proxy for LLM tests specifically because models write assertions that encode current behavior; mutation score (TestGenEval, ACH), F→P on known bugs (SWT-Bench), and "misguidance" rates are the metrics that discriminate. Any evaluation of harness-vs-review pipelines should use real-bug detection or mutant kills, never coverage alone.
- Threats to validity recurring across the corpus: label noise (PrimeVul), contamination (XBOW suite, SWE-bench), brittleness to renaming, non-determinism, version drift, and spurious crashes from precondition-violating harnesses.

### Gaps
- TDD-Bench Verified results and the 2607.22880 correlation numbers were not retrievable; Defects4J contamination estimates for frontier models not found.

## KQ6. "LLM as orchestrator of classical tools" framing: agent frameworks that call fuzzers/analyzers/verifiers

### Takeaway
By 2025–2026 nearly every system that reports confirmed real-world bugs is built as an LLM driving executable tooling: Big Sleep (code browser + Python input generation + debugger), Buttercup (OSS-Fuzz + LLM seeds/patcher), IRIS (LLM specs → CodeQL), RepoAudit (agent + SMT-style path validator), XBOW (agents + deterministic validators), Aardvark (sandbox exploit validation), Anthropic/Mozilla (task verifiers, VM validation), and OSS-Fuzz-Gen (LLM harness → fuzzer). Peer-reviewed work explicitly theorizing this ("Agentic Fuzzing", "Fuzzing with Agents? Generators Are All You Need", OpenAnt, vEcho) appeared in 2026.

### Cited Findings
- Big Sleep agent tools: navigate codebase, "run Python scripts in a sandboxed environment to generate inputs for fuzzing, and debug the program and observe results" [via search summary] — [Project Zero](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)
- Buttercup: fuzzing-first CRS with LLM "Seed Generator" and "multi-agent AI-driven patcher"; requires projects with existing OSS-Fuzz harnesses (fetched) — [GitHub](https://github.com/trailofbits/buttercup); Team Atlanta's Atlantis (1st place) — [GitHub](https://github.com/Team-Atlanta/aixcc-afc-atlantis); AIxCC SoK — [arXiv 2602.07666](https://arxiv.org/html/2602.07666v2)
- IRIS (LLM → CodeQL specs → LLM filter), LLift (static analyzer → LLM path reasoning), RepoAudit (agent → validator) — see KQ2 citations.
- XBOW: "separates discovery from validation entirely ... deterministic logic deciding what's real" [via search summary] — [Rawsec](https://blog.raw.pm/en/about-the-hype-around-xbow/); [XBOW blog](https://xbow.com/blog/we-ran-1060-autonomous-attacks)
- Aardvark: validates candidate vulns "in a sandbox" before reporting [via search summary] — [OpenAI](https://openai.com/index/introducing-aardvark/)
- Anthropic/Mozilla: "task verifiers — a trusted method of confirming whether an AI agent's output actually achieves its goal"; isolated-VM validation (fetched) — [Anthropic](https://www.anthropic.com/news/mozilla-firefox-security)
- OSS-Fuzz-Gen now includes an "integrated agent execution framework" and an "Agent prompt" mode credited with one UAF finding (fetched) — [GitHub](https://github.com/google/oss-fuzz-gen); Google docs page on LLM target generation — [OSS-Fuzz research](https://google.github.io/oss-fuzz/research/llms/target_generation/)
- Research framing papers (2025–2026; not openable, listed for the writer): "Agentic Fuzzing: Opportunities and Challenges" — [arXiv 2605.10074](https://arxiv.org/pdf/2605.10074); "Fuzzing with Agents? Generators Are All You Need" — [arXiv 2604.01442](https://arxiv.org/pdf/2604.01442); OpenAnt: "LLM-Powered Vulnerability Discovery Through Code Decomposition, Adversarial Verification, and Dynamic Testing" — [arXiv 2606.19149](https://arxiv.org/pdf/2606.19149); vEcho: "from Vulnerability Verification to Proactive Discovery" — [arXiv 2603.01154](https://arxiv.org/pdf/2603.01154); CLEAR causal-context agentic reasoning — [arXiv 2608.03134](https://arxiv.org/pdf/2608.03134); LLMxCPG (USENIX Security 2025, code-property-graph context for LLM detection) — [PDF](https://www.usenix.org/system/files/usenixsecurity25-lekssays.pdf); "LLM Agents for Automated Web Vulnerability Reproduction: Are We There Yet?" — [arXiv 2510.14700](https://arxiv.org/pdf/2510.14700); "Words Speak Louder Than Code: Cognitive Heuristics in LLM-Based Code Vulnerability Detection" (LLMs over-weight comments/names) — [arXiv 2606.30587](https://arxiv.org/pdf/2606.30587); PatchPilot (cost-efficient SWE agent with formal-verification attempts) — [arXiv 2502.02747](https://arxiv.org/pdf/2502.02747); "State Machine Guided Harness Automatic Generation" — [arXiv 2607.07007](https://arxiv.org/pdf/2607.07007); CKGFuzzer — [ResearchGate](https://www.researchgate.net/publication/392668998_CKGFuzzer_LLM-Based_Fuzz_Driver_Generation_Enhanced_By_Code_Knowledge_Graph)
- Counter-trend evidence that raw reasoning is improving: Anthropic claims Opus 4.6 finds high-severity bugs "without ... task-specific tooling, custom scaffolding" [via search summary] — [The Hacker News](https://thehackernews.com/2026/02/claude-opus-46-finds-500-high-severity.html); SastBench's no-tools Gemini 2.5 Pro recall rivaled tool-using agents [via search summary] — [arXiv 2601.02941](https://arxiv.org/pdf/2601.02941); Carlini's per-file loop uses no fuzzer in the discovery step but confirms with exploits/PoCs [via search summary] — [SCW podcast](https://securitycryptographywhatever.com/2026/03/25/ai-bug-finding/)

### Inferences
- The orchestrator design is now the de-facto industrial architecture; the open question is where discovery happens (model reading vs fuzzer searching), not whether verification is executable. Anthropic's 2026 results suggest frontier models can *propose* candidates from reading alone, but the published pipelines still pay for validation (Firefox: 112 reports from ~6,000 files, 22 confirmed vulns, i.e., ≈20% of submitted reports became accepted vulnerabilities even after Anthropic's own VM validation, with the remainder being crashes of unclear security impact).
- A reasonable synthesis for the user's design question: use the large model to (1) write/repair harnesses, specs and seeds and (2) triage/validate engine output (where ablations show it adds the most), and let fuzzers/static analyzers do the exhaustive search; reserve raw whole-file reading for targets with no harnessable interface, and gate any raw finding on a reproducer before it leaves the pipeline.

### Gaps
- No controlled study found that fixes a dollar budget and compares "frontier model reads the repo" vs "same model writes harnesses, fuzzer runs N CPU-hours" on identical targets; this is the central missing experiment.
- Primary texts for Agentic Fuzzing (2605.10074), OpenAnt, vEcho, and Google's 2024–2025 OSS-Fuzz LLM scaling posts were not retrievable in this sandbox.
