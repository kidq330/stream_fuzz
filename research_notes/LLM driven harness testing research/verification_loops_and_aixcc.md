## Key Question 1 — Spec inference, contract generation, and Dafny/Verus/Lean "LLM writes, verifier judges" loops: what success rates, what failure modes?

### Takeaway
On small, self-contained tasks the LLM+verifier loop now routinely clears 80–96% in Dafny (DafnyBench 68% in 2024 → ~96% by late 2025), ~40–90% in Verus depending on benchmark difficulty, and <10–30% in Lean; the dominant known failure mode is not proof failure but **spec quality**: verification-passing specs are frequently incomplete, vacuous, or co-adapted to the code, and several 2025–2026 benchmarks (CLEVER, Verina, AlgoVeri, vericoding) were explicitly designed to close that loophole.

- DafnyPro (arXiv 2601.05385, Jan 2026): Claude Sonnet 3.5 + DafnyPro reaches 86% on DafnyBench, +16 pp over the base model **[search-summary]** — [alphaxiv 2601.05385](https://www.alphaxiv.org/abs/2601.05385)

**Benchmarks (Lean) and cross-language alignment**

**Documented failure modes of LLM-written specs**
- "How Powerful are LLMs in Generating Formal Program Specifications?" (arXiv 2608.13077, Aug 2026): 34.6% of specifications that *pass verification* are incomplete relative to human-written counterparts, "a weakness obscured by existing evaluation metrics"; a main failure mode is oversimplification — merging branch-specific pre/postconditions into one over-general constraint; examples include preconditions that are simply `True` and postconditions that omit the critical constraint **[search-summary]** — [arXiv 2608.13077](https://arxiv.org/pdf/2608.13077)
- Verina authors note that a spec which verifies "might still be vacuous (true of any implementation) or non-discriminating (true of a deliberately unsafe variant)" **[search-summary]** — [arXiv 2505.23135](https://arxiv.org/pdf/2505.23135)
- "An Empirical Study of LLM-Generated Specifications for VeriFast" (arXiv 2606.26490) — located, not read — [arXiv 2606.26490](https://arxiv.org/pdf/2606.26490)
- AutoCLRS (Swamy et al., MSR, March 2026): ~52 CLRS algorithms, >100k lines of F*/Pulse specs+code+proofs produced by Copilot CLI running Claude Opus 4.6 in autopilot with FStar-MCP for incremental type-checking; ~5,000 lines of spec required human audit; recurring defects were trivially weak postconditions (e.g., only "source distance ≤ 0"), one-sided bounds, "vacuous complexity proofs" that assign a large number at the end rather than counting operations, and AI spec-review failing to catch inconsistencies; 46 commits were needed for Dijkstra alone; author's verdict: "AI slop is real" **[primary]** — [RiSE AutoCLRS post](https://risemsr.github.io/blog/2026-03-06-autoclrs/)
- "Spotting Specification Gaps with Small Proof-Oriented Tests" (Swamy & Lahiri, April 2026): writing small concrete *verified* tests against the AutoCLRS specs exposed significant spec gaps in 8 of 52 algorithms (44 judged sufficiently precise) **[primary]** — [RiSE post](https://risemsr.github.io/blog/2026-04-16-spotting-specs/)

### Inferences
- Across DafnyBench → vericoding → AlgoVeri, headline "verified" rates fall sharply as the task moves from re-deriving annotations for existing code (≈90%+) to synthesizing code against aligned, non-trivial contracts (≈40% Dafny, ≈25% Verus, <10% Lean). Proof automation, not model capability per se, drives the Dafny/Verus/Lean gradient.
- The field's own benchmark designers have converged on three anti-vacuity mechanisms: (1) proving equivalence to a hidden ground-truth spec (CLEVER), (2) test-based soundness/completeness with output mutation (Verina, nl2postcond, AutoVerus filtering), and (3) aligned fixed contracts across languages (AlgoVeri). Results that report only "verifier accepted" (DafnyBench, early VerusBench numbers) should be read as upper bounds.
- When the same agent writes both code and spec (AutoCLRS, vericoding from NL), human audit of specs remains the bottleneck; the measured 8/52 gap rate after an expert-run project is a useful planning number.

### Gaps
- Exact AutoSpec and SpecGen success counts were not verifiable in this session (arXiv blocked); the report writer should pull them from the CAV 2024 and SpecGen papers directly.
- Vericoding paper's own discussion of spec-gaming/contamination (half of its tasks derive from existing benchmarks) could not be read; only the "6,174 new unseen" count is known.
- Per-model tables for Verina, CLEVER and VeruSAGE not read; the 61%/51%/3.6%/22% Verina figures come from a search summary.
- No source found that quantifies "spec-code co-adaptation" directly as a rate, other than the 34.6%-incomplete figure (arXiv 2608.13077) and the AutoCLRS 8/52 gap count.

## Key Question 2 — Bounded model checking and symbolic execution driven by LLMs (Kani/verify-rust-std, CBMC/ESBMC, KLEE, CrossHair): metrics and results

### Takeaway
The clearest production-grade evidence is verify-rust-std: 16,748 automatically generated Kani harnesses (11,970 verified) plus 989 contract-verified proofs, with LLM-written contracts merged since mid-2025 — and a 2026 follow-up PR showing that LLM-generated harnesses had silently violated a dependency precondition because CI ran with contract assertions disabled. ESBMC-AI is the main BMC-as-oracle repair loop (up to 80% repair on buffer-overflow/pointer classes over 50k FormAI programs). LLM+KLEE harness synthesis exists (90.3% compilable harnesses on incomplete Rust CVE snippets); no LLM+CrossHair work was found.

### Inferences
- The verify-rust-std PR trail is the best available natural experiment for "LLM writes harness/contract, Kani judges": the loop produced mergeable artifacts at scale, but the #623 incident shows the verifier only judges what it is configured to check — a harness that under-constrains its inputs can pass while technically violating a dependency's contract. Any LLM-harness pipeline needs contract assertion enabled and a vacuity/coverage check (Kani `cover`) as part of the oracle.
- ESBMC-AI's design choice (formal re-verification as acceptance) is the direct BMC analogue of test-based repair, and the reported 80% is on synthetic FormAI programs, not real repositories.

### Gaps
- KaPilot's success rate vs. human verify-rust-std harnesses not read.
- No LLM+CrossHair (Python) research found; CrossHair only appears in practitioner contexts.
- No quantitative "harness quality" statistics (fraction vacuous, fraction with over-constraining assumes) exist for the 16,748 automatic harnesses in the public summary.
