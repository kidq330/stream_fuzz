## Key Question 1 — Spec inference, contract generation, and Dafny/Verus/Lean "LLM writes, verifier judges" loops: what success rates, what failure modes?

### Takeaway
On small, self-contained tasks the LLM+verifier loop now routinely clears 80–96% in Dafny (DafnyBench 68% in 2024 → ~96% by late 2025), ~40–90% in Verus depending on benchmark difficulty, and <10–30% in Lean; the dominant known failure mode is not proof failure but **spec quality**: verification-passing specs are frequently incomplete, vacuous, or co-adapted to the code, and several 2025–2026 benchmarks (CLEVER, Verina, AlgoVeri, vericoding) were explicitly designed to close that loophole.

**Documented failure modes of LLM-written specs**
- "How Powerful are LLMs in Generating Formal Program Specifications?" (arXiv 2608.13077, Aug 2026): 34.6% of specifications that *pass verification* are incomplete relative to human-written counterparts, "a weakness obscured by existing evaluation metrics"; a main failure mode is oversimplification — merging branch-specific pre/postconditions into one over-general constraint; examples include preconditions that are simply `True` and postconditions that omit the critical constraint **[search-summary]** — [arXiv 2608.13077](https://arxiv.org/pdf/2608.13077)
- Verina authors note that a spec which verifies "might still be vacuous (true of any implementation) or non-discriminating (true of a deliberately unsafe variant)" **[search-summary]** — [arXiv 2505.23135](https://arxiv.org/pdf/2505.23135)
- "An Empirical Study of LLM-Generated Specifications for VeriFast" (arXiv 2606.26490) — located, not read — [arXiv 2606.26490](https://arxiv.org/pdf/2606.26490)
- AutoCLRS (Swamy et al., MSR, March 2026): ~52 CLRS algorithms, >100k lines of F*/Pulse specs+code+proofs produced by Copilot CLI running Claude Opus 4.6 in autopilot with FStar-MCP for incremental type-checking; ~5,000 lines of spec required human audit; recurring defects were trivially weak postconditions (e.g., only "source distance ≤ 0"), one-sided bounds, "vacuous complexity proofs" that assign a large number at the end rather than counting operations, and AI spec-review failing to catch inconsistencies; 46 commits were needed for Dijkstra alone; author's verdict: "AI slop is real" **[primary]** — [RiSE AutoCLRS post](https://risemsr.github.io/blog/2026-03-06-autoclrs/)
- "Spotting Specification Gaps with Small Proof-Oriented Tests" (Swamy & Lahiri, April 2026): writing small concrete *verified* tests against the AutoCLRS specs exposed significant spec gaps in 8 of 52 algorithms (44 judged sufficiently precise) **[primary]** — [RiSE post](https://risemsr.github.io/blog/2026-04-16-spotting-specs/)

### Inferences
- Across DafnyBench → vericoding → AlgoVeri, headline "verified" rates fall sharply as the task moves from re-deriving annotations for existing code (≈90%+) to synthesizing code against aligned, non-trivial contracts (≈40% Dafny, ≈25% Verus, <10% Lean). Proof automation, not model capability per se, drives the Dafny/Verus/Lean gradient.
- The field's own benchmark designers have converged on three anti-vacuity mechanisms: (1) proving equivalence to a hidden ground-truth spec (CLEVER), (2) test-based soundness/completeness with output mutation (Verina, nl2postcond, AutoVerus filtering), and (3) aligned fixed contracts across languages (AlgoVeri). Results that report only "verifier accepted" (DafnyBench, early VerusBench numbers) should be read as upper bounds.
- When the same agent writes both code and spec (AutoCLRS, vericoding from NL), human audit of specs remains the bottleneck; the measured 8/52 gap rate after an expert-run project is a useful planning number.

### Gaps
- Exact AutoSpec and SpecGen success counts were not verifiable in this session (arXiv blocked); the report writer should pull them from the CAV 2024 and SpecGen papers directly.
- Vericoding paper's own discussion of spec-gaming/contamination (half of its tasks derive from existing benchmarks) could not be read; only the "6,174 new unseen" count is known.
- Per-model tables for Verina, CLEVER and VeruSAGE not read; the 61%/51%/3.6%/22% Verina figures come from a search summary.
- No source found that quantifies "spec-code co-adaptation" directly as a rate, other than the 34.6%-incomplete figure (arXiv 2608.13077) and the AutoCLRS 8/52 gap count.

## Key Question 2 — Bounded model checking and symbolic execution driven by LLMs (Kani/verify-rust-std, CBMC/ESBMC, KLEE, CrossHair): metrics and results

### Takeaway
The clearest production-grade evidence is verify-rust-std: 16,748 automatically generated Kani harnesses (11,970 verified) plus 989 contract-verified proofs, with LLM-written contracts merged since mid-2025 — and a 2026 follow-up PR showing that LLM-generated harnesses had silently violated a dependency precondition because CI ran with contract assertions disabled. ESBMC-AI is the main BMC-as-oracle repair loop (up to 80% repair on buffer-overflow/pointer classes over 50k FormAI programs). LLM+KLEE harness synthesis exists (90.3% compilable harnesses on incomplete Rust CVE snippets); no LLM+CrossHair work was found.

### Cited Findings

**Kani / verify-rust-std**
- "Verifying the Rust Standard Library" (arXiv 2606.17374, June 2026): first large-scale community effort; 16,748 automatic proof harnesses of which 11,970 verified against Kani's supported undefined-behavior classes; 989 contract-verified proofs across automatic and manual harnesses **[search-summary]** — [arXiv 2606.17374](https://arxiv.org/html/2606.17374v1)
- Repo state (Oct 2026): 29 numbered challenges; resolved with Kani: Challenges 1 (core transmuting, $10k), 3, 6, 9, 11, 12 (NonZero, $10k), 14; resolved with VeriFast: 5 (linked list, $20k), 19 (RawVec, $10k); Challenge 15 (SIMD intrinsics, $20k) via "testable models"; 19 challenges open at $5k–$25k; accepted tools Kani, VeriFast, Flux, GOTO-transcoder/ESBMC, KMIR; no explicit AI/LLM participation policy in README **[primary]** — [model-checking/verify-rust-std](https://github.com/model-checking/verify-rust-std)

### Inferences
- The verify-rust-std PR trail is the best available natural experiment for "LLM writes harness/contract, Kani judges": the loop produced mergeable artifacts at scale, but the #623 incident shows the verifier only judges what it is configured to check — a harness that under-constrains its inputs can pass while technically violating a dependency's contract. Any LLM-harness pipeline needs contract assertion enabled and a vacuity/coverage check (Kani `cover`) as part of the oracle.
- ESBMC-AI's design choice (formal re-verification as acceptance) is the direct BMC analogue of test-based repair, and the reported 80% is on synthetic FormAI programs, not real repositories.

### Gaps
- KaPilot's success rate vs. human verify-rust-std harnesses not read.
- No LLM+CrossHair (Python) research found; CrossHair only appears in practitioner contexts.
- No quantitative "harness quality" statistics (fraction vacuous, fraction with over-constraining assumes) exist for the 16,748 automatic harnesses in the public summary.

## Key Question 3 — Refinement types: LHC (ICSE 2025) and follow-ups; LLM-generated Zod/Pydantic/Effect "refine" predicates as lightweight contracts

### Takeaway
LHC remains the single rigorous data point: a fine-tuned 3B model with LiquidHaskell as oracle annotated up to 94% of functions across three real Haskell packages in hours, replacing days-to-weeks of expert work. No 2025–2026 LLM-inference follow-up for Flux, LiquidHaskell or Liquid Java was found, and no research treats LLM-generated Zod/Pydantic refine predicates as checked contracts.

### Cited Findings
- LHC "Neurosymbolic Modular Refinement Type Inference" (Sakkas, Sahu, Ong, Jhala; ICSE 2025 research track): LLM generates refinement type annotations for every function in a package/module; LiquidHaskell is the oracle; dataset of three Haskell packages whose properties range from data-structure invariants to low-level memory safety and that previously took experts "several days to weeks" to annotate; with a fine-tuned 3B StarCoder and carefully chosen context the agent annotates up to 94% of functions across entire libraries "in just a few hours" **[search-summary of ICSE page]** — [ICSE 2025 page](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/115/Neurosymbolic-Modular-Refinement-Type-Inference); [IEEE record](https://ieeexplore.ieee.org/document/11029908/); [UCSD thesis](https://escholarship.org/content/qt0b2298fh/qt0b2298fh_noSplash_c7b46bfdd38ac19c2372e1723c1bb79e.pdf?t=sq4lwk)

## Key Question 4 — Intent formalization (MSR grand challenge, March 2026) and de Moura's "who verifies it" essay: proposed agenda and who is executing

### Takeaway
Lahiri's MSR paper frames the problem as a four-tier spectrum (tests → executable contracts → logical contracts in Dafny/F*/Verus → DSL synthesis) and names automated spec-validation metrics (test-based soundness; mutation-based completeness) as the foremost open problem; the RiSE group is executing on it (TiCoder, nl2postcond, ClassInvGen, VeriStruct, AutoVerus, 3DGen, AutoCLRS/SPOTs). De Moura's essay (Feb 28 2026) argues no one is formally verifying AI-written software and that an AI vendor also supplying the verifier is a conflict of interest — but its full text could not be read here.

### Cited Findings
- "Intent Formalization: A Grand Challenge for Reliable Coding in the Age of AI Agents" (Shuvendu K. Lahiri, MSR RiSE; arXiv 2603.17150; blog March 5 2026): defines intent formalization as "automatically translating informal user intent into a set of formal, checkable program specifications"; distinguishes it from autoformalization; thesis: "the intent gap is the bottleneck" and "specifications are the bottleneck — verification tools remain idle without them" **[primary]** — [RiSE blog](https://risemsr.github.io/blog/2026-03-05-shuvendu-intent-formalization/); [arXiv 2603.17150](https://arxiv.org/html/2603.17150v1); [MSR page](https://www.microsoft.com/en-us/research/publication/intent-formalization-a-grand-challenge-for-reliable-coding-in-the-age-of-ai-agents/)
- Spectrum: (1) tests, (2) executable code contracts (assertions, pre/post, class invariants), (3) logical contracts in verification-aware languages (Dafny, F*, Verus), (4) DSLs with verified synthesis (3D/EverParse) **[primary]** — same source
- Seven research challenges: benchmarks → real systems (side effects, concurrency, async handlers, ML pipelines); change intent and compositionality (SpecTra); cost-effective clarification (TiCoder divergence-targeted tests); automated metrics for spec validation ("no oracle for specification correctness other than the user"); rich logics/quantifiers (LLMs struggle; verifiers cannot unroll recursive predicates on concrete inputs); human-AI interaction; workflow integration (issues, code review, CI; in "vibe coding" specs become the primary human-machine interface) **[primary]** — same source
- Proposed metrics: *soundness* = spec satisfied on every (input, output) test pair; *completeness* = fraction of output mutations the spec rejects; automated symbolic evaluation of quantified contracts on concrete tests; the metrics exposed a GPT-4 Dafny spec missing a bi-implication and found 3 mislabeled and 2 inconsistent specs that human labelers missed **[primary]** — same source
- Named executing work: TiCoder (IEEE TSE 2024; ~2× better developer correctness judgments); nl2postcond (FSE 2024; 1 in 8 Defects4J bugs caught); ClassInvGen (SAIV 2025; C++ class invariants beating Daikon and direct prompting); VeriStruct (TACAS 2026; nearly all functions in 11 Verus modules); AutoVerus (ICLR 2025); 3DGen (ICSE 2025; verified parsers for 20 protocols via EverParse); SpecTra (2024); Clover (SAIV 2024). Collaborators listed include Bjorner, Fakhoury, Chakraborty, Kuppe, Lu, Ramananandro, Swamy, Naik, Sakkas, Endres, Dinella, Mytkowicz, Musuvathi **[primary]** — same source
- Execution evidence from the same group: AutoCLRS (Swamy, March 6 2026; Claude Opus 4.6 via Copilot CLI + FStar-MCP; 52 algorithms; >100k lines) and "Spotting Specification Gaps with Small Proof-Oriented Tests" (April 16 2026; 8/52 algorithms with gaps) **[primary]** — [AutoCLRS](https://risemsr.github.io/blog/2026-03-06-autoclrs/); [SPOTs](https://risemsr.github.io/blog/2026-04-16-spotting-specs/)
- Related MSR 2026 posts in the same series: "DeepTest" (May 4 2026) and an "A3" post (Feb 16 2026) — titles only — [RiSE blog listing](https://github.com/risemsr/risemsr.github.io/tree/main/src/content/docs/blog)
- "Faithful Autoformalization of Natural Language Assertions" (arXiv 2607.13303, July 2026) cites the grand challenge — [arXiv 2607.13303](https://arxiv.org/html/2607.13303)
- Leonardo de Moura, "When AI Writes the World's Software, Who Verifies It?" (Feb 28 2026): per search summaries, the essay observes that Anthropic's parallel-agent-built ~100,000-line C compiler (boots Linux, compiles SQLite/PostgreSQL/Redis/Lua) was not formally verified and that "if the same vendor provides both the AI and the verification, there is a conflict of interest" **[search-summary; page blocked]** — [essay](https://leodemoura.github.io/blog/2026-2-28-when-ai-writes-the-worlds-software-who-verifies-it/); [blog index](https://leodemoura.github.io/blog/)

### Inferences
- The two documents are complementary: Lahiri specifies *what* to check (metrics for spec validity) while de Moura's framing concerns *who* checks (independent verifier, trusted kernel). Together they define a research agenda where spec validation, not proof search, is the open problem.

### Gaps
- De Moura's concrete proposals (e.g., role of Lean/Lean FRO, verification tiers, independent-verifier architecture) could not be read; only two claims are relayed via secondary summaries.
- Whether anyone outside MSR/Lean FRO has formally taken up the "grand challenge" framing by name is unknown.

## Key Question 5 — "LLM + verifier loop" vs "LLM reads code and reports bugs": recall, precision, cost; Big Sleep, Aardvark, Mythos; DARPA AIxCC 2025 architectures and attribution

### Takeaway
No controlled head-to-head study was found, but every production-scale LLM bug-hunting system reviewed converged on the same architecture: the LLM proposes, a dynamic oracle (sanitizer crash, PoV reproduction, sandbox exploit) judges before anything is reported. Pure-LLM white-box detection carries 10–50% false-positive rates in a 2026 benchmark, whereas AIxCC winners scored near-perfect accuracy multipliers by never reporting unexecuted findings. In AIxCC finals, Team Atlanta's Multilang component attributes 48 unique PoVs to the baseline fuzzer vs 25 to LLM-integrated modules, with the LLM path credited for format-aware bugs fuzzing struggled on.

### Inferences
- The AIxCC scoring rule (quartic accuracy penalty) economically forced every finalist into "LLM proposes, execution judges"; the resulting systems are effectively LLM+dynamic-verifier loops, and their self-reported precision is high precisely because unverified LLM claims were never submitted. Pure-LLM reporting (10–50% FPR) would have been penalized.
- The only quantitative attribution available (Multilang: 48 fuzzer vs 25 LLM-module PoVs; MLLA ≥7) suggests LLM paths added roughly a third to a half again as many unique findings on top of fuzzing, concentrated in structured-input bugs — consistent with "verification/fuzzing finds what the LLM misses and vice versa", but no team published a clean per-bug overlap matrix.
- Vendor programs (Big Sleep, Aardvark, Mythos) all insert a validation step (human expert, sandbox exploit, independent firms) before counting a finding, so their >90% true-positive figures measure the post-filter pipeline, not raw LLM precision.

- No peer-reviewed study directly comparing "LLM + verifier loop" with "LLM-only review" on the same codebase with recall/precision/cost was found.
- Final per-team scores for Theori, Shellphish, 42-b3yond-6ug, Lacrosse and FuzzingBrain, and aggregate false-positive/cost statistics, are in the SoK paper's CSV appendices, which could not be fetched.
- Aardvark's claimed recall on seeded "golden" repositories could not be verified (OpenAI page blocked).

## Key Question 6 — Elixir angle: Elixir 1.20 set-theoretic types as a verification tier; LLM-generated specs for Elixir/Erlang (Dialyzer, Gradualizer)

### Takeaway
Elixir 1.20 (June 3 2026) completed "inference first": every construct is typed and gradually checked with no annotations, reporting "verified bugs" at a stated very low false-positive rate; function type signatures are the next milestone. No research or tooling applying LLMs to generate Elixir/Erlang typespecs or to drive Dialyzer/Gradualizer was found.

### Cited Findings
- Elixir v1.20 release (June 3 2026): "Elixir is now a gradually typed language"; first milestone complete — type inference and gradual checking of every Elixir program without annotations; type system is sound, gradual (`dynamic()`), set-theoretic (unions, intersections, negations); reports dead code and "verified bugs: typing violations that are guaranteed to fail at runtime if executed, with an extremely low false positives rate" **[search-summary; page blocked]** — [Elixir v1.20 announcement](https://elixir-lang.org/blog/2026/06/03/elixir-v1-20-0-released/); [Elixir Forum thread](https://elixirforum.com/t/elixir-v1-20-0-released/75566)
- Roadmap (Jan 9 2026 post "Type inference of all constructs and the next 15 months"): inference first, then typed structs, then set-theoretic type signatures for functions, after which Erlang-style typespecs are expected to be phased out **[search-summary]** — [Elixir blog](https://elixir-lang.org/blog/2026/01/09/type-inference-of-all-and-next-15/); [typespecs reference v1.20](https://elixir.hexdocs.pm/typespecs.html)
- Theory basis: Castagna et al., "The Design Principles of the Elixir Type System" (arXiv 2306.06391) and "Guard Analysis and Safe Erasure Gradual Typing" (arXiv 2408.14345) — [design principles](https://arxiv.org/pdf/2306.06391); [guard analysis](https://arxiv.org/pdf/2408.14345)

- The Elixir compiler's "verified bug" reports are the closest Elixir has to a verifier-in-the-loop, and they require no LLM-written artifact; once function signatures land (post-1.20), an "LLM writes signatures, compiler judges" loop analogous to LHC becomes possible but is unreported.
