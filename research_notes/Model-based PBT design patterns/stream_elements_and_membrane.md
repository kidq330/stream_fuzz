## KQ1. What guarantees does Membrane document for an element's outputs, what harness does it ship, and are there any property-based tests in the Membrane org? What are `Membrane.TimestampQueue`'s documented invariants?

### Takeaway
Membrane documents the element contract mostly as *action legality rules* (which actions may be returned from which callback, in which playback state, on which pad type) plus prose about demand; it does **not** state ordering/timestamp invariants ("buffers must be monotonic", "stream format before first buffer") as explicit guarantees in the callback docs — the only "before" rules I found are in `Membrane.Testing.Source` ("StreamFormat to be sent before the output") and the end-of-stream dedup logic in core. `Membrane.TimestampQueue` (now a separate repo, `membrane_timestamp_queue`, Apache-2.0) *does* document precise availability/ordering semantics that read like a contract. No `ExUnitProperties`/`StreamData`/`PropCheck` usage was found anywhere in the `membraneframework` org; the closest thing is a randomized 100-pad × 200-item shuffle test in the TimestampQueue repo that asserts a sortedness invariant rather than an exact oracle.

### Cited Findings

**Element behaviours (membrane_core, Apache-2.0 — LICENSE fetched)**

- Element taxonomy: "source, producing buffers (contain only output pads), / filter, processing buffers (contain both input and output pads), / endpoint, producing and consuming buffers (contain both input and output pads), / sink, consuming buffers (contain only input pads)." — [Membrane.Element.Base source](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/base.ex)
- `handle_playing`: "From this point, element can send and receive buffers, events, stream formats and demands through its pads." — [base.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/base.ex)
- `handle_event`: "Callback that is called when event arrives. Events may arrive from both input and output pads. In filters by default event is forwarded to all output and input pads, respectively. By default, it ignores received event." — [base.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/base.ex)
- `handle_stream_format`: "Callback invoked when Element is receiving information about new stream format for given pad. In filters stream format is forwarded through all output pads by default. Context passed to this callback contains additional field `:old_stream_format`." — [Membrane.Element.WithInputPads](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/with_input_pads.ex)
- `handle_start_of_stream`: "Callback invoked when element receives the first buffer from the specific pad, before `handle_buffer/4`." — [with_input_pads.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/with_input_pads.ex)
- `handle_end_of_stream`: "Callback invoked when the previous element has finished processing via the pad, and it cannot be used anymore." — [with_input_pads.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/with_input_pads.ex)
- `handle_buffer`: "Callback that is called when buffer should be processed by the Element. For pads in pull mode it is called when buffer have been demanded (by returning `:demand` action from any callback). For pads in push mode it is invoked when buffer arrive." — [with_input_pads.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/with_input_pads.ex)
- `handle_demand` (output pads): "It is called only for output pads in the `:manual` flow control mode, as in their case demand is triggered by the input pad of the subsequent element. In sources and endpoint, appropriate amount of data should be sent here. In filters, this callback should usually return `:demand` action with size sufficient for supplying incoming demand. … If a source or an endpoint is unable to produce enough buffers, or a filter underestimated returned demand, the `:redemand` action should be used". — [Membrane.Element.WithOutputPads](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/with_output_pads.ex)
- Filter defaults (the default "pass-through" contract): `handle_stream_format` → `{[broadcast: stream_format], state}`; `handle_event` forwards to all pads of the opposite direction (`opposite_dir = Membrane.Pad.opposite_direction(context.pads[pad].direction)`); `handle_end_of_stream` → `{[broadcast: :end_of_stream], state}`. — [Membrane.Filter source](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/filter.ex)
- Filter moduledoc: "If the pad has the flow control set to `:manual`, then filter is also responsible for receiving demands on the output pad and requesting them on the input pad". — [filter.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/filter.ex)
- Flow control modes: "`:auto` - meaning that the pad works in a pull mode and the demand is managed automatically: the core ensures that there's demand on each input pad (that has `flow_control` set to `:auto`) whenever there's demand on all output pads (that have `flow_control` set to `:auto`). … `:push` - … An element with a `:push` input pad has to deal with data whenever it comes through such a pad - note, that it needs to be done fast enough so that not to let data accumulate, what may lead to overflow of element process erlang queue … Linking pads with different flow control is possible, but only in case of an output pad working in a push mode, and an input pad in pull mode … In such case, however, an error will be raised whenever too many buffers accumulate on the input pad, waiting to be processed." — [Membrane.Pad](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/pad.ex)
- Demand action guarantee: "This action does NOT entail _sending_ demand through the pad, but just _requesting_ some amount of data from pad's internal queue, which _sends_ demands automatically when it runs out of data. If there is any data available at the pad, the data is passed to `handle_buffer/4` callback. Invoked callback is guaranteed not to receive more data than demanded." — [Membrane.Element.Action](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/action.ex)
- `pause_auto_demand`: "This action does not guarantee that no more buffers will arrive on the specific pad, but ensures, that demand on this pad will not increase until returning `resume_auto_demand()` action. Number of buffers, that will arrive on the pad, depends on the behaviour of the elements earlier in the pipeline." — [action.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/action.ex)
- Stream format action: "Sends stream format through a pad. The pad must have output direction. Sent stream format must fit constraints on the pad. Allowed only when playback is `playing`." Buffer action: "Sends buffers through a pad. The pad must have output direction. Allowed only when playback is playing." End of stream action: "Marks that processing via a pad (output) has been finished and the pad instance won't be used anymore. Triggers `end_of_stream/3` callback at the receiver element. Allowed only when playback is in playing state." — [action.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/action.ex)
- `stop_timer` is the one action documented as atomic: "This action is atomic: stopping timer guarantees that no ticks will arrive from it." — [action.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/element/action.ex)
- Buffer struct and timestamps: `%Buffer{pts: Time.t() | nil, dts: Time.t() | nil, payload, metadata}`; `get_dts_or_pts/1` "Returns `:dts` if available or `:pts` if `:dts` is not set. If none of them is set `nil` is returned." No monotonicity rule is stated. — [Membrane.Buffer](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/buffer.ex)
- Runtime enforcement in core: stream-format actions are validated against the pad's `accepted_format` ("Stream format: … is not matching accepted format pattern … in def_#{direction}_pad for pad … Beware that stream format is forwarded by the default implemetation of handle_stream_format in filters.") — [stream_format_controller.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/core/element/stream_format_controller.ex); duplicate EOS is tolerated and logged ("Ignoring end of stream as it has already arrived before") — [event_controller.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/core/element/event_controller.ex); stream actions outside `:playing` raise `ActionError … {:invalid_component_playback, playback}` — [action_handler.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/core/element/action_handler.ex). I found **no** core check that a stream format was sent before the first buffer on an output pad (searched `stream_format_controller.ex`, `buffer_controller.ex`, `action_handler.ex`).

**Testing harness (membrane_core)**

- `Membrane.Testing.Pipeline`: "This Pipeline was created to reduce testing boilerplate and ease communication with its children. It also provides a utility for informing testing process about playback changes and received notifications." Example in the moduledoc: `child(:source, %Membrane.Testing.Source{output: [1, 2, 3]}) |> child(:tested_element, TestedElement) |> child(:sink, Membrane.Testing.Sink)` then `assert_end_of_stream(pipeline, :sink)` and `assert_sink_buffer(pipeline, :sink, %Membrane.Buffer{payload: 1})`. Options include `test_process: pid()`. — [testing/pipeline.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/pipeline.ex)
- `Membrane.Testing.Source`: `def_output_pad :output, flow_control: :manual`; option `output`: "If `output` is an Enumerable, then each element of it will be sent through the `:output` pad, followed by `end_of_stream`. … Otherwise, if `output` is a `{initial_state, function}` tuple then the function will be invoked each time `handle_demand` is called. … Such function should return `{actions, next_state}`"; option `stream_format`: "StreamFormat to be sent before the `output`." (default `%Membrane.RemoteStream{}`). — [testing/source.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/source.ex)
- `Membrane.Testing.Sink`: "Sink Element that notifies the pipeline about buffers and events it receives. By default `Sink` will demand buffers automatically, but you can override that behaviour by using `autodemand` option. If set to false no automatic demands shall be made. Demands can be then triggered by sending `{:make_demand, size}` message." It is `def_input_pad :input, flow_control: :manual, demand_unit: :buffers`; it emits `notify_parent: %Notification{payload: ...}` for `:playing`, `{:event, event}`, `{:start_of_stream, pad}`, `{:end_of_stream, pad}`, `{:stream_format, pad, stream_format}`, `{:buffer, buf}`; with `autodemand: true` each `handle_buffer` returns `[demand: :input] ++ notify({:buffer, buf})`. — [testing/sink.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/sink.ex)
- `Membrane.Testing.Assertions`: "These assertions will work ONLY in conjunction with `Membrane.Testing.Pipeline` and ONLY when pid of tested pipeline is provided as an argument to these assertions." `@default_timeout 2000`. Every macro expands to ExUnit `assert_receive`/`refute_receive` on `{Membrane.Testing.Pipeline, ^pid, pattern}`; `assert_sink_buffer(pipeline, sink_name, pattern, timeout \\ 2000)`, `refute_sink_buffer` ("Asserts that `Membrane.Testing.Sink` with name `sink_name` has not received and will not receive a buffer matching `buffer_pattern` within the `timeout` period"), `assert_end_of_stream(pipeline, element_name, pad \\ :input, timeout \\ 2000)` matching `{:handle_element_end_of_stream, {element_name, pad}}`, plus `assert_sink_stream_format`, `assert_sink_event`, `assert_start_of_stream`, `assert_pipeline_notified`. — [testing/assertions.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/assertions.ex)
- Settle mechanism implied by the harness: the test process is a mailbox; "settle" = `assert_end_of_stream(pipeline, :sink)` (EOS reached the sink) followed by draining `{:buffer, _}` notifications; non-occurrence is checked with `refute_sink_buffer` over a wall-clock timeout (2 s default). — [assertions.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/assertions.ex); [pipeline.ex](https://raw.githubusercontent.com/membraneframework/membrane_core/master/lib/membrane/testing/pipeline.ex)

**Property-based testing in the Membrane org**

- GitHub code search for `ExUnitProperties org:membraneframework`, `StreamData org:membraneframework filename:mix.exs`, and `PropCheck org:membraneframework` each returned `"total_count":0` (searched 2026-10-03). — [GitHub code search via MCP](https://github.com/search?q=ExUnitProperties+org%3Amembraneframework&type=code)
- The TimestampQueue test suite is plain ExUnit (`grep` for `ExUnitProperties|StreamData|property` returned nothing), but one test is a randomized invariant check: 100 pads × 200 items, random `dts_offsets`, random interleaving of `push_buffer`/`push_event`/`push_stream_format`, random pad choice per step, then: `assert length(batch) == pads_number * pad_items_number + pads_number` (conservation, counting one EOS per pad) and `assert batch_without_eos == sorted_batch_without_eos` where sorting is by `item.dts - dts_offsets[pad_ref]` (monotone output after per-pad offset normalisation). — [membrane_timestamp_queue unit_test.exs](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/test/membrane_timestamp_queue/unit_test.exs)
- Other test names in that file describe the contract: "queue raises on buffer with nil dts and pts", "queue prioritizes stream formats and buffers not preceded by a buffer", "queue returns events and stream formats, even if it cannot return next buffer", "queue doesn't return any buffer, if it should wait on buffer from the registered pad", "flush_and_close/1 works like pop_available_items/1 on a queue with end of stream on every pad", "push_buffer_and_pop_* functions work as composition of push and pop functions", "push_buffer_and_pop_* functions don't return pause and resume demand actions for the same pad". — [unit_test.exs](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/test/membrane_timestamp_queue/unit_test.exs)

**`Membrane.TimestampQueue` (repo `membraneframework/membrane_timestamp_queue`, v0.2.3, Apache-2.0; not in membrane_core master — the `lib/membrane` listing has no `timestamp_queue`)**

- Purpose: "Implementation of a queue, that accepts: Membrane buffers, events, stream formats, end of streams from various pads. Items in queue are sorted according to their timestamps. Moreover, `Membrane.TimestampQueue` is able to manage demand of pads, based on the amount of buffers from each pad currently stored in the queue." README: "a helper queue that is aimed to help manage flow control in `Membrane` elements with pads with `flow_control: :auto`." — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex); [README](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/README.md)
- Precondition: "Buffers pushed to the queue must have a non-`nil` `dts` or `pts`." — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- **Availability rule (the core invariant)**: "A buffer `b` from pad `p` is available, if all pads different than `p` — either have a buffer in the queue, that is older than `b` — or haven't ever had any buffer on the queue — or have end of stream pushed on the queue. An item other than a buffer is considered available if all newer buffers on the same pad are available." — [timestamp_queue.ex, `pop_available_items/1`](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- Demand side-effects as *suggested actions*: `push_buffer/3 :: {[Action.pause_auto_demand()], t()}` — "If the amount of buffers associated with the specified pad in the queue just exceded `pause_demand_boundary`, the suggested actions list contains `pause_auto_demand()` action, otherwise it is equal an empty list." `pop_available_items/1 :: {[Action.resume_auto_demand()], [popped_value()], t()}` — "If the amount of buffers associated with any pad in the queue falls below the `pause_demand_boundary`, the suggested actions list contains `resume_auto_demand()` actions". Default boundary `{:buffers, 1000}`; units `:buffers | :bytes | :time`. — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- Synchronisation strategies: "`:synchronize_on_arrival` - in the moment of the arrival of the first buffer from a specific pad, there will be caluclated timestamp offset for this pad. These offsets will be added to the buffers timestamps … Every offset will be calculated in such a way that the first buffer from a new pad will be returned as the next item. `:explicit_offsets` - buffers from various pads will be sorted based on their timestamps and pads offsets. … If pad offset is not explicitly set before the first buffer from this pad, it will be equal 0." — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- `register_pad/3` option `wait_on_buffers?` (default true): "Specyfies, if the queue will wait with returning buffers in `pop_*` functions, until it receives the first buffer from a pad passed as a second argument". — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- Chunking is deliberately approximate (a legitimate-nondeterminism clause): "The duration of each chunk may not be exactly the `chunk_duration`, but the average duration will converge to it. With that exception, only full chunks are returned." — [timestamp_queue.ex, `pop_chunked/1`](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- Close/flush discipline: `flush_and_close/1` "Pops all items in the proper order and closes the queue. After being closed, nothing can be pushed to the queue anymore … Suggested actions list contains `resume_auto_demand()` for every pad, that had pasued auto demand before the flush." `has_pad?/2`: "true, if the pad has been registered in the queue or item from it has been pushed to the queue and moreover, end of stream of this pad hasn't been popped from the queue." — [timestamp_queue.ex](https://raw.githubusercontent.com/membraneframework/membrane_timestamp_queue/master/lib/membrane/timestamp_queue.ex)
- Users in the wild: `membraneframework/membrane_mpegts_plugin` `lib/muxer.ex` and `kim-company/membrane_mpeg_ts_plugin` `lib/membrane/mpeg/ts/muxer.ex` reference `Membrane.TimestampQueue` (code search). — [GitHub code search](https://github.com/search?q=%22Membrane.TimestampQueue%22+language%3Aelixir&type=code)

### Inferences
- The Membrane element contract that is actually enforced by core is: (i) stream actions only in `:playing`; (ii) stream formats must match `accepted_format`; (iii) `handle_buffer` never receives more than demanded; (iv) duplicate EOS is swallowed; (v) `:auto` demand is propagated from all auto output pads to each auto input pad. Everything else (format-before-buffer, PTS monotonicity, EOS-is-final on output) is convention, so a README model for a Membrane filter must *state* those as properties rather than cite them as framework guarantees.
- `Membrane.TimestampQueue`'s availability rule is already in "contract form": it is a predicate over the multiset of queued items, not an algorithm. A model for it can be: for every popped buffer `b` from pad `p`, every other open pad either had an older buffer still queued or has EOS; and popping preserves per-pad FIFO and global sortedness by `(ts + offset)`. The repo's own randomized test checks exactly conservation + sortedness, which is evidence the maintainers think of it that way.
- The Testing.Sink/Assertions mailbox design means settling is message-driven: EOS at the sink is the settle signal; absence is only checkable by timeout (`refute_*`).

### Gaps
- hexdocs pages for membrane_core were blocked; all quotes are from source `@doc`s on `master` (functionally the same text).
- I could not find any Membrane guide text stating "stream format must precede buffers" as a rule; the only "before" wording is Testing.Source's option doc. Treat it as a convention to be asserted, not a documented framework guarantee.
- The code search index returned zero for PBT libs in the org; GitHub code search can miss files, so "no PBT in Membrane org" is strongly indicated but not proven.

## KQ2. What invariants does GStreamer state for elements (design docs), what does GstHarness do, and what does gst-validate check on live pipelines?

### Takeaway
GStreamer is the richest source of *explicitly written* streaming-element invariants: the design docs use MUST/SHOULD language for segment-before-buffers, EOS-is-final, clipping to segment, latency reporting and serialized-event ordering; `gst-validate`'s pad monitor turns these into runtime checks with named issue IDs (e.g. `BUFFER_BEFORE_SEGMENT`, `BUFFER_AFTER_EOS`, `BUFFER_TIMESTAMP_OUT_OF_RECEIVED_RANGE`, `EVENT_SERIALIZED_OUT_OF_ORDER`, `EVENT_EOS_WITHOUT_SEGMENT`); and `GstHarness` is a deterministic black-box harness with virtual time ("crank").

### Cited Findings

**Design-doc invariants (GStreamer monorepo, `subprojects/gst-docs`, LGPL docs)**

- Segment before buffers: "Before sending buffers, an element must send a SEGMENT event. An element is free to refuse buffers if they were not preceded by a SEGMENT event." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md)
- Clipping/dropping policy: "Buffers should be clipped within the range indicated by the newsegment event start and stop values. Sinks must drop buffers with timestamps out of the indicated segment range." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md); segments.md: "Some elements might produce buffers that fall outside of the segment and that might therefore be discarded or clipped." and "Note that `BUFFER_TIMESTAMP` is always >= `segment_start` or else it would fall outside of the configured segment." — [segments.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/segments.md)
- Serialization: "The SEGMENT event should be sent from the streaming thread and should be serialized with the buffers." "The EOS event should always be interleaved with the data flow, therefore the GStreamer core will take the `STREAM_LOCK`." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md)
- EOS discipline: "The downstream element should forward the EOS event to its downstream peer elements." "An element might want to flush its internally queued data before forwarding the EOS event downstream." "For elements with multiple sink pads it might be possible to wait for EOS on all the pads before forwarding the event." "An element that sends EOS on a pad should stop sending data on that pad." "A `FLUSH_STOP` event on an element flushes the EOS state and all pending EOS messages." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md)
- Flush semantics: "After the flush completes the second stage, data is flowing again in the pipeline and all buffers are more recent than those before the flush." "Any pending EOS events should be discarded too." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md)
- Sticky-event bookkeeping (why "format before buffers" is structural): "When the next data item is pushed, the pending events are pushed first. This ensures that the event function is never called for flushing pads and that the sticky array only contains events for which the event function returned success." — [events.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/events.md)
- Latency contract (bounded delay): "**`min-latency`** … Elements answering the latency query and introducing latency must set this to the maximum time for which they will delay data, while considering upstream's minimum latency. As such, from an element's perspective this is *not* its own minimum latency but its own maximum latency." … `min_latency = upstream_min_latency + own_min_latency`. "**`max-latency`** … the maximum time an element … Elements answering the latency query should set this to the maximum time for which they can buffer upstream data without blocking or dropping further data." Blocking buffers add (`max_latency = upstream_max_latency + own_max_latency`), leaky buffers take `MIN (upstream_max_latency, own_max_latency)`. "If the element has multiple sinkpads, the minimum upstream latency is the maximum of all live upstream minimum latencies." — [latency.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/latency.md)
- Why late = dropped: "clock is now `>= 1` second, the sink will drop this buffer because it is too late. Without any latency compensation in the sink, all buffers will be dropped." — [latency.md](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-docs/markdown/additional/design/latency.md)

**gst-validate runtime checks (`subprojects/gst-devtools/validate`, LGPL-2.1+)** — each is a registered issue with id, summary, description:

- `BUFFER_BEFORE_SEGMENT` (WARNING): "buffer was received before a segment" / "in push mode, a segment event must be received before a buffer". — [gst-validate-report.c](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-devtools/validate/gst/validate/gst-validate-report.c)
- `BUFFER_IS_OUT_OF_SEGMENT` (ISSUE): "buffer being pushed is out of the current segment's start-stop range. Meaning it is going to be discarded downstream without …". — [gst-validate-report.c](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-devtools/validate/gst/validate/gst-validate-report.c)
- `BUFFER_TIMESTAMP_OUT_OF_RECEIVED_RANGE` (WARNING) — the "no invention" invariant: "a buffer leaving an element should have its timestamps in the range of the received buffers timestamps. i.e. If an element received buffers with timestamps from 0s to 10s, it can't push a buffer with a 11s timestamp, because it doesn't have data for that". Implemented in the pad monitor by tracking `timestamp_range_start`/`timestamp_range_end` over received buffers (with `AUDIO_TIMESTAMP_TOLERANCE (GST_MSECOND * 100)`). — [gst-validate-report.c](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-devtools/validate/gst/validate/gst-validate-report.c); [gst-validate-pad-monitor.c](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-devtools/validate/gst/validate/gst-validate-pad-monitor.c)

### Inferences
- GStreamer's documented element contract, restated as properties: (1) `caps`/`segment` precede the first buffer; (2) no buffer after EOS on a pad; (3) output timestamps ⊆ hull of input timestamps (no invention); (4) serialized events keep relative order and are not dropped; (5) outputs clipped/dropped only per segment policy; (6) element never delays data longer than its reported min-latency; (7) flow-return is propagated. gst-validate shows these are checkable on *any* element without a reference implementation — i.e. a contract, not an oracle.
- GstHarness's "crank" is the canonical answer to "how do you settle a time-driven element": advance virtual time to the next registered wait and release it, then inspect queues; wall-clock sleeps are avoided.

## KQ3. How do dataflow / stream-processing systems test operators with properties (Flink, Kafka Streams, Beam, Timely, Materialize; FlinkCheck / sscheck)?

### Takeaway
Mainstream engines ship *synchronous, virtual-time operator harnesses* (Flink `OneInputStreamOperatorTestHarness`, Kafka `TopologyTestDriver`) that make "settle" trivial (every call returns after processing; time is advanced explicitly); the Beam model and Timely progress tracking supply the watermark/frontier invariants worth asserting (monotone watermark, "once the frontier passes t no more data at t"). Academic PBT for stream processors (sscheck for Spark Streaming; FlinkCheck for Flink) expresses properties in bounded linear temporal logic over batches (`always (...) during n`).

## KQ4. What invariants/tests exist for jitter buffers and reordering queues (GStreamer rtpjitterbuffer, pion)?

### Takeaway
Real jitter-buffer tests assert (a) output strictly increasing in both seqnum and RTP timestamp, (b) conservation accounting (`received + dropped == pushed`), (c) policy-governed loss with explicit counters (`num-pushed`, `num-lost`, `num-late`, `num-duplicates`), (d) lost events carrying the expected seq/ts/duration, and (e) "nothing else in the queue" after each crank. Latency is a declared bound: packets arriving after `latency` are "considered to be lost".

### Cited Findings

**GStreamer `rtpjitterbuffer` (gst-plugins-good, LGPL-2+)**
- Element contract: "This element reorders and removes duplicate RTP packets as they are received from a network source." "The rtpjitterbuffer will wait for missing packets up to a configurable time limit using the `latency` property. Packets arriving too late are considered to be lost packets. If the `do-lost` property is set, lost packets will result in a custom serialized downstream event of name GstRTPPacketLost." "The jitterbuffer will use the DTS (or PTS if no DTS is set) of the incoming buffer and the rtptime inside the RTP packet to create a PTS on the outgoing buffer." "This element acts as a live element and so adds `latency` to the pipeline." — [gstrtpjitterbuffer.c](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-plugins-good/gst/rtpmanager/gstrtpjitterbuffer.c)

### Inferences
- A minimal jitter-buffer contract, as actually tested in the wild: (1) per-stream strictly increasing seqnum and timestamp on output; (2) `out + dropped(+lost events) == in` accounting; (3) no duplicates out (duplicates counted, not emitted); (4) a packet is either emitted, or classified `lost`/`late` by the latency policy — never silently vanished; (5) lost events carry the expected seq/ts/duration; (6) nothing is emitted before the buffering threshold / before `latency` has elapsed in virtual time; (7) EOS flushes everything still held.
- Both codebases use *counters* as the way to make drops legitimate yet checkable: the postcondition becomes "emitted ∪ counted-dropped = pushed" rather than "emitted = pushed".

- No published *property-based* (random-input) test of a jitter buffer was found in any of the fetched repos; all are example-based with invariant-style oracles.

## KQ5. How do history checkers (Jepsen `queue`/`total-queue`, Knossos) express a queue contract without a reference implementation?

### Takeaway
Jepsen's `total-queue` is the cleanest existing "model as contract" for a queue: it never simulates the queue, it just multiset-compares *attempted* enqueues, *acknowledged* enqueues and *ok* dequeues, defining `ok`, `unexpected` (invention), `duplicated`, `lost` and `recovered`, with validity = `lost` and `unexpected` both empty. It also states the precondition for conservation to be checkable: the history must drain the queue.

### Cited Findings
- `total-queue` docstring: "What goes in *must* come out. Verifies that every successful enqueue has a successful dequeue. Queues only obey this property if the history includes draining them completely. O(n)." — [jepsen/checker.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/main/jepsen/src/jepsen/checker.clj)
- `TotalQueue` implementation (EPL-1.0 per `project.clj`): builds three multisets — `attempts` (`:enqueue` invocations), `enqueues` (`:enqueue` ok), `dequeues` (`:dequeue` ok) — then: `; The OK set is every dequeue which we attempted. ok (multiset/intersect dequeues attempts)`; `; Unexpected records are those we *never* tried to enqueue. … Definitely don't want your queue emitting records from nowhere! unexpected (->> dequeues (remove (c/set (keys (multiset/multiplicities attempts)))) …)`; `; Duplicate records are those which were dequeued more times than they could have been enqueued; but were attempted at least once. duplicated (-> dequeues (multiset/minus attempts) (multiset/minus unexpected))`; `; lost records are ones which we definitely enqueued but never came out. lost (multiset/minus enqueues dequeues)`; `; Recovered records are dequeues where we didn't know if the enqueue suceeded or not, but an attempt took place. recovered (multiset/minus ok enqueues)`; `{:valid? (and (empty? lost) (empty? unexpected)) …}`. — [jepsen/checker.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/main/jepsen/src/jepsen/checker.clj); licence: [project.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/main/jepsen/project.clj) (`:license {:name "Eclipse Public License"}`)
- `queue` checker (model-reducing variant): "Every dequeue must come from somewhere. Validates queue operations by assuming every non-failing enqueue succeeded, and only OK dequeues succeeded, then reducing the model with that history. Every subhistory of every queue should obey this property. Should probably be used with an unordered queue model, because we don't look for alternate orderings. O(n)." Code: filters `:enqueue` → `invoke?`, `:dequeue` → `ok?`, then `(reduce model/step model)` and fails if `(model/inconsistent? final)`. — [jepsen/checker.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/main/jepsen/src/jepsen/checker.clj)
- Same pattern for sets and IDs: `set`: "verifies that every successfully added element is present in the read, and that the read contains only elements for which an add was attempted." `unique-ids`: "Checks that a unique id generator actually emits unique IDs … `:valid? (empty? dups)`". `counter`: "validates that at each read, the value is greater than the sum of all :ok increments, and lower than the sum of all attempted increments." — [jepsen/checker.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/main/jepsen/src/jepsen/checker.clj)
- Knossos (linearizability with a sequential model): "Given a history of operations by a set of clients, and some singlethreaded model, attempts to show that the history is not linearizable with respect to that model." Histories are invoke/ok/fail/info pairs: "if you're not sure what happened, e.g. the operation timed out." "Notice that we don't have to provide a value for invocations if we don't know what it will be in advance--for instance, during a read. Knossos will fill in the invocation's `:value` from the completion operation, when possible." — [knossos README](https://raw.githubusercontent.com/jepsen-io/knossos/master/README.md)

### Inferences
- The `total-queue` vocabulary maps one-to-one onto stream-element conservation: `unexpected` = *no invention*; `duplicated` = *no duplicate*; `lost` = *no loss*; `recovered` handles the indeterminate case (an item whose enqueue/push status is unknown may or may not appear). The "must drain" precondition is exactly the EOS/flush-before-check discipline.
- `queue` vs `total-queue` shows the two ways to handle ordering nondeterminism: either (a) reduce with a *reference model* that tolerates reorder (unordered queue), or (b) drop ordering from the contract and check it separately (e.g. per-key monotonicity on the output sequence alone, as GStreamer's test does).
- The invoke/ok/fail/info split is how Jepsen handles legitimate nondeterminism: an `info` (timeout) outcome widens the set of acceptable histories instead of asserting one.

### Gaps
- Knossos's `model.clj` queue models were not fetched; only README text is quoted.

## KQ8 (synthesis across sources). What is the minimal invariant set for a reordering element, how is legitimate nondeterminism handled, and how is "settle" done?

### Takeaway
Across GStreamer, jitter-buffer tests, Jepsen and the dataflow harnesses, the recurring contract for a reordering/timestamp element is: protocol order (format/segment → buffers → EOS, nothing after EOS), per-stream monotone output, conservation as `out ⊎ counted-drops = in` with no invention and no duplicates, a declared latency bound, and EOS/flush that drains. Nondeterminism is admitted via counters/categories (`lost`, `late`, `duplicates`, `recovered`, `info`), set-based or "exactly one pane" postconditions, and declared approximations; settling is done with virtual time (`crank`, `setProcessingTime`, `advanceWallClockTime`), synchronous drivers, progress frontiers (`probe.less_than`), or an EOS round-trip.

### Inferences
- Minimal contract for a Membrane-style reordering element (TimestampQueue-like), assembled from the above: (1) **Protocol**: stream format precedes the first buffer on each output pad; no buffer/event after `end_of_stream` on a pad; EOS emitted exactly once per output pad. (2) **Monotonicity**: `get_dts_or_pts` of emitted buffers is non-decreasing per output pad (strict if duplicates are disallowed). (3) **Conservation**: multiset of emitted payloads ⊎ items classified as dropped-by-policy == multiset pushed; no element emitted that was never pushed; nothing emitted twice. (4) **Bounded hold**: an item pushed at virtual time `t` is emitted or classified by `t + latency`; equivalently occupancy ≤ `pause_demand_boundary`-derived bound and `pause_auto_demand`/`resume_auto_demand` are suggested exactly when the boundary is crossed (TimestampQueue's own stated rule). (5) **Drain**: after EOS on all inputs (or flush) the element is empty and conservation holds exactly.
- Preferred way to express policy drops: model-side counters or a classification function returning `{:emitted | :dropped_late | :dropped_dup}` per item, so the postcondition is a partition check, not a value check (GStreamer stats; Jepsen categories).
- For a BEAM element the practical settle choices, in order of determinism: inject a virtual clock (Membrane timers use `Process.send_after` per `action.ex`, so a test clock would need the element's `clock` option), or do a synchronous round-trip (EOS → `assert_end_of_stream`) and treat `refute_sink_buffer` timeouts as the only way to check non-emission.

### Gaps
- No source fetched describes virtual-time injection for Membrane elements specifically (the `latency` action doc points to a `guides/timer.md` that was not fetched).
