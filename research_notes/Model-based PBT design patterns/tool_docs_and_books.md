## Key question 1: What do the authors say the model state should contain? (abstraction, "simplified version", "ignore details")

### Takeaway
Every tool that says anything about this says the same thing in different words: the model tracks only "the useful part" of the SUT's hidden state, as an abstract/simplified data structure (a proplist, a list of key/value pairs, a `dict`, a map from references to ints, a single integer for a list's size), treated as a black box via its API; fast-check is the only tool whose docs explicitly warn in prose that the model "should not be a carbon copy of the system" and that one must "avoid testing the code by comparing it to itself".

### Cited Findings
- PropEr `proper_statem` module doc: "In order to be able to test impure code, we need a way to track its internal state (at least the useful part of it). To this end, we use an abstract state machine representing the possible configurations of the system under test. When referring to the *model state*, we mean the state of the abstract state machine." Example given: "assuming that the internal state of the process dictionary is modeled as a proplist, the model state after generating the previous command sequence will be `[{b,{var,2}}]`." — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- PropEr tutorial on the "problem/solution" framing: "**The problem:** Our server has some internal state based on previous operations (e.g. user accounts which have been created, the set of available movies, next password to be allocated, etc.) and this state is not directly accessible, at least not from the API. **The solution:** Even if not observable, the state is there! And this means we can try to compute it, even without knowing the details of the implementation. To this end, we build an abstract state machine that models the behaviour of the server. The state of the abstract state machine, also referred as the _model state_, corresponds to the implicit internal state of the system under test. Now, all we have to check is whether these states ever become inconsistent." — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial, explicit black-box instruction: "Write a callback module describing the expected behaviour of the SUT. The expected behaviour is specified via an abstract state machine that models the operations in the SUT, treating it as a blackbox accessible only from the API." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial, the clearest "don't copy the implementation" passage (about server-generated passwords): "Password allocation is on the server side and we have little information about it, since we decided to test it as a blackbox. We could make an exception and take a look at the algorithm for password generation, but in this way we would be copying and not actually testing how passwords are created. We can take a different approach: since passwords are available to the users as the result of creating a new account (i.e. `create_acount/1` calls), they should be treated and tested exactly as such." The resulting model is just two lists: `-record(state, {users :: [password()], rented :: [{password(),movie()}]}).` "The first component is a list of passwords generated from `create_account/1` calls in the current test, while the second is a list keeping track of rented movies." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial on model errors being expected: "Such an inconsistency can be detected from the results of API calls. When this occurs, there is much probability that the error lies in our model and not in the implementation. But then, it is quite easy to redefine our model and run the test again." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr `proper_fsm`: state split into name + data: "`StateName` is used to denote a state of the finite state machine and `StateData` is any relevant information that has to be stored in the model state. States are fully represented as tuples `{StateName, StateData}`." FSM tutorial adds: "the initial state of our model should coincide with the initial state of the system under test." — [proper_fsm.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_fsm.erl); [FSM tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_finite_state_machines.md)
- PropCheck `StateM.ModelDSL` (Hébert-derived cache example): "The SUT is a cache implementation based on an ETS and the model is is based on a list of (key/value)-pairs. This example is derived from [Fred Hebert's PropEr Testing, Chapter 9](http://propertesting.com/book_stateful_properties.html)" and "In our simplified cache example the initial model is an empty list: `def initial_state(), do: []`". It also calls the model "the ingenious part of stateful property based testing!" — [model_dsl.ex](https://raw.githubusercontent.com/alfert/propcheck/master/lib/statem/model_dsl.ex)
- PropCheck ModelDSL on what the model is for: "Instead of testing operations and their effects on the data structure directly, we construct a model of the system and generate a sequence of commands operating on both, the model and the system. Then we check that after each command step, the system has evolved accordingly to the model. This is the same idea which is used in model checking and is sometimes called a bisimulation." — [same](https://raw.githubusercontent.com/alfert/propcheck/master/lib/statem/model_dsl.ex)
- PropCheck's port of Hébert's cache model (the actual model code): `defstruct max: @cache_size, entries: [], count: 0`; the `cache` command's `next` is a 3-clause list manipulation with comments "When the cache is at capacity, the first element is dropped (tl(L)) before adding the new one at the end", "When the cache still has free place, the entry is added at the end, and the counter incremented", "If the entry key is a duplicate, it replaces the old one without refreshing it". — [cache_dsl_test.exs](https://raw.githubusercontent.com/alfert/propcheck/master/test/cache_dsl_test.exs)
- Hypothesis docs: the worked example is explicitly a comparison against a *simplified* in-memory model: "An example database maps keys to sets of values, and in this test we compare one implementation of it to a simplified in memory model of its behaviour, which just stores the same values in a Python `dict`. The test then runs operations against both the real database and the in-memory representation of it and looks for discrepancies in their behaviour." Model code: `self.model = defaultdict(set)`. — [Hypothesis stateful.rst (6.100.0)](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst)
- Hypothesis `RuleBasedStateMachine` docstring: "The idea is that a state machine carries the system under test and some supporting data. This data can be stored in instance variables or divided into Bundles. The state machine has a set of rules which may read data from bundles (or just from normal strategies), push data onto bundles, change the state of the machine, or verify properties. At any given point a random applicable rule will be executed." — [stateful.py (6.100.0)](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/src/hypothesis/stateful.py)
- Hypothesis docs downplay formality: "Both of these names are somewhat misleading: You don't really need any sort of formal model of your code to use this, and it can be just as useful for pure APIs that don't involve any state as it is for stateful ones." — [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst)
- qsm README: "We now have an implementation, the next step is to define a model for the implementation to be tested against. We'll use a simple map between references and integers as a model. `newtype Model r = Model [(Reference (Opaque (IORef Int)) r, Int)]`". The "How it works" list asks the user for "a datatype model" and "a state transition function that given a model and an action advances the model to its next state". — [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)
- qsm Bookstore example (port of Hébert's bookstore case study): model is `newtype Model r = Model [(Isbn, Book)]` with `initModel = Model []`; the file header says "Based on Bookstore case study from: https://propertesting.com/book_case_study_stateful_properties_with_a_bookstore.html". — [Bookstore.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/test/Bookstore.hs)
- fast-check docs, the most explicit anti-mirroring warning of any tool: "With model-based testing, we compare our system to a highly simplified version of it: the model." And: ":::warning[The model, a simplified version of the system] Although the model can be a useful tool, it's important to use it carefully. Model's goal is to simplify the system, but there is a risk that it may mimic the system too closely, leading to errors. The model should not be a carbon copy of the system but a simplified representation of it. It's crucial to avoid testing the code by comparing it to itself." — [fast-check model-based-testing.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md)
- fast-check also says the model is optional: ":::info[The model, an optional helper] While the model part can assist you in writing your tests by storing intermediate states, past actions, or even mimicking the system, it is entirely optional. Model-based testing can be performed without it as well." And its example: "Model based testing requires a model. A model is a simplified version of the real system. In this precise case our model would contain only a single integer representing the size of the list. `type Model = { num: number };`" — [same](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md)
- fast-check `ICommand` docstring describes the model parameter as "Model, simplified or schematic representation of real system". — [ICommand.ts](https://raw.githubusercontent.com/dubzzz/fast-check/main/packages/fast-check/src/check/model/command/ICommand.ts)
- proptest-state-machine: "The reference state machine's state type. This should contain the minimum required information needed to implement the state machine. It is used to drive the generations of transitions to decide which transitions are valid for the current state." — [strategy.rs](https://raw.githubusercontent.com/proptest-rs/proptest/main/proptest-state-machine/src/strategy.rs)
- jqwik's new (1.7.0+) approach has **no separate model at all**: actions are `Transformer<S>` functions on the SUT state `S` itself, and "a transformer will not only invoke the transformation but will often check the correct state changes and postcondition(s) as well." Postconditions are relational, computed from before/after observations of the SUT (e.g. `int sizeBefore = stack.size(); stack.push(element); assertThat(stack.size()).isEqualTo(sizeBefore + 1);`). — [jqwik stateful-testing.md](https://raw.githubusercontent.com/jqwik-team/jqwik/main/documentation/src/docs/include/stateful-testing.md)
- Quickstrom has no model state either: "In Quickstrom, the intended behavior of a web application is described in a specification language called *Specstrom*. It's a propositional temporal logic with a functional expression language." State is read from the DOM via selectors; "A powerful way of writing specifications is by expressing them as state machines. A transition is expressed as an assertion about the current state and another assertion about the next state. The state machine proposition says that one of the transitions are always taken." — [Quickstrom specification-language.rst](https://raw.githubusercontent.com/quickstrom/quickstrom/main/docs/source/topics/specification-language.rst)

### Inferences
- The consensus "model" in the Erlang/Haskell lineage is a plain functional data structure over *observable* facts (what was created in this test, what is owned by whom), never a copy of the SUT's internal algorithms. The PropEr tutorial's password passage is the canonical argument: if you look inside to copy the algorithm, "we would be copying and not actually testing".
- jqwik and Quickstrom show a second school: no model at all, only relational pre/post assertions over the SUT's own observable state or a temporal-logic spec over observations. This is relevant for a StreamData runner: a "model" can legitimately be trivial or absent when the postconditions are relational.

### Gaps
- Fred Hébert's book prose ("model should be simpler than the system", "sketchy model", how the cache/bookstore models deliberately ignore details) could not be fetched: `propertesting.com` (and `pragprog.com`, `ferd.ca`, archive.org) are blocked. The only Hébert-derived material reachable is PropCheck's and qsm's *ports of his code* (cited above), which show the resulting models (a list of `{key, value}` pairs for the cache; `[(Isbn, Book)]` for the bookstore) but not his commentary.
- Quviq's eqc_statem documentation (quviq.com) is blocked; Andrew Stone's eqc_statem notes gist could not be extracted (raw gist host blocked, HTML did not include the content in a parseable form). No Quviq prose about model abstraction could be quoted.

## Key question 2: Which postcondition styles do the authors recommend? (exact value vs relation/invariant vs set-of-allowed vs lockstep)

### Takeaway
All tools support exact-value postconditions ("the result equals what the model says") and most examples use them, but the PropEr tutorial's actual postconditions are mostly *relational membership checks* (`lists:member(Movie, Result)`, `not lists:member(Result, S#state.users)`) and the qsm Bookstore port uses `Forall rs (...)` quantified checks; qsm's Lockstep style is a reference-implementation ("mock") comparison; fast-check and jqwik mix relational assertions on the SUT with model comparisons. None of the fetched docs describe an explicit "result is in a set the model allows" API; nondeterminism is handled implicitly by writing weaker postconditions.

### Cited Findings
- PropEr `postcondition/3` contract: "Specifies the postcondition that should hold about the result `Res` of performing `Call`, given the dynamic state `S` of the abstract state machine prior to command execution. This function is called during runtime, this is why the state is dynamic." — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- PropEr tutorial postconditions, mostly relational: "When creating an account, a _new_ password is always returned. `postcondition(S, {call,_,create_account,[_Name]}, Result) -> not lists:member(Result, S#state.users);`" … "When someone asks for a movie, then if it's available it's added to her list, otherwise not. `postcondition(S, {call,_,rent_dvd,[_Password,Movie]}, Result) -> case is_available(Movie, S) of true -> lists:member(Movie, Result); false -> not lists:member(Movie, Result) end;`" … "When someone returns a dvd, then it's no longer in her list. `postcondition(_S, {call,_,return_dvd,[_Password,Movie]}, Result) -> not lists:member(Movie, Result);`". Exact-value ones: `Result =:= account_deleted`, `Result =:= bon_appetit`. — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial: a postcondition can branch on the *pre*-state to allow several legal outcomes: "`postcondition(S, {call, _, delete_account, [Password]}, Result) -> case proplists:is_defined(Password, S#state.rented) of false -> Result =:= account_deleted; true -> Result =:= return_movies_first end;`" with the warning "Keep in mind that when changing postconditions, we might also need to change the `next_state/3` callback." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr FSM tutorial: postconditions are per (from-state, call) and the property name is an invariant-like claim ("the creature never runs out of food in the storage"); a failing run shows `State: {grapes_day,{storage,4,8,-1}} Result: {postcondition,false}` and the author notes "the content of the `State` variable reveals that the quantity of available food starts getting negative values." — [FSM tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_finite_state_machines.md)
- PropCheck ModelDSL (Hébert's cache) uses exact lookup in the model: "`def post(entries, [key], call_result) do case List.keyfind(entries, key, 0, false) do false -> call_result == {:error, :not_found}; {^key, val} -> call_result == {:ok, val} end end`" described as "checking that after calling the system in phase 2, the system is in the expected state compared the model." Default `post` "always returns true". — [model_dsl.ex](https://raw.githubusercontent.com/alfert/propcheck/master/lib/statem/model_dsl.ex)
- Hypothesis example: comparison rule as a *rule* rather than a per-command postcondition: "`@rule(k=keys) def values_agree(self, k): assert set(self.database.fetch(k)) == self.model[k]`" — "`values_agree` then checks that the contents of the database agrees with the model for a particular key." — [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst)
- qsm README postconditions: exact for reads, `Top` (trivially true) for writes: "`postcondition (Model m) cmd resp = case (cmd, resp) of (Create, Created ref) -> m' ! ref .== 0 .// "Create" where Model m' = transition (Model m) cmd resp; (Read ref, ReadValue v) -> v .== m ! ref .// "Read"; (Write _ref _x, Written) -> Top; (Increment _ref, Incremented) -> Top`". Note `postcondition :: model Concrete -> cmd Concrete -> resp Concrete -> Logic` returns a `Logic` value that annotates failures (`.//`), and the failing output shows `PostconditionFailed "AnnotateC \"Read\" (PredicateC (6 :/= 5))"`. — [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md); [Types.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/src/Test/StateMachine/Types.hs)
- qsm Bookstore port: quantified/relational postconditions for searches: "`FindByAuthor Exist x -> case resp of Rows rs -> Forall rs (Boolean . isInfixOf x . author) .&& Forall rs (\b -> Just b .== lookup (Isbn $ isbn b) m)`" i.e. every returned row matches the query and is in the model (not an exact list equality). — [Bookstore.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/test/Bookstore.hs)
- qsm Lockstep (reference-implementation style): `Test.StateMachine.Lockstep.Simple` header: "State machine test — This captures the design patterns sketched in <https://well-typed.com/blog/2019/01/qsm-in-depth/> for the case where there is exactly one real handle." Types: "The type of the real handle in the system under test" vs "The type of the mock handle"; commands are "`Cmd t (RealHandle t)  -- for the system under test` / `Cmd t (MockHandle t)  -- for the mock`" and responses likewise. The N-ary variant maintains "Relation between real and mock references for /all/ handle types" and its event translation notes "we maintain a mapping between references and mock handles in the model ... We can therefore apply this mapping, and re-compute the mock response." — [Lockstep/Simple.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/src/Test/StateMachine/Lockstep/Simple.hs); [Lockstep/NAry.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/src/Test/StateMachine/Lockstep/NAry.hs)
- qsm `mock` (the reference implementation inside the model): "Finally, we show how to mock responses given a model. `mock (Model m) cmd = case cmd of Create -> Created <$> genSym; Read ref -> ReadValue <$> pure (m ! ref); Write _ _ -> pure Written; Increment _ -> pure Incremented`" and "`mock` *must* provide responses that will make the model advance *on par* with the implementation. Note that as responses might define fields which are expected to be used only by `postcondition`, those might be filled with dummy values in `mock` as the `postcondition` is called only with the `Concrete` response from the implementation." — [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)
- fast-check: postconditions live inside `run`: "`run(m: Model, r: RealSystem): void`: execute the command on the system and update the model accordingly. Check for potential problems or inconsistencies between the model and the real system - throws in such case." Example mixes a type-level relational check (`assert.equal(typeof r.pop(), 'number')`) with an exact model comparison (`assert.equal(r.size(), m.num)`). `ICommand.run` docstring: "Receive the non-updated model and the real or system under test. Perform the checks post-execution - Throw in case of invalid state. Update the model accordingly". — [model-based-testing.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md); [ICommand.ts](https://raw.githubusercontent.com/dubzzz/fast-check/main/packages/fast-check/src/check/model/command/ICommand.ts)
- proptest-state-machine: "Apply a transition in the SUT state and check post-conditions. The post-conditions are properties of your state machine that you want to assert. Note that the `ref_state` is the state *after* this `transition` is applied. You can use it to compare it with your SUT after you apply the transition." (Note: the opposite convention to PropEr, which passes the state *before*.) — [test_runner.rs](https://raw.githubusercontent.com/proptest-rs/proptest/main/proptest-state-machine/src/test_runner.rs)
- jqwik: purely relational postconditions over the SUT (no model): push: "The string should be on top afterwards and the size should have increased by 1."; pop: "If (and only if) the stack is not empty, pop the element on top off the stack. The size of the stack should have decreased by 1."; and the "_fundamental property of stateful systems_: > For any valid sequence of actions all required state changes (aka postconditions) should be fulfilled." — [jqwik stateful-testing.md](https://raw.githubusercontent.com/jqwik-team/jqwik/main/documentation/src/docs/include/stateful-testing.md)
- Quickstrom: temporal formulas over consecutive observed states; `unchanged` is the framing device for "everything else stays the same": "The formula `unchanged p` says that `p` in the current state is equal to `p` in the next state... This operator is useful when expressing state transitions, specifying that a certain queried value should be the same both before and after a particular transition." — [specification-language.rst](https://raw.githubusercontent.com/quickstrom/quickstrom/main/docs/source/topics/specification-language.rst)

### Inferences
- The authors' practice (vs. their API) leans relational: PropEr's tutorial checks membership/non-membership rather than reconstructing the full returned list; qsm's Bookstore uses `Forall`. This is how models stay simpler than the SUT: they only need enough state to decide the *predicate*, not to reproduce the exact output.
- Lockstep/mock is the one place a model *is* a reference implementation; qsm documents it as a separate design pattern with a real/mock handle mapping, not the default.
- No fetched doc exposes a "set of allowed results" primitive; nondeterminism is encoded by weakening postconditions (PropEr's `case is_available(...)`), by `Top`, or by invariants.

### Gaps
- Edsko de Vries's qsm blog ("An in-depth look at quickcheck-state-machine", well-typed.com 2019-01-23), which is the primary prose for the Lockstep/mock design and the "model as a mock file system" idea, is blocked (also on iohk.io/iog.io mirrors). Only the Haskell module headers that cite it are quoted.
- Hébert's "negative testing" and nondeterminism guidance (book chapter) could not be fetched.

## Key question 3: How are run-time-created values handled (symbolic variables, Bundles, references) and why does it matter for shrinking?

### Takeaway
PropEr/PropCheck/qsm bind each command's result to a symbolic variable at generation time and substitute real values at run time; the authors say this is what makes generation side-effect-free and therefore shrinking repeatable, and PropEr warns you must never pattern-match or compute on a symbolic result in `next_state` except via symbolic calls. Hypothesis solves the same problem with Bundles (named collections populated by rule return values, with `consumes` to remove); fast-check instead advises indexing into model-held collections (`trackPosition % allTracks.length`) so a command stays valid regardless of history; proptest-state-machine has no reference mechanism in the docs read.

### Cited Findings
- PropEr on why symbolic: "Symbolic representation has several benefits, which are listed here in increasing order of importance: Generated testcases are easier to read and understand. Failing testcases are easier to shrink. The generation phase is side-effect free and this results in repeatable testcases, which is essential for correct shrinking." "Since the actual results of symbolic calls are not known at generation time, we use symbolic variables (`symbolic_var()`) to refer to them. A command (`command()`) is a symbolic term, used to bind a symbolic variable to the result of a symbolic call." ### Inferences
- Two viable designs for an Elixir/StreamData runner: (a) PropEr-style `{:var, n}` placeholders substituted at run time (requires that the model's `next_state` be written to work on opaque terms — PropEr's `hd/1` caveat); (b) Hypothesis-style Bundles/indices, which avoid symbolic terms in the model but make preconditions unable to see the bundle contents (a limitation Hypothesis documents). fast-check's "index modulo length" trick is a third, cheaper approach that keeps every generated command valid under deletion-based shrinking.
- All three approaches exist precisely so that *deleting* earlier commands during shrinking does not produce dangling references.

- MacIver's blog explanation of why Bundles were introduced and why shrinking is better with rules (hypothesis.works) is blocked; only the changelog and reference docs could be quoted.

## Key question 4: Generation — state-dependent command generation vs flat lists with runtime precondition skipping; what do authors say about shrinking quality and the cost of skipped commands?

### Takeaway
PropEr, PropCheck, qsm and proptest-state-machine generate each command from the *current symbolic model state* and re-check preconditions during shrinking; Hypothesis chooses "a random applicable rule" (filtering by precondition before running); fast-check is the one tool that generates a flat list and *skips* commands whose `check(model)` fails at run time, and it deals with the cost by shrinking only the commands that actually executed and by using a dedicated `commands` shrinker. PropEr explicitly warns that strict preconditions make generation expensive (`cant_generate`) and skew coverage, and that preconditions are what keep shrinking sound.

### Cited Findings
- PropEr `command/1`: "Generates a symbolic call to be included in the command sequence, given the current state `S` of the abstract state machine. However, before the call is actually included, a precondition is checked. This function will be repeatedly called to produce the next call to be included in the test case." `precondition/2`: "In case precondition doesn't hold, a new call is chosen using the `command/1` generator. If preconditions are very strict, it will take a lot of tries for PropEr to randomly choose a valid command. Testing will be stopped if the `constraint_tries` limit is reached ... and a `{cant_generate,[{proper_statem,commands,4}]}` error will be produced in that case." — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- PropEr on preconditions and shrinking: "Preconditions are also important for correct shrinking of failing testcases. When shrinking command sequences, we try to eliminate commands that do not contribute to failure, ensuring that all preconditions still hold. Validating preconditions is necessary because during shrinking we usually attempt to perform a call with the system being in a state different from the state it was when initially running the test." — [same](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- PropEr tutorial: the idiom for state-dependent generation is list comprehension guards: "`command(S) -> HasUsers = (S#state.users =/= []), oneof([{call,?SERVER,create_account,[name()]}, {call,?SERVER,ask_for_popcorn,[]}] ++ [{call,?SERVER,delete_account,[password(S)]} || HasUsers] ++ ...`" and later `frequency/1` with weights 1/1/1/5/5 plus `?LET({Password,Movie}, elements(S#state.rented), {call,?SERVER,return_dvd,[Password, Movie]})`. ### Inferences
- The flat-list-plus-skip approach (fast-check) is production-proven but its author treats skipped commands as a real cost: the shrinker must be told which commands ran, and replay needs an extra path. In state-driven designs (PropEr/qsm/ptsm) the equivalent cost appears instead as generation retries (`cant_generate`, "global rejection filtering") and as coverage skew that must be corrected with weights.
- Across tools the two uses of preconditions are distinct: (1) during generation to pick legal commands, (2) during shrinking to re-validate a subsequence under a *different* model state. ptsm states the minimal rule: preconditions need only cover state-dependent validity "that may be broken by shrinking".
- Hypothesis's history (GenericStateMachine → RuleBasedStateMachine) is direct evidence that an API where the user writes an arbitrary `steps(state)` generator shrinks worse than a fixed rule set with preconditions.

- No fetched document quantifies the shrink-quality difference between flat-list-skip and state-driven generation.

## Key question 5: Invariants checked after every step vs postconditions per command

### Takeaway
Hypothesis (`@invariant`), qsm (`invariant :: Maybe (model Concrete -> Logic)`), proptest-state-machine (`check_invariants`) and jqwik (`withInvariant`) all provide a hook run after every step in addition to per-command postconditions; PropEr/PropCheck have no invariant callback and express global properties through postconditions (or through FSM-level property naming). Hypothesis's stated reason is that an invariant written as a rule "would be run zero or multiple times between other rules".

### Cited Findings
- Hypothesis: "Often there are invariants that you want to ensure are met after every step in a process. It would be possible to add these as rules that are run, but they would be run zero or multiple times between other rules. Hypothesis provides a decorator that marks a function to be run after every step." Example: `@invariant() def divide_with_one(self): assert self.num % 2 == 0`. "Invariants can also have `precondition`s applied to them, in which case they will only be run if the precondition function returns true. Note that currently invariants can't access bundles". Docstring: "The decorated function will be run after every rule and can raise an exception to indicate failed invariants... By default, invariants are only checked after all `@initialize()` rules have been run. Pass `check_during_init=True` for invariants which can also be checked during initialization." — [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst); [stateful.py](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/src/hypothesis/stateful.py)
- qsm `StateMachine` record has `invariant :: Maybe (model Concrete -> Logic)` alongside `postcondition`; the README example passes `Nothing`; the parallel diagram labels the prefix as "pre/postconditions and invariant checked, executed sequentially". — [Types.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/src/Test/StateMachine/Types.hs); [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)
- proptest-state-machine `StateMachineTest::check_invariants`: "Check some invariant on the SUT state after every transition. Note that just like in `StateMachineTest::apply` you can use the `ref_state` to compare it with your SUT." — [test_runner.rs](https://raw.githubusercontent.com/proptest-rs/proptest/main/proptest-state-machine/src/test_runner.rs)
- jqwik: "We can also add invariants to our sequence checking property: `chain.withInvariant("greater", stack -> assertThat(stack.size()).isGreaterThanOrEqualTo(0)).withInvariant("less", stack -> assertThat(stack.size()).isLessThan(5)) // Does not hold! .run();`" with the failure report "Invariant 'less' failed after the following actions: [...]". "Also, state machines can have invariants that should never be violated regardless of the sequence of performed actions." — [jqwik stateful-testing.md](https://raw.githubusercontent.com/jqwik-team/jqwik/main/documentation/src/docs/include/stateful-testing.md)
- PropEr: only `postcondition/3` (and `postcondition/5` in `proper_fsm`); no invariant callback is listed among "The callback functions" in either module doc. — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl); [proper_fsm.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_fsm.erl)
- Quickstrom: `always` is the invariant operator: "The formula `always p` says that the formula `p` is true in the current and all subsequent states. As an example, in the following proposition we check that the heading is always `"Home"`". — [specification-language.rst](https://raw.githubusercontent.com/quickstrom/quickstrom/main/docs/source/topics/specification-language.rst)

### Inferences
- An invariant hook costs nothing in model design and removes the temptation to duplicate a global check into every postcondition; the tools that lack it (PropEr family) force users to encode invariants into `postcondition` or into the property's final-state check.

### Gaps
- None material beyond the blocked prose sources.

## Key question 6: Pitfalls the docs warn about (mirroring, over-specification, nondeterminism, timing, too-strict preconditions, etc.)

### Takeaway
Documented pitfalls are: models that mimic the SUT too closely (fast-check), pattern-matching on symbolic results (PropEr), non-deterministic `initial_state` (PropEr/PropCheck), too-strict preconditions causing `cant_generate`/rejection slowdowns and coverage skew (PropEr, ptsm, Hypothesis on `assume`), ambiguous FSM transitions (PropEr `too_many_targets`), tests that are not self-contained/cleaned up (PropEr), the Erlang scheduler being too deterministic for parallel tests (PropEr), the parallel model needing to be sequentially correct first (qsm), and the fast-check `check`/`run` not depending on other scheduled tasks.

### Cited Findings
- Mirroring: fast-check: "there is a risk that it may mimic the system too closely, leading to errors. The model should not be a carbon copy of the system but a simplified representation of it. It's crucial to avoid testing the code by comparing it to itself." — [model-based-testing.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md)
- Copying the algorithm: PropEr tutorial: "in this way we would be copying and not actually testing how passwords are created." — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- Symbolic-result misuse: "pattern matching on the result `V` of the call should be avoided. Moreover, any information has to be extracted in a symbolic way". — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- Non-deterministic initial state: "`initial_state/0` ... should be deterministic and self-contained." (PropEr); "It doesn't accept any arguments, because this function has to be deterministic." (PropCheck). — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl); [model_dsl.ex](https://raw.githubusercontent.com/alfert/propcheck/master/lib/statem/model_dsl.ex)
- Non-self-contained tests / cleanup: "When testing impure code, it is very important to keep each test self-contained. For this reason, almost every property for testing stateful systems contains some clean-up code. Such code is necessary to put the system in a known state, so that the next test can be executed independently from previous ones." Hypothesis has `teardown`: "Called after a run has finished executing to clean up any necessary state." qsm has `cleanup :: model Concrete -> m ()`. — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl); [stateful.py](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/src/hypothesis/stateful.py); [Types.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/src/Test/StateMachine/Types.hs)
- Too-strict preconditions: PropEr `cant_generate` (quoted in Q4); FSM tutorial on `?SUCHTHAT`: "Error: Couldn't produce an instance that satisfies all strict constraints after 50 tries. {error,cant_generate}" with the fix "modify the generator that is responsible for this error" rather than raising `constraint_tries`; ptsm: "pre-conditions that are hard to satisfy might slow down the test or even fail by exceeding the maximum rejection count"; Hypothesis on `assume`: "you can quickly run into a situation where few or none of your rules pass their assumptions." — [FSM tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_finite_state_machines.md); [strategy.rs](https://raw.githubusercontent.com/proptest-rs/proptest/main/proptest-state-machine/src/strategy.rs); [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst)
- Coverage skew from preconditions and the need to measure: PropEr tutorial's `aggregate(command_names(Cmds), ...)` revealing `1.32% return_dvd`; FSM tutorial: "We cannot be sure of what was tested unless we have a look at the testcase distribution." and "It seems that the creature doesn't get hungry very often in our tests. Thus, our previous conclusion about everlasting food supplies cannot be really trusted." — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md); [FSM tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_finite_state_machines.md)
- Ambiguous transitions (FSM): "It is possible for more than one transitions to be triggered by the same symbolic call and lead to different target states. In this case, at most one of the target states may have a true precondition. Otherwise, PropEr will not be able to detect which transition was chosen and an exception will be raised." (`too_many_targets`). — [proper_fsm.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_fsm.erl)
- Model/postcondition coupling: "Keep in mind that when changing postconditions, we might also need to change the `next_state/3` callback." — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- Crashing SUT swallowing diagnostics: "What is not acceptable is that PropEr also crashes without providing any kind of useful information about the cause of the failure... Enclosing a property in `?TRAPEXIT` prevents PropEr from crashing when a linked process dies abnormally." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- Timing/scheduling in parallel tests: PropEr: "the actual interleaving of commands of the parallel component depends on the Erlang scheduler, which is too deterministic. For PropEr to be able to detect race conditions, the code of the system under test should be instrumented with `erlang:yield/0` calls to the scheduler." qsm: "As we cannot control the actual scheduling of the tasks, each sequence of commands ... is actually executed several times by default... One can further increase entropy by introducing random `threadDelay`s in the semantic function." — [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl); [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)
- Parallel testing requires a sequentially-correct model: "Despite the system under test running in a concurrent way, the model can still be designed to work sequentially as *it will not be run in parallel*, it will only be advanced in a sequential way when evaluating possible interleavings. This particularly means that the model must be correct with respect to sequential execution before used in parallel testing." PropEr likewise: "After ensuring that a system's behaviour can be described via an abstract state machine when commands are executed sequentially, it is possible to move to parallel testing." — [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md); [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- Linearizability check as the parallel oracle: PropEr: "PropEr uses the state machine specification to check if the results observed could have been produced by a possible serialization of the parallel component. If no such serialization is possible, then an atomicity violation has been detected." qsm: "try to find a possible sequential interleaving of action invocations and responses that respects the post-conditions... The last two steps basically try to find a linearisation of calls that could have happend on a single thread." — [same two sources]
- fast-check async/scheduled pitfalls: ":::warning[Do not depend on other scheduled tasks in the model] Neither `check` nor `run` should rely on the completion of other scheduled tasks to fulfill themselves. But they can still trigger new scheduled tasks as long as they don't wait for them to resolve." — [race-conditions.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/race-conditions.md)
- Hidden bugs needing longer sequences: PropCheck: "Sometimes issues can hide when the command sequences are short. In order to tease out these hidden bugs we can increase the number of commands generated by using the `max_size` option". PropEr: targeted testing for rare sequences: "there may be some failing command sequences that the random property based testing does not find with ease, or at all. In these cases, stateful targeted property based testing can help find such edge cases, provided a utility value." — [statem_dsl.ex](https://raw.githubusercontent.com/alfert/propcheck/master/lib/statem_dsl.ex); [proper_statem.erl](https://raw.githubusercontent.com/proper-testing/proper/master/src/proper_statem.erl)
- Readability of counterexamples: Hypothesis: "The output from a rule based state machine should generally be pretty close to Python code - if you have custom `repr` implementations that don't return valid Python then it might not be". fast-check: print resolved names via `toString()` ("you would certainly prefer to see "go to track 'the super track'" instead of "go to track 1200""). qsm prints model diffs between steps ("notice how the diff of the model is displayed between each action"). — [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst); [model-based-testing.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md); [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)

### Inferences
- The tutorial-style sources treat model bugs as the normal first failure mode and iterate model → precondition → postcondition; a runner should therefore make the History/State/Result triple visible on failure (PropEr's `?WHENFAIL` pattern, Hypothesis's generated program, qsm's model diff).

### Gaps
- No fetched primary source discusses "flaky settle/timing" for asynchronous *sequential* systems (e.g. waiting for a GenServer cast to apply) beyond the parallel-scheduling notes above.

## Key question 7: Negative testing and "the model as a specification of the API protocol" (which calls are legal when)

### Takeaway
The PropEr tutorial demonstrates both approaches and presents the choice explicitly: either forbid an illegal call with a precondition (protocol spec; used for a crashing `return_dvd`) or allow it and encode the expected error in the postcondition and `next_state` (negative testing; used for `delete_account` with outstanding rentals). qsm's Bookstore port makes negative cases first-class by tagging each command `Invalid|Exist|Avail|Unavail|Taken|Full` with matching preconditions and exact error postconditions; Hypothesis's docs frame preconditions as "a valid step"; fast-check's `check` is the protocol.

### Cited Findings
- PropEr tutorial, option 1 (precondition = protocol) for a crash: "This happened because the `inception` movie was never available at the dvd-club. In real life, we can be certain that nobody will ever return a movie that they didn't rent in advance. However, in a production system there is always the possibility that an unlikely sequence of events might actually happen. For this reason, it's not a good idea to let our server crash and we shall fix the code later. For the moment, we are interested in discovering more bugs. So, we add a precondition that doesn't let this situation happen. `precondition(S, {call,_,return_dvd,[Password,Movie]}) -> lists:member({Password,Movie}, S#state.rented);`" Later: "Now that tests seem to pass, we will temporarily remove the first precondition that we introduced and correct our code to prevent the server from crashing." — [PropEr statem tutorial](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial, option 2 (negative testing via postcondition): "The server replied `return_movies_first`, but our model did not account for this. There are two options to deal with this inconsistency: 1. Add a precondition that prevents users from deleting an account before returning all dvds. 2. Change our postcondition to account for these annoying clients. Since this kind of users might exist in practice, we decide to change the postcondition." — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- PropEr tutorial, deliberately generating invalid inputs: the movie generator includes titles the shop never stocks — "apart from the movies available, clients will also ask for titanic and inception, in order to test how the server responds to these requests" — while passwords are restricted to valid ones with the explicit alternative noted: "(Alternatively, we can possibly define the frequency that invalid passwords may appear in our tests. The choice depends on what we are interested in testing.) Being interested only in valid passwords, we define: `password(#state{users = Passwords}) -> elements(Passwords).`" And a third precondition for a legal-but-unmodelled case: "Mary wants to rent another copy of the same movie, but there are no more copies available. In this case the postcondition for `rent_dvd/2` is false. Again, it is up to us to redefine our model and we decide to add a precondition that prevents the aforementioned scenario. `precondition(S, {call,_,rent_dvd,[Password,Movie]}) -> not lists:member({Password,Movie}, S#state.rented) andalso lists:member(Password, S#state.users);`" — [same](https://raw.githubusercontent.com/proper-testing/proper-testing.github.io/master/tutorials/PropEr_testing_of_generic_servers.md)
- qsm Bookstore port (Hébert's case study): negative cases are generated on purpose and pinned by preconditions: "`AddCopy Invalid key -> Not $ hasKey key`, `NewBook Exist key _ _ -> hasKey key`, `Borrow Unavail key -> keyPred key (\b -> avail b .== 0)`, `Return Full key -> keyPred key (\b -> owned b .== avail b)`", with postconditions "`NewBook Exist _ _ _ -> resp .== UniqueError`, `AddCopy Invalid _ -> resp .== NotFound`, `Borrow Unavail _ -> resp .== NotFound`, `FindByIsbn Invalid _ -> resp .== Rows []`"; transitions ignore failed operations (`_ -> m`). — [Bookstore.hs](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/test/Bookstore.hs)
- PropCheck cache port: a protocol-style precondition that exists only to avoid redundant work, not illegality: "# pre condition: do not call flush() twice `def pre(%__MODULE__{count: c}, _args), do: c != 0`". — [cache_dsl_test.exs](https://raw.githubusercontent.com/alfert/propcheck/master/test/cache_dsl_test.exs)
- qsm README: "The pre-condition of an action specifies in what context the action is well-defined. For example, we can always create a new mutable reference, but we can only read from references that already have been created." — [qsm README](https://raw.githubusercontent.com/stevana/quickcheck-state-machine/master/README.md)
- Hypothesis: `precondition` "Specifies a precondition for a rule to be considered as a valid step in the state machine". Initialization-as-protocol: "Initializes can also allow you to initialize the system under test in a way that depends on values chosen from a strategy. You could do this by putting an instance variable in the state machine that indicates whether the system under test has been initialized or not, and then using preconditions (below) to ensure that exactly one of the rules that initialize it get run before any rules that depend on it being initialized." — [stateful.py](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/src/hypothesis/stateful.py); [stateful.rst](https://raw.githubusercontent.com/HypothesisWorks/hypothesis/hypothesis-python-6.100.0/hypothesis-python/docs/stateful.rst)
- fast-check: `check` encodes protocol ("should not call pop on empty list `return m.num > 0;`"). — [model-based-testing.md](https://raw.githubusercontent.com/dubzzz/fast-check/main/website/docs/advanced/model-based-testing.md)
- jqwik: "Some actions have preconditions to constrain when they can be invoked." pop: `Action.<MyStringStack>when(stack -> !stack.isEmpty())`. — [jqwik stateful-testing.md](https://raw.githubusercontent.com/jqwik-team/jqwik/main/documentation/src/docs/include/stateful-testing.md)
- Quickstrom: preconditions are mostly built in; "It's more likely that preconditions will be domain-specific rules, if required at all." Event postconditions: "a DOM element might have changed, but only if it's changed in a certain way we considered it a specific event." — [specification-language.rst](https://raw.githubusercontent.com/quickstrom/quickstrom/main/docs/source/topics/specification-language.rst)

### Inferences
- The PropEr tutorial's two-option rule is the operative design guidance: precondition when the call is *illegal/undefined* (or temporarily, to keep hunting other bugs), postcondition when the call is *legal but has an error outcome*. The Bookstore tagging pattern is the mature form: generate negatives deliberately, pin them with preconditions so shrinking can't turn a negative into a positive, and assert exact error responses.
- For a StreamData runner, this argues for letting a command carry a generation-time "intent tag" that preconditions re-validate during shrinking.

### Gaps
- Hébert's own prose on negative testing (book chapter and bookstore case study) could not be fetched; only the Haskell port of the resulting spec is available.
