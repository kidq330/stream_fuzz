## Key Question 1: What kinds of properties find bugs?

### Takeaway
Hughes's controlled experiment (BST with 8 planted bugs, 48 properties) found that validity/invariant properties miss most bugs, postconditions and metamorphic properties each eventually catch every bug but only in aggregate (metamorphic ones individually leaky and slow), while **model-based properties—one per operation, comparing `toList(op(t))` to a list-level operation—found every bug with 5 properties and ~10× fewer tests** (mean 5.8 tests-to-failure vs 56 metamorphic vs 77 postcondition). Practitioner data agree: at Jane Street "differential/model-based" properties were "by far the most widely implemented kind of property" (17/30 interviewees), followed by round-trip (11/30), classical/invariant (11/30), and crash-only (7/30); the whole field's advice is to combine a cheap validity property (to catch bad generators) with a model-based or oracle property, falling back to metamorphic properties when a model is too costly.

### Cited Findings

**Hughes's five families (How to Specify It!, TFP 2019 / LNCS 12053, 2020). All quotes verbatim from Hughes's text as reproduced in Link's remix** — [Link remix](https://johanneslink.net/how-to-specify-it/) ([source](https://github.com/jlink/how-to-specify-it/blob/master/docs/README.md)); Hughes's original PDF: https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf (blocked for me).

- Abstract: "This tutorial paper presents five generic approaches to writing such specifications (for purely functional code). We discuss the costs, benefits, and bug-finding power of each approach, with reference to a simple example with eight buggy variants."
- Introduction names the problem: "We have found that many developers trying property-based testing for the first time find it difficult to identify *properties to write* — and find the simple examples in tutorials difficult to generalize. This is known as the *oracle problem* [3], and it is common to all approaches that use test case generation." The five approaches: "invariants, postconditions, metamorphic properties and the preservation of equivalence, inductive properties, and model-based properties".
- **Validity (invariants).** Slogan: "Every operation should return valid results." Summary: "*Validity testing consists of defining a function to check the invariants of your datatypes, writing properties to test that your generators and shrinkers only produce valid results, and writing a property for each function under test that performs a single random call, and checks that the return value is valid.*" Limits: "if every function returning a BST were defined to return `nil` in every case, then all the properties written so far would pass. `insert` could be defined to delete the key instead, or `union` could be defined to implement set difference — as long as the invariant is preserved, the properties will still pass."
- "Test your tests." On generator validity: "A property such as `arbitrary_valid` is essential to check that these definitions are mutually consistent." and "it is vital to test generators and shrinkers *independently* of the operations under test, because a bug in either can result in very many hard-to-debug failures in other properties."
- **Postconditions.** Slogan: "Postconditions relate return values to arguments of a single call." Method: "we can define properties by asking ourselves 'What should be *True* after calling *f*?'". Summary: "*A postcondition tests a single function, calling it with random arguments, and checking an expected relationship between its arguments and its result.*" The `find` postcondition dilemma: "in order to test `find`, we need to reimplement it." Resolution: "a very powerful and general idea, that of constructing a test case whose outcome is easy to predict. In this case, we know that a tree must contain a key `key`, if we have just inserted it." Caveat: "there is a risk, when we write properties in this form, that we are only testing very special cases" — hence the completeness property `insert_delete_complete`.
- **Metamorphic.** Slogan: "Related calls return related results." "A metamorphic property, like this one, (almost) always *relates two calls* to the function under test... Metamorphic testing is a fruitful source of property ideas, since if we are given O(n) operations to test, each of which can also be used as a modifier, then there are potentially O(n²) properties that we can define." Summary: "*A metamorphic property tests a single function by making (usually) two related calls, and checking the expected relationship between the two results.*" The need for an equivalence relation: "we should not care what shape of tree each operation returns, provided it contains the right information... We therefore define an equivalence relation on trees that is true if they have the same contents". Sixteen metamorphic properties were derived.
- **Inductive.** Slogan: "Inductive proofs inspire inductive tests." "in some cases, a subset of metamorphic properties *does* form a complete specification." Summary: "*Inductive properties relate a call of the function-under-test to calls with smaller arguments. A set of inductive properties covering all possible cases together test the base case(s) and induction step(s) of an inductive proof-of-correctness. If all the properties hold, then we know the function is correct – inductive properties together make up a complete test.*" Hidden assumption to test: "that any tree can be constructed using insertions only" → `insert_complete`, `insert_complete_for_delete`, `insert_complete_for_union`, which "also justify our choice of generator".
- **Model-based.** Slogan: "Abstract away from details to simplify properties." "In 1972, Hoare published an approach to proving the correctness of data representations [14], by relating them to abstract data using an abstraction function... In this case we abstract trees `t` (the concrete implementation) as ordered lists of key–value pairs `kvs` (the abstract data), using an abstraction function which is just `toList()`. The diagram says that both paths from top left to bottom right should yield the same result... If a similar diagram commutes for every operation in an API, then it follows that any sequence of concrete operations behaves in the same way as the same sequence of abstract ones." Summary: "*A model-based property tests a single function by making a single call, and comparing its result to the result of a related "abstract operation" applied to related abstract arguments. An abstraction functions maps the real, concrete arguments and results to abstract values, which we also call the "model".*"
- The actual model-based properties, verbatim Haskell from Hughes's repo ([BSTSpec.hs](https://github.com/rjmh/how-to-specify-it/blob/master/BSTSpec.hs)) — the whole "model" is `Data.List`:
  ```haskell
  prop_NilModel = toList (nil :: Tree) === []
  prop_InsertModel (k,v) t = toList (insert k v t) === L.insert (k,v) (deleteKey k $ toList t)
  prop_DeleteModel k t     = toList (delete k t)   === deleteKey k (toList t)
  prop_UnionModel t t'     = toList (union t t')   === L.sort (L.unionBy ((==) `on` fst) (toList t) (toList t'))
  prop_FindModel k t       = find k t              === L.lookup k (toList t)
  deleteKey k = filter ((/=k) . fst)
  ```
  Note the first attempt failed and had to be corrected: "The problem is that the insertion function in `java.util.List` may create duplicate elements, but `insert` for trees does not. So it is not quite the correct abstract implementation; we can correct this by deleting the key if it is initially present". (Hughes's original: `L.insert` on a sorted list, same correction.)
- Experiment scale (Hughes's repo README, verbatim): "a simple, but non-trivial example of code to test, an implementation of a finite map as a binary search tree (BST.hs, 66 non-comment non-blank lines of source code)"; "48 properties designed using the principles explained in the paper, of which two are duplicates"; "31 properties discovered automatically by QuickSpec... of which 11 duplicate hand-written properties"; "Eight buggy versions of the implementation (BST1..BST8.hs), with bugs ranging from the blatant to the somewhat-more-subtle"; "Some properties require almost 2,000 random tests to falsify them for some variants" — [rjmh/how-to-specify-it README](https://github.com/rjmh/how-to-specify-it/blob/master/README.txt).
- The eight bugs (Hughes, via Link): #1 "*insert* discards the existing tree, returning a single-node tree just containing the newly inserted value"; #2 "*insert* fails to recognize and update an existing key, inserting a duplicate entry instead"; #3 "*insert* fails to update an existing key, leaving the tree unchanged instead"; #4 "*delete* fails to rebuild the tree above the key being deleted, returning only the remainder of the tree from that point on (an easy mistake for those used to imperative programming to make)"; #5 "Key comparisons reversed in *delete*; only works correctly at the root of the tree"; #6 "*union* wrongly assumes that all the keys in the first argument precede those in the second"; #7 "*union* wrongly assumes that if the key at the root of `bst1` is smaller than the key at the root of `bst2`, then all the keys in `bst1` will be smaller than the key at the root of `bst2`"; #8 "*union* works correctly, except that when both trees contain the same key, the left argument does not always take priority." — [Link remix §5](https://johanneslink.net/how-to-specify-it/)
- **Which families caught which bugs** (Link's jqwik replication of Hughes's table; Link omitted #6/#7 because his `union` differed; `X` = both QuickCheck and jqwik caught it, `Ox` = QuickCheck only, `Xo` = jqwik only) — [Link remix §5](https://johanneslink.net/how-to-specify-it/):
  - Validity: `insert valid` X on #2; `union valid` X on #2; `arbitrary valid`/`delete valid` Ox on #2; nothing on #1,#3,#4,#5,#8.
  - Postconditions: `insert post` X #1,#2,#3; `delete post` Ox #2, Ox #4, X #5; `find post present` X #2,#3; `find post absent` Ox #2, X #5; `insert delete complete` X #2,#4; `union post` Xo #2, Xo #3, X #8.
  - Metamorphic: `insert insert weak` X #1 only; `insert insert` X #1,#2,#3; `insert delete weak` X #4 only; `insert delete` X #2,#3,#4; `delete insert` X #1,#2,#4,#5; `delete union` X #1,#2,#4,#5, Ox #8; `union delete insert` X #1–#5, Ox #8; `union union assoc` Ox #8 only; `find insert` X #1,#2,#3; `find delete` X #4,#5; `find union` Xo #1,#2, X #8; `delete nil`, `union nil1`, `union nil2`, `find nil`: nothing.
  - Preservation of equivalence: `insert preserves equivalence` nothing; `delete preserves equivalence` X #1,#4,#5; `union preserves equivalence` X #1, Ox #8; `find preserves equivalence` X #1.
  - Insert completeness: only `insert complete for union` Ox #1.
  - **Model-based: `insert model` X #1,#2,#3; `delete model` X #4,#5; `union model` X #1,#2, Xo #3, X #8; `nil model`/`find model` nothing (nothing to find).**
- Hughes's observations (§5.1, verbatim): "*Validity properties miss many bugs* (five of six), as do 'preservation of equivalence' and 'completeness of insertion' properties. In contrast, every bug is found by at least one postcondition, metamorphic property, and model-based property." (Caveat: "five of six" may be Link's edit for his 6-bug table; Hughes's original compares against eight bugs.) "*Invalid test data provokes false positives.* Bug #2, which causes invalid trees to be generated as test cases, causes many properties that do not use `insert` to fail. This is why property `arbitrary_valid` is so important — when it fails, we need not waste time debugging false positives in properties unrelated to the bug." "*Model-based properties are effective at finding bugs;* each property tests just one operation, and finds every bug in that operation. In fact, the model-based properties together form a complete specification of the code, and so should be expected to find every bug." "*Postconditions are quite effective;* each postcondition for a buggy operation finds all the bugs we planted in it, but some postconditions are less effective than we might expect. For example, property `find_post_present` uses both `find` and `insert`, so we might expect it to reveal the three bugs in `insert`, but it reveals only two of them." "*Metamorphic properties are less effective individually*, but powerful in combination. Weak properties miss bugs (compare each line ending in Weak with the line below), because their preconditions to exclude tricky test cases result in tricky bugs escaping detection... Degenerate metamorphic properties involving `nil` are particularly ineffective. Metamorphic properties are essentially an axiomatization of the API under test, and there is no guarantee that this axiomatization is complete, so some bugs might be missed altogether." — [Link remix §5.1](https://johanneslink.net/how-to-specify-it/)
- **Bug-finding speed** (§5.2, Link says this text is unchanged from Hughes): mean number of random tests to first failure, averaged over 7 bugs and all detecting properties of a type, each measured 1,000 times: Postcondition min 7.1 / max 245 / mean 77; Metamorphic 2.4 / 714 / 56; **Model-based 3.1 / 9.8 / 5.8.** "In this example model-based properties find bugs far faster than postconditions or metamorphic properties, while metamorphic properties find bugs a little faster than postconditions on average, but their mean time to failure varies more." Why: "for the same bug in `union`, `prop_UnionPost` fails after 50 tests on average, while `prop_UnionModel` fails after only 8.4 tests, *even though they are logically equivalent*. The reason is that after computing a union that is affected by the bug, the model-based property checks that the model of the result is correct — which requires every key and value to be correct. The post-condition, on the other hand, checks that a random key has the correct value in the result. Thus `prop_UnionPost` may exercise the bug many times without detecting it." — [Link remix §5.2](https://johanneslink.net/how-to-specify-it/)
- Lessons (§5.3, verbatim): "These results suggest that, if time is limited, then writing model-based properties may offer the best return on investment, in combination with validity properties to ensure we don't encounter confusing failures caused by invalid data. In situations where the model is complex (and thus expensive) to define, or where the model resembles the implementation so closely that the same bugs are likely in each, then metamorphic properties offer an effective alternative, at the cost of writing many more properties." — [Link remix §5.3](https://johanneslink.net/how-to-specify-it/)
- Discussion (§7): "Model-based testing seemed the most effective approach overall, revealing all our bugs with a small number of properties, and generally finding bugs fast. But metamorphic testing was a fertile source of ideas, and was almost as effective at revealing bugs, so is a useful alternative, especially in situations where a model is expensive to construct." Stateful code: "Test cases are sequences of operations, to set up the state for each operation under test, and to observe changes made to the state afterwards. Nevertheless, the same ideas can be adapted to this setting; in particular, there are a number of state-machine modelling libraries for property-based testing tools that support a 'model-based' approach in a stateful setting." — [Link remix §7](https://johanneslink.net/how-to-specify-it/)
- Test-data distribution matters for all families: with plain `Int` keys "*in almost 80% of tests, key is not found in the tree at all!*" (Hughes; Link measured 91% with jqwik); "'collisions' (that is, cases in which we randomly choose the same value in two places) can be important test cases... The choice of generator should be made on the basis of how important collisions are as test cases." — [Link remix §4.6](https://johanneslink.net/how-to-specify-it/)
- Link's addendum (his own words): his 11 TDD unit tests also detected each of the 6 bugs (failure counts 7/3/2/1/1/1) but "Those tests did *not* lead me to a bug-free implementation; the most serious error I had made was in the deletion code, in which full subtrees could sometimes get lost. So writing and running the properties definitely helped me weed out some of my blunders." — [Link remix, Personal Addendum](https://johanneslink.net/how-to-specify-it/)

**Wlaschin's seven patterns** (read in full from site source) — [Choosing properties for property-based testing](https://fsharpforfunandprofit.com/posts/property-based-testing-2/):
- "when it comes time to start creating your own properties, the universal complaint is: 'what properties should I use? I can't think of any!'"
- "Different paths, same destination" — "combining operations in different orders, but getting the same result... In category theory, this is called a *commutative diagram*."
- "There and back again" — "combining an operation with its inverse, ending up with the same value you started with... pairs such as `insert`/`contains`, `create`/`exists`, etc." even "though they are not strict inverses".
- "Some things never change" — "an invariant that is preserved after some transformation... Common invariants include size of a collection (for `map` say), the contents of a collection (for `sort` say), the height or depth of something in proportion to size (e.g. balanced trees)."
- "The more things change, the more they stay the same" — "'idempotence' -- that is, doing an operation twice is the same as doing it once... can be extended to things like database updates and message processing."
- "Solve a smaller problem first" — "'structural induction' -- that is, if a large thing can be broken into smaller parts, and some property is true for these smaller parts, then you can often prove that the property is true for a large thing as well."
- "Hard to prove, easy to verify" — "finding a route through a maze is hard, but checking that it works is trivial!... you might check that a string tokenizer works by just concatenating all the tokens again."
- "The test oracle" — "you often have an alternate version of an algorithm or process (a 'test oracle') that you can use to check your results... you might compare it with a brute force algorithm that is much slower but is also much easier to write correctly. Similarly, you might compare the result of a parallel or concurrent algorithm with the result of a linear, single thread version."
- Model-based testing defined as an oracle variant: "in parallel with your (complex) system under test, you create a simplified model. Then, when you do something to the system under test, you do the same (but simplified) thing to your model. At the end, you compare your model's state with the state of the system under test. If they are the same, you're done. If not, either your SUT is buggy or your model is wrong and you have to start over!"
- Part 3 on the "EDFH" (enemy developer from hell) and why weak properties still matter: "trivial but wrong implementations often satisfy the properties as well as good implementations... you should think of property-based testing not as a *testing* process, but as a *design* process -- a technique that helps you clarify what your system is really trying to do." Insertion sort as oracle for a fast sort: "A test oracle is simply an alternative implementation that gives the right answer... Often the test oracle implementation is not suitable for production -- it's too slow, or it doesn't parallelize". — [Choosing properties in practice, part 1](https://fsharpforfunandprofit.com/posts/property-based-testing-3/)
- Part 4, cross-checking two implementations of Roman numerals: "It's a great way to cross-check two different implementations when you're not sure that *either* implementation is right!" — the oracle check found both disagreed at 4000 ("MMMM" vs "M?"). — [part 2](https://fsharpforfunandprofit.com/posts/property-based-testing-4/)

**Jane Street interview study** (read in full) — Goldstein, Cutler, Dickstein, Pierce, Head, *Property-Based Testing in Practice*, ICSE 2024, [PDF](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf), [ACM](https://dl.acm.org/doi/10.1145/3597503.3639581):
- Method: "30 in-depth interviews with experienced users of PBT at Jane Street". Abstract: "PBT's main strengths lie in testing complex code and in increasing confidence beyond what is available through conventional testing methodologies, and that most uses fall into a relatively small number of high-leverage idioms. Its main weaknesses lie in the relative complexity of writing properties and random data generators and in the difficulty of evaluating their effectiveness."
- §4.3 idioms: "**Classical Properties (11/30).** ... mathematical properties (e.g., the commutativity of addition), properties drawn from CS theory (e.g., repeated sorting has no effect), and properties that naturally fall out of a data structure's invariants (e.g., the ordering condition of a BST)." "**Round-Trip Properties (11/30)** are also common in the literature; we heard about them so much more often than the other classical cases that they seem worth calling out on their own... parsing and pretty-printing or encoding and decoding". "**Catastrophic Failure Properties (7/30).** Rather than write logical specifications, some participants used PBT to try to provoke catastrophic failures such as assertion failures and uncaught exceptions. In general, these kinds of properties provide less confidence in code quality (there can still be logical errors, even if the code does not crash), but they help to rule out worst-case scenarios and they are easy to write." "**Differential Properties (17/30).** A 'differential property' (in sense of differential testing [25]) compares the system under test to a reference implementation of the same functionality that serves as a specification; these are often also called model-based properties (c.f. model-based testing [54]), especially when the reference implementation is designed to be an abstract model of the original code. Differential properties were by far the most widely implemented kind of property. Differential properties were described as a 'natural place to use property based testing' (P3)—indeed, one participant remarked that PBT was challenging in a particular situation in part because a good reference implementation was not available (P1)."
- "The common theme of the high-leverage scenarios described above is the availability of a succinct abstraction that can be used in writing a property. These PBT scenarios were summed up by P9 with the following mantra: '[PBT is] most useful when... you have a really good abstraction with a complicated implementation.'"
- OB4: "Property-based testing is used opportunistically in high-leverage scenarios where properties are readily available; developers rarely go out of their way to write subtle specifications... participants generally did the opposite: they saw an obvious testable property and then decided to use PBT." RO2: "Improve support for differential and model-based testing. As the most popular high-leverage scenario for PBT, differential testing seems particularly interesting as a topic of further research."
- Related work confirms the pattern in open source: "A study analyzing open-source libraries using Hypothesis [12] ... found that both round-trip and differential or model-based testing are overrepresented in real-world tests." "An experience report from Amazon [9] described differential testing as a major use-case of PBT".

**MacIver, Hypothesis** (read in full):
- "Rule Based Stateful Testing" (2016): a binary heap tested first with a fixed-shape property (`assert r == sorted(ls)`), then with a `RuleBasedStateMachine` whose `pop` rule checks `correct = min(self.heap); result = heappop(self.heap); assert correct == result` — the "model" is just `min` over the same list. "Instead of just letting Hypothesis give us data which we feed into a fixed structure of test, we let Hypothesis choose which operations to perform on our data structure". The subtly-broken `heapmerge` needed a 13-step sequence of merges; "I don't know about you, but I would never have come up with that example... if it takes this complicated an example to demonstrate that a completely wrong implementation is wrong, how hard can it sometimes be to demonstrate subtle bugs?" Real-world: Hypothesis's own example-database tests; Mercurial bugs 5112 and 5113. — [hypothesis.works article](https://hypothesis.works/articles/rule-based-stateful-testing/) ([source](https://github.com/HypothesisWorks/hypothesis/blob/master/website/content/2016-04-19-rule-based-stateful-testing.md))
- "What is Property Based Testing?" (2016): "Historically the definition of property based testing has been 'The thing that QuickCheck does'." Proposed definition: "Property based testing is the construction of tests such that, when these tests are fuzzed, failures in the test reveal problems with the system under test that could not have been revealed by direct fuzzing of that system." "property based testing requires you to reason about how your program should behave, while fuzzing can just be applied to arbitrary programs with minimal understanding of their behaviour". On oracles: running a formatter over a corpus and checking PEP8 "is classic property-based testing with an oracle." — [hypothesis.works article](https://hypothesis.works/articles/what-is-property-based-testing/)

### Inferences
- The ranking that emerges across Hughes (controlled), Jane Street (interviews), and the Hypothesis corpus (snippet) is consistent: **model/oracle/differential ≫ round-trip ≈ postcondition > metamorphic (individually) > invariant-only > crash-only** in bug-finding power per property, while cost rises in roughly the same order except that round-trip is both cheap and strong (which is why it is over-represented in practice).
- Hughes's speed result generalizes into a design rule: a property that checks *the whole observable state* after each operation (model-based) detects a bug the first time it is triggered; a property that spot-checks one random observation (postcondition with a random key) needs the bug to be triggered *and* observed, which multiplies tests-to-failure by roughly the inverse of the observation probability (≈6× in his `union` example).
- Validity properties are not for finding logic bugs; they exist to localise failures (generator bugs vs implementation bugs) and to keep model-based failures debuggable. Every author who ran a real campaign (Hughes, Wickström, Goldstein's interviewees) reports bugs in generators or tests before bugs in code.
- Weak/preconditioned variants of properties (Hughes's `*_weak`, Wickström's `prop_two_failures_are_returned`) are explicitly less effective but are defended as cheap, decoupled starting points to be strengthened later.

## Key Question 2: What do the experts say when the model is as complex as the implementation ("am I just re-writing the logic")?

### Takeaway
Hughes names replicating the implementation as "the most obvious approach... and it is deeply unsatisfying... both *expensive*... and of *low value*", and the entire How-to-Specify-It method exists to avoid it; his answer for model-based properties is the **abstraction function**: the model is a *different, simpler data type* (a list, not a tree; "a few lines of Erlang" vs "one or two thousand lines of C") that is allowed to be slow, non-thread-safe and memory-hungry because it omits everything the implementation does for performance. When the model would still "resemble the implementation so closely that the same bugs are likely in each", he recommends switching to metamorphic properties; Wickström, Goldstein et al. and Wlaschin independently describe the same trap ("tests end up mirroring... the full implementation complexity", "over-specifying... comparing to a behaviorally complete model... which might need to be separately implemented") and the same escapes: abstract away, generate expected output instead of input, use a deliberately naive oracle, or accept weaker/partial properties.

### Cited Findings

**Hughes, How to Specify It! (verbatim via Link's reproduction)** — [Link remix](https://johanneslink.net/how-to-specify-it/):
- The trap, stated at the outset with `reverse`: "but `predictRev` *is not easier to write than reverse* — it is *exactly the same function*! This is the most obvious approach to writing properties — to replicate the implementation in the test code — and it is deeply unsatisfying. It is both an *expensive* approach, because the replica of the implementation may be as complex as the implementation under test, and of *low value*, because there is a grave risk that misconceptions in the implementation will be replicated in the test code. 'Expensive' and 'low value' is an unfortunate combination of characteristics for a software testing method!" Slogan: "**Avoid replicating your code in your tests.**"
- "Now we have seen the benefits of property-based testing — random generation of very many test cases, and shrinking of counterexamples to minimal failing tests — and the major pitfall: the temptation to replicate the implementation in the tests, incurring high costs for little benefit. In the remainder of this paper, we present systematic ways to define properties *without* falling into this trap."
- The same trap recurs for `find`: "to write a postcondition for `find`, we need to be able to determine whether a given key is present in a tree, and if so, with what associated value. *But this is exactly what `find` does!* So it seems we are in the awkward situation discussed in the introduction: in order to test `find`, we need to reimplement it." Escape: "constructing a test case whose outcome is easy to predict" (test `find k (insert k v t)` and `find k (delete k t)`), plus a completeness property proving those forms cover all trees.
- Even "simple" invariant checks get the same treatment — prefer the obviously-correct slow version over the clever fast one: "This definition is obviously correct, but it is an inefficient implementation of the validity checking function; it is quadratic in the size of the tree in the worst case... But the equivalence of these two definitions depends on reasoning, and we prefer to *avoid reasoning that is not checked by tests*... We prefer, therefore, to use the obvious-but-inefficient definition, at least initially. The trees we are generating are relatively small, so quadratic complexity is not a problem."
- The model-based answer: the model is a *different representation* related by an abstraction function (Hoare 1972): "we abstract trees `t` (the concrete implementation) as ordered lists of key–value pairs `kvs` (the abstract data), using an abstraction function which is just `toList()`". Slogan: "Abstract away from details to simplify properties." The model operations are library one-liners (`L.insert`, `filter`, `L.unionBy`, `L.lookup` — see KQ1 code).
- The explicit condition under which the model is *not* the right tool, and what to do instead: "In situations where the model is complex (and thus expensive) to define, or where the model resembles the implementation so closely that the same bugs are likely in each, then metamorphic properties offer an effective alternative, at the cost of writing many more properties." And: "metamorphic testing ... is a useful alternative, especially in situations where a model is expensive to construct."
- Postconditions as a middle ground that avoids reimplementation: `insert_post_same_key` "devotes *all* test effort to the case of finding a newly inserted key, but does not require us to replicate the code in the more general postcondition."

**Hughes, Experiences with QuickCheck (2016)** — `[SNIPPET]` (cs.tufts.edu / chalmers / springer blocked). Search snippet attributed to the paper, on the Erlang process registry model vs. implementation: "The model is just a few lines of Erlang code, while the implementation is one or two thousand lines of C in the guts of the Erlang virtual machine—because it uses far more efficient data structures, manages memory explicitly, and needs to be thread-safe on multicore processors. The model is indeed much simpler than the implementation whose behaviour it specifies." — mirrors: https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf , https://publications.lib.chalmers.se/records/fulltext/232550/local_232550.pdf , DOI 10.1007/978-3-319-30936-1_9. Another snippet (slide/talk summary, unverified): "The test code is 3-6x smaller than the implementation"; "surprisingly simple models can discover defects, such as in Riak where a failing corner case was found using only a single key and few concurrent clients"; talk slogan "Don't write tests! Generate them!" — https://slideplayer.com/slide/4692582/ , https://www.youtube.com/watch?v=V8v-1PnFisU (Midwest.io 2016).

**Goldstein et al., HATRA 2022, *Some Problems with Properties*** (read in full) — [PDF](https://harrisongoldste.in/papers/hatra2022.pdf): the over-specification failure mode named explicitly: "While participants did write properties, often times they either under-specified the behavior of the system (for instance, simply testing that a program does not crash), or over-specifying it (for instance, comparing to a behaviorally complete model of the program under test, which might need to be separately implemented) (P1, P3–5). These participants were not testing conventional PBT properties, which either undermined the power of their tests or led to tests that could be brittle or time-consuming to implement." "P1 described this as the problem of 'formulating the right property in the first place,' a difficulty they had experienced despite prior successes using PBT following an over-specified model-based approach." P1 quote: "The hard part is knowing when you have a property that you can test and how to write that test. What would make it easier? I almost feel like more examples, you know, like... just examples upon examples upon examples".

**Goldstein et al., ICSE 2024** (read in full) — [PDF](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf): the positive framing of the same issue — a model is worth it when the abstraction is *succinct*: "The common theme of the high-leverage scenarios described above is the availability of a succinct abstraction that can be used in writing a property... '[PBT is] most useful when... you have a really good abstraction with a complicated implementation.'" (P9). Conversely P1 found PBT "challenging in a particular situation in part because a good reference implementation was not available". P4: "I think the most common failure mode is actually not knowing what properties to test." P2: "With [example-based unit tests], I kind of look at it, I can just make a snap judgment as to whether this is okay or not. Trying to formalize that judgment sometimes can be very difficult." RO3 describes a workaround for poorly-abstracted modules: "P5 described a technique that they used to test a poorly abstracted module with an overly complicated interface: instead of writing normal properties, they instrumented the module with log statements, wrote properties about what those logs should look like, and then tested the module via an external interface that hides many of its internal details."

**Wickström** (read in full):
- The trap, named: "It's not uncommon in example-based testing that tests end up mirroring the structure, and even the full implementation complexity, of the system under test. The same can happen in property-based testing. With some complex systems it's very hard to describe the correctness as a relation between any valid input and the system's observed output. The video classifier is one such case. How do I decide if an output classification is correct for a specific input, without reimplementing the classification itself in my tests?" Escape: "The other way around is easy, though! If I have a classification, I can convert that into video frames. Thus, the solution to the testing problem is to not generate the input, but instead generate the *expected output*. Hillel Wayne calls this technique 'oracle generators' in his recent article." "When using oracle generators, the assertions can often be plain equality checks on generated and actual output." — [Case Study 2](https://wickstrom.tech/2019-04-17-property-based-testing-in-a-screencast-editor-case-study-2.html)
- Why it is hard at all: "Why it's so hard to come up with these properties? I'd argue that it's because doing so forces us to understand our system in a way we're not used to. It's challenging understanding and expressing the general behavior of a system, rather than particular *anecdotes*". — [Introduction](https://wickstrom.tech/2019-03-02-property-based-testing-in-a-screencast-editor-introduction.html)
- The single-property-vs-many trade-off and the mirroring cost: "The drawback of using a single property is that the assertion not only becomes more complicated, it's also likely to mirror the implementation of the SUT. As we saw with our single property testing the validation function, the assertion duplicated the validation rules... there's a strong coupling... They both suffer from the classic problem of a test suite mirroring the system it's testing." And a defence of weak properties: "weak properties are beneficial in that they are: 1. easier to define 2. likely to catch simple mistakes early 3. less coupled to the SUT... If you can't formulate the strong property you'd like, instead start simple. Lure out some bugs, and improve the strength and specificity of your properties over time." — [Time Travelling](https://wickstrom.tech/2019-11-17-time-travelling-and-fixing-bugs-with-property-based-testing.html)
- Integration-level properties as the escape from implementation coupling: "At that level, the property tests are less tied to the implementation, and focus on describing the higher-level outcomes of the interaction between subsystems." — [Case Study 1](https://wickstrom.tech/2019-03-24-property-based-testing-in-a-screencast-editor-case-study-1.html)
- Note on "when the model is the implementation": I read all five Komposition posts; none contains that phrase. The closest passage is the classifier paragraph above. The phrase may come from his talk "Property-Based Testing The Ugly Parts" (flatMap Oslo 2019, https://2019.flatmap.no/talks/wickstrom, not reachable).

**Wlaschin** (read): "Now, we normally can't prove that the internals of an implementation are correct without duplicating the function under test. But often we can determine that the *output* is correct quite easily." (hard-to-prove/easy-to-verify as the primary escape). The oracle is legitimate precisely when it is *not* production-grade: "Often the test oracle implementation is not suitable for production -- it's too slow, or it doesn't parallelize... but that doesn't stop it being very useful for testing." A naive brute-force oracle is "much slower but is also much easier to write correctly." And: "If [model and SUT] are the same, you're done. If not, either your SUT is buggy or your model is wrong and you have to start over!" — [part 1](https://fsharpforfunandprofit.com/posts/property-based-testing-3/), [Choosing properties](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)

**MacIver**: the heap model is not a second heap — it is `min(self.heap)` on the same list, i.e. a one-line specification of the observable result; the state-machine's job is to generate operation *sequences*, not to re-implement the heap. — [Rule Based Stateful Testing](https://hypothesis.works/articles/rule-based-stateful-testing/)

**quickcheck-state-machine README** (read): the model for `IORef`-based mutable references is "a simple map between references and integers" — `newtype Model r = Model [(Reference (Opaque (IORef Int)) r, Int)]` — and the same sequential model is reused for race detection with no extra specification: "the model can still be designed to work sequentially as *it will not be run in parallel*, it will only be advanced in a sequential way when evaluating possible interleavings. This particularly means that the model must be correct with respect to sequential execution before used in parallel testing." — https://hackage.haskell.org/package/quickcheck-state-machine ([README](https://github.com/stevana/quickcheck-state-machine))

### Inferences
- The consensus answer to "am I rewriting the logic?" has four parts, each with a named expert source: (a) **change the data type** — model a different, simpler representation reached through an abstraction function, so the model cannot share the implementation's representation bugs (Hughes; Hoare); (b) **drop everything that exists for performance or concurrency** — the model may be O(n²), single-threaded, immutable, allocation-heavy (Hughes's registry quote; his "obvious-but-inefficient" validity function; Wlaschin's "too slow... doesn't parallelize"); (c) **if the abstract version would still be structurally the same algorithm, don't write a model** — use metamorphic relations, postconditions on constructed cases, round-trips, or oracle *generators* instead (Hughes §5.3; Wickström classifier); (d) **a naive reference implementation is a legitimate special case** (differential testing), and is in fact the dominant practice at Jane Street and in open-source Hypothesis use, *provided* it is genuinely simpler or independently written (Wlaschin's two Roman-numeral algorithms; Goldstein RO2).
- "The model should be obviously correct" is implicit rather than explicitly stated in any source I read; the nearest explicit statements are Hughes's "This definition is obviously correct, but it is an inefficient implementation" (about the validity checker) and "we prefer to *avoid reasoning that is not checked by tests*". The operational test for a good model is Hughes's: can the model operation be a library one-liner on a plain collection?
- Hughes's own first model attempt (`L.insert` on a sorted list) was *wrong* and QuickCheck exposed it; Wlaschin says the same ("either your SUT is buggy or your model is wrong"). Experts treat model bugs as a normal, cheap part of the loop, not a reason to avoid models — which only works if the model is small enough that fixing it is trivial.
- For a README aimed at people and coding agents: the concrete "stop" signal is Hughes's phrase "the model resembles the implementation so closely that the same bugs are likely in each". The concrete "go" signal is Goldstein's "a really good abstraction with a complicated implementation".

## Key Question 3 (supporting): How were real-world models built, and how do they handle nondeterminism? (case studies)

### Takeaway
Across the industrial cases, the model is always a small abstract state plus per-operation transitions and postconditions: a list of (name, pid) pairs for the Erlang registry, a map from references to ints, `Data.List` for a BST, a "server value" plus per-node local values with invisible "conjectured" upload/download events for Dropbox, 20,000 lines of QuickCheck standing in for 3,000 pages of AUTOSAR prose. Nondeterminism is handled not by making the model deterministic but by letting the model carry hidden state that may change at any time and accepting any observation consistent with *some* sequence of hidden events (Dropbox), or by checking that a concurrent history is explainable by *some* sequential interleaving of the unchanged sequential model (PULSE / quickcheck-state-machine); both let the same simple model serve.

### Cited Findings
- **Erlang process registry & dets (PULSE, ICFP 2009)** — `[SNIPPET]`; paper at https://publications.lib.chalmers.se/records/fulltext/125252/local_125252.pdf (blocked), ACM 10.1145/1631687.1596574. Snippets: "QuickCheck's state-machine testing was extended to execute two independent command sequences concurrently, with correctness defined through a linearizability-style criterion where observed results must be explainable by some sequential ordering of the operations." "To test the process registry using eqc_par_statem, it is necessary to modify the property to use eqc_par_statem rather than eqc_statem to generate and run test cases." Bugs: "the method exposed two race conditions—one involving message overtaking and inconsistent cleanup of forward and reverse registry entries, and another arising when multiple clients attempted to register a dead process concurrently after independently auditing the registry." dets: "Hughes and Bolinder applied the same combination of QuickCheck-generated parallel tests, randomized scheduling, and sequential-consistency checking to dets, a substantially larger database component of Erlang/OTP, and reported finding five race conditions, including two that could plausibly explain production failures" (that is the follow-up paper *Testing a database for race conditions with QuickCheck*, Erlang Workshop 2011, https://dl.acm.org/doi/abs/10.1145/2034654.2034667). ### Inferences
- The two nondeterminism strategies are duals of the same idea — "accept any observation explainable by some hidden choice": PULSE/qsm search over interleavings of a deterministic sequential model; Dropbox adds unobservable events to the model state. In both, the model stays a *specification* (what results are allowed) rather than a *simulator* (which result will occur). Hughes's guidance that "the model may be nondeterministic" / "postcondition as a set of allowed results" (in the assignment brief) is consistent with these snippets but I could not verify the wording.
- The case studies all keep the model's per-operation transition tiny and push effort into (i) generators (operation sequences, precondition-satisfying data) and (ii) deciding what is observable (e.g., `toList`, quiescence). That is where a README should direct effort too.
